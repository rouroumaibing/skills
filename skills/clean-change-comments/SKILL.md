# clean-change-comments（注释规范：函数名即说明，注释只讲功能 + 参数）

## 这个 skill 的核心原则（一句话）

> **好的代码，函数名称就说明了功能；要加注释，最多是一句话描述该函数什么功能，下面再列一下输入输出参数是什么。配置文件就只需要说明一下，这个配置参数是什么功能的开关即可。**

这就是全部要点的浓缩。下面解释为什么**这一条就能覆盖之前所有的"清理注释"规则**，以及它顺带解决了什么。

## 为什么这条原则能覆盖之前的修改规则

之前散落的多条规则——「禁止变更叙述（原来是 / 改为 / 不再）」「禁止复述实现逻辑（遍历…累加）」「配置注释不写实现细节」——其实都是同一条原则的不同切面：

- **「原来是 / 改为 / 不再 / 已废弃」这类变更叙述**：它不是"一句功能说明 + 参数"，所以按核心原则直接删。它只是把"变化过程"写进了注释，而注释该写的是"现在做什么"。
- **「遍历列表逐项累加」「先校验再写入」这类实现复述**：同样不是"功能说明"——代码 / 好命名已经说清了"做了什么"，再抄一遍是噪音。删。
- **配置里的"探测顺序 / 内部变量名 / 底层服务片段"**：它不是一个"开关控制什么功能"的说明，所以移出，只留用户视角的开关含义。
- **那"历史 / 决策"去哪？** 既然注释只描述功能，历史与决策本就不属于注释——它们落到「变更历史」章节或 commit message（见规则 2）。这正是"删掉变更叙述"的另一半：不只是"注释里别写"，更是"该写的地方写对"。

所以不需要一堆并列的"禁止清单"。遵守核心原则，下面的规则自然成立。

## 规则

### 规则 1：注释只写「功能 + 参数」，不写实现、不写历史

- **正例**：一行功能描述 +（必要时）输入 / 输出参数列表。

  ```ts
  // 把未读数聚合成按会话分组的摘要，供侧边栏展示
  // 入参：raw: UnreadItem[]   出参：GroupedSummary
  function summarize(raw: UnreadItem[]): GroupedSummary { /* ... */ }
  ```

- **反例（一律删除）**：
  - 变更叙述：`// 原来用 map，改成 sync.Map`
  - 实现复述：`// 遍历列表过滤活跃用户再按时间排序`
  - 指路导读：`// 见 README` / `// 无需配置，详见 xxx`
- **唯一允许的例外——"why"注释**：当一段代码"看起来能简化但改了会出问题"（**防回退**），或"不写后人看不懂为什么这么写"（**非直觉业务规则 / 外部约束**），可留**一行**为什么，绝不讲故事、绝不讲实现步骤：

  ```ts
  // 防回退：看似可合并为一次 Set，但两字段更新频率不同，合并会丢更新
  // 外部约束：用 sessionStorage——关闭页面需清除登录态（不能用 localStorage）
  ```

判断口诀：**删掉这句注释，代码含义是否依然完整可读？是 → 删。**

### 规则 2：历史与决策不进注释，落到「变更历史」/ commit

注释只描述功能，所以"什么时候改了什么、为什么改、当时考虑了哪些方案"不属于注释，去两处之一：

- **变更历史**（谁 / 何时 / 改了什么 / 为什么）→ 文档「变更历史」章节（或 CHANGELOG）、或 commit message。**格式**：日期 + 变更内容 + 原因，一行即可。
- **决策**（结论 + 理由 + 时间）→ 对应设计文档的「变更历史」章节 + commit。**决策时间只有唯一归宿**：只出现在「变更历史」章节，绝不漏到文档标题 / 副标题 / 状态行 / 正文 inline，也不另起带日期的「决策记录」章节（并入「变更历史」即可）。

理由：历史一旦散落到正文 / 标题，会随演进变成又一处会过时的叙述，也让"只读正文就够"的承诺失效。

### 规则 3：配置文件注释只说「这个开关控制什么功能」

配置文件（yaml / yml / toml / ini / cfg 等）是使用者配置必经之路，注释只服务"用户要填什么、这个开关控制什么功能"：

- **该写**：字段含义、合法取值 / 可选值、留空默认行为、**该开关控制的功能是什么**。
- **不该写**：探测算法与顺序、内部环境变量名（NODE_IP / POD_IP）、兜底 / 回退逻辑、底层服务片段（dnsmasq 的 `bind-interfaces` / `listen-address`、ntp 的 `restrict default` / `fudge`）、具体网卡选取——这些属于代码或 README。

```yaml
# ❌ 违规：泄漏实现细节
# listen_ip：缺省自动探测本机 IP（顺序：NODE_IP/POD_IP → 默认路由出口 IP）；探测失败兜底 0.0.0.0

# ✅ 合规：只说这个开关控制什么
# listen_ip: ""   # 可选：留空自动探测本机 IP；填了则绑定该地址
```

### 规则 4：提交前自检 + 顺手清理残留（附扫描脚本）

**落笔前 30 秒**：这条注释是我正要新写的吗？先归类——是「防回退 / 非直觉约束」的 why 一行？是「功能 + 参数」说明？都不是 → 不写。

**处理已有文件时**：顺手扫描并清理其中残留的变更叙述注释、决策日期泄漏（规则 2），以最新内容重写，不留"原来是 / 改成了"的尾巴。这不是额外任务，是改这块代码顺带该做的。

**本次改动用 diff 全量复核**：提交前跑 `python scripts/detect_change_narrative.py <路径> --diff`，把 `git diff` 里**所有新增注释行**拉出来标为「待归类」——注释必要性无法机器判断，"出现在 diff 里"本身就是复核触发器。逐条归类：**属于「防回退 / 非直觉约束」why 一行、或「功能 + 参数」说明才保留，其余（含变更叙述、实现复述）即删**。

**关于废弃注释所附的代码（安全边界）**：删注释可直接做；删它下面的代码要谨慎——显然无用的（空桩、死分支、无调用方）可一并删并说明；非空实现 / 可能有调用方的，只删注释、把代码标记「待人工确认」，不擅自删代码（删除不可逆，先确认 scope）。

## 判定清单（落笔前 30 秒）

- [ ] 这条注释是新写的吗？归类：防回退 / 非直觉约束 why 一行 / 功能 + 参数说明 / 其他——**其他一律不写**（尤其「见 xxx」指路类）。
- [ ] 它是在**复述实现逻辑**或**讲变更历史**（"原来是 / 改为 / 不再"）吗？是 → 删。
- [ ] 留下的 what 说明是否严格是"一句功能 + 输入 / 输出参数"、没写成"先…再…"步骤？否 → 压成一句或删。
- [ ] 留下的 why 注释是否恰好一行、讲"为什么"不讲"怎么实现 / 怎么变的"？否 → 压一行或删。
- [ ] 「这次为什么改」「为什么选这个方案」写进变更历史或 commit 了吗？别留在正文 / 代码。
- [ ] **决策日期是否漏到标题 / 副标题 / 状态行 / 正文 inline？是 → 移到「变更历史」章节。**
- [ ] 顺手扫了同文件旧注释，清掉残留变更叙述与决策日期泄漏了吗？
  - [ ] 配置文件注释是否只说"这个开关控制什么功能"？实现细节是否已移出？

## 落地工具：变更叙述扫描脚本

处理已有文件、大范围自查时，用脚本先扫出候选，再人工判断（脚本只标记、不自动改，避免误删有意为之的注释）：

```
python scripts/detect_change_narrative.py <文件或目录> [--json] [--ext go,ts,py,md,mjs,vue,makefile,sql,yaml,sh]
```

提交前自查**本次新写内容**时加 `--diff`：只扫 `git diff <BASE>`（缺省 `HEAD`，`--diff <ref>` 可指定基准）新增的行，新增注释**全量标记**为候选（必要时会吵，属有意设计——注释必要性无法机器判断，人工逐条归类），md 正文只标禁词 / 日期命中：

```
python scripts/detect_change_narrative.py <文件或目录> --diff [BASE]
```

- 对代码文件：只在注释行里检查变更叙述禁词（自动识别 `//` `#` `--` `/* */` 及行尾注释）。**覆盖**：Go/TS/JS/Java/C 系（`//` 与 `/* */`）、Python/Shell/YAML/Makefile（`#`）、SQL（`--`）、Vue 的 `<script>` 块（`//` 与 `/* */`）。
- **Makefile 按文件名匹配**（`Makefile`/`GNUmakefile`/`kbuild`，无扩展名也扫），不靠扩展名。
- **Vue 文件双重扫描**：既扫 `<template>` 里的 `<!-- -->` HTML 注释，也扫 `<script>` 块内的 `//` / `/* */` 注释。
- 对 Markdown：检查所有正文行与**标题行**，但**跳过「变更历史 / 变更记录 / CHANGELOG / ADR」类章节的正文**（那些是合法去处）；**标题行若带决策日期（如 `## 结论（2026-10-08 裁定）`）会被标记**——标题不得承载决策日期。
- **决策日期泄漏检测**：脚本额外标记 `（2026-xx-xx 裁定 / 修正 / 拍板 / 设计已定 / 决策）` 这类把决策日期写进正文 / 标题的标记（规则 2），因为它们不属于「变更历史」章节，是决策时间的非法去处。
- **配置文件注释冗余检测（规则 3）**：对 yaml/yml/toml/ini/cfg 等配置文件的注释，除变更叙述禁词外，额外用一组「实现细节」标记（如 `顺序：...→`、`NODE_IP/POD_IP`、`默认路由出口`、`探测失败兜底`、`bind-interfaces` / `listen-address` / `restrict default` / `fudge`、内部环境变量说明）标记疑似泄漏实现细节的行，命中模式前缀 `[配置冗余]`。同样只标记不修改，噪声需人工过滤。
- **核心原则召回（`[待归类]` 前缀）**：指路导读、实现复述、时间/版本标记、配置实现措辞，以及连续 ≥4 行非装饰注释块，均可机械召回，统一标为「待人工归类」；脚本只召回、不判定，是否删除由人按核心原则裁决（与 `--diff` 的「新增注释·待归类」同属召回层）。
- 输出 `文件:行号 | 命中模式 | 该行内容`，方便逐条复核。`--json` 输出机器可读结果，便于接入 CI 或批量处理。

**diff 模式「待归类」口径**：所有新增注释行（未命中禁词者）标为「待归类」，其中既含可能合理的 why 一行 / 功能 + 参数说明，也含「变更叙述」「实现复述」类。归类时后者一律删除——脚本只负责把候选捞出来，是否合规由人工按核心原则判断。

（脚本详细用法见同目录 `scripts/detect_change_narrative.py`。）

## 反例 ↔ 正例对照

| 场景 | ❌ 违规 | ✅ 合规（核心原则下） |
| --- | --- | --- |
| 并发结构 | `// 原来用 map，改成 sync.Map` | `// sync.Map：本结构被多 goroutine 并发读写`（防回退 why 一行） |
| 存储选择 | `// 不要用 localStorage，改用 sessionStorage` | `// sessionStorage：关闭页面需清除登录态`（外部约束 why 一行） |
| 复述实现逻辑 | `// 遍历用户列表，过滤活跃用户，再按创建时间排序` | （删掉；函数名 + 列表推导已说明；若需说明只留"一句功能 + 参数"） |
| 函数注释 | `// 先查缓存，未命中再查库，最后组装返回` | `// 组装用户画像，优先读缓存、未命中回源；入参 uid，出参 Profile` |
| 文档正文 | `本章原先描述 v1 流程，已更新为 v2` | （直接写 v2；v1→v2 记入变更历史） |
| 决策时间泄漏 | `## 结论（2026-10-08 裁定）` | 正文只写当前事实；结论 + 理由 + 日期进「变更历史」 |
| 配置注释 | `# 监听地址：缺省探测本机 IP（顺序 NODE_IP/POD_IP → 默认路由）；兜底 0.0.0.0` | `# listen_ip: ""   # 可选：留空自动探测；填了则绑定该地址` |

## 语言

注释 / 文档语言跟随项目现状（看代码库与既有文档用什么），不强制中文或英文。本规范约束的是「注释是否只描述功能 + 参数」，与用哪种语言无关。
