# clean-change-comments（注释与文档的"只描述现状"规范）

## 这个 skill 解决什么问题

代码注释和文档正文会随修改"长"出历史叙述——「原来是 X，改成 Y」「这里不再用 A 了」「禁止用 B 改用 C」。这些话在写下的那一刻是清楚的，但代码会一直改下去，叙述却不会跟着更新。三个月后，那段「改成 Y」早已是旧闻，读代码的人却被它牵着走：要么误以为 Y 是某种特殊选择，要么照着叙述去「改回」一个早已不存在的东西。

本 skill 把一条规则钉死：**修改即意味着旧内容作废**。正文和注释只描述「现在是什么、为什么是这样」，不描述「它之前是什么、怎么变的」。变更的历史有专门去处（变更记录 / commit message），方案的取舍有专门去处（决策记录），都不进正文。

这不是洁癖，是让「后来者读到的永远是当前事实」的最低成本办法——否则每份文件都得先做一次真伪辨别的考古。

## 核心原则

> 后来者打开文件，应该只读得到「现在」，不需要知道「曾经」。凡是描述「变化过程」的文字，都在正文之外另有归宿。

## 启用判定（什么时候走这套规范）

| 场景 | 是否启用 |
| --- | --- |
| 修改代码、写或改代码注释 | 启用 |
| 修改文档正文（设计文档、README、规格说明） | 启用 |
| 用户说「清理注释」「整理文档」「删掉历史说明」 | 启用 |
| 提交前对改动做注释/文档自查 | 启用 |
| 处理已有文件时发现残留的变更叙述注释 | 启用（顺手清理） |
| 纯新增、且内容本身不涉历史叙述的文案 | 一般无需，但落笔时仍按规则 2 自查 |
| 写变更记录章节、决策记录章节本身 | 不启用本规范（那是它们的正职） |

**不确定就启用**：误用本规范最多让注释更干净；漏用会让旧叙述继续误导。

## 五条规则

### 规则 1：正文只描述当前状态，禁止变更叙述

代码注释和文档正文里，不得出现描述「变化过程」的叙述。典型禁词（中英文同义）：

- 原状态类：**原来是 / 原是 / 原本 / 原先 / 以前 / 之前 / 以前是 / 起初**
- 改动动作类：**改为 / 改成 / 修改为 / 已改 / 换成了 / 替换成**
- 停止类：**不再 / 已不再 / 不再使用 / 不再支持**
- 废弃类：**已废弃 / 已弃用 / 废弃 / 弃用 / 过时 / 旧版 / 老做法 / 旧逻辑**
- 替用指令类：**禁止 xxx 改用 xxx / 改用 / 不要再用 / 切勿 / 不要再 / 不应该再**
- 动作回顾类：**新增了 / 删除了 / 重构了 / 优化了 / 迁移到 / 升级到 / 已修复**

为什么：禁词描述的是「变化过程」，而文件只应留存「现在」；错位后的叙述会主动误导后来者。

**正确做法**：直接写成现状。修改即作废旧内容，不留痕迹。

```go
// ❌ 违规：变更叙述
// 原来用 map 存，改成 sync.Map 以支持并发读写

// ✅ 合规：只描述现状 + 一行理由（非直觉约束）
// 用 sync.Map：本结构会被多个 goroutine 并发读写
var cache sync.Map
```

### 规则 2：只允许两类「现状理由」注释（一行，只讲现在）

只有下面两种情况，才允许在代码里留一行注释，并且**只描述现状为什么是这样**，不回头讲历史：

1. **防回退说明**：某段代码看起来能简化、但换个写法会出问题。留一行说明「为什么不能动」，防止后来者「好心」改坏。
2. **非直觉的业务规则或外部约束**：不写这行，后来者看不懂为什么这么写，或会按直觉改错。

写法示例：

```ts
// ✅ 防回退：看似可合并为一次 set，但两个字段有独立更新频率，合并会丢更新
// ✅ 外部约束：用 sessionStorage——页面关闭后需清除登录态（不能用 localStorage）
```

约束：
- **一行为限**，不展开讲故事。
- 主语是「现在怎么做、为什么必须这样」，不是「以前不是这样」。
- 凡是不满足这两类、或多于一行的「解释」，要么删掉，要么挪到规则 3 / 规则 4 的归宿里。

### 规则 3：变更历史 → 变更记录章节或 commit message

「什么时候改了什么、为什么改」放两处之一：

- 文档里的 **「变更记录」** 章节（或 CHANGELOG）；
- 或 **commit message**。

格式：**日期 + 变更内容 + 原因，一行即可**。例如：

```markdown
## 变更记录
- 2026-10-08 将缓存结构由 map 改为 sync.Map，因需支持并发读写
```

不得写进正文、不得写进代码注释。变更记录 / CHANGELOG 章节本身不受本规范约束——它们就是干这个的。

### 规则 4：方案选型 / 判断逻辑 / 被否决备选项 → 决策记录

「为什么选 A 不选 B」「当时考虑了哪些方案」「为什么否决了 C」这类内容，写入对应开发文档的 **「决策记录」** 章节（或 ADR）。**代码里不重复这些**——代码只体现最终选择。

理由：决策推理塞进代码会变成又一处会过时的叙述；放决策记录里既不与代码耦合，又能在需要时追溯。

### 规则 5：提交前自检 + 顺手清理残留

**写/改完提交前，逐条问自己**：*删掉这条注释，后来者会不会误改它指向的代码？*
- 会 → 它属于规则 2 的「防回退 / 非直觉约束」，保留（且压到一行）。
- 不会 → 直接删，它只是噪音。

**处理已有文件时**：顺手扫描并清理其中残留的变更叙述类注释（规则 1 禁词），一律以最新内容为准重写该处，不留「原来是 / 改成了」的尾巴。这不是额外任务，是改这块代码顺带该做的。

**关于废弃注释所附的代码（安全边界）**：删注释是低风险动作，可以直接做；但删它下面的代码要谨慎。判断标准：

- **显然无用的代码**（空桩函数、无人调用的死分支、已被等价实现取代且无调用方）→ 可随注释一并删除，并在回复里说明删了什么。
- **非空实现 / 可能有调用方 / 含真实逻辑的代码** → **只删注释，把代码本身标记为「待人工确认是否删除」**，不要擅自删代码。删除非空实现是不可逆动作，应先确认 scope（调用方、影响面），与删除类操作的既有安全习惯一致。

这条边界只约束「动作大小」，不改变「注释必须清理」的结论——无论代码最终留不留，那句「已废弃 / 不再走这里」的叙述都要先拿掉。

## 判定清单（落笔前 30 秒）

- [ ] 这条注释 / 这段正文，有没有出现规则 1 的禁词？有 → 改成现状描述或删除。
- [ ] 留下的注释是不是恰好属于「防回退」或「非直觉约束」两类之一？不是 → 删。
- [ ] 注释是否超过一行、或在讲历史？是 → 压一行 / 挪到变更记录或决策记录。
- [ ] 「这次为什么改」写进变更记录或 commit 了吗？别留在正文。
- [ ] 「为什么选这个方案」写进决策记录了吗？别留在代码里。
- [ ] 顺手扫了同文件的旧注释，清掉残留变更叙述了吗？

## 落地工具：变更叙述扫描脚本

处理已有文件、大范围自查时，用脚本先扫出候选，再人工判断（脚本只标记、不自动改，避免误删有意为之的注释）：

```
python scripts/detect_change_narrative.py <文件或目录> [--json] [--ext go,ts,py,md,mjs,vue,makefile,sql,yaml,sh]
```

- 对代码文件：只在注释行里检查规则 1 禁词（自动识别 `//` `#` `--` `/* */` 及行尾注释）。**覆盖**：Go/TS/JS/Java/C 系（`//` 与 `/* */`）、Python/Shell/YAML/Makefile（`#`）、SQL（`--`）、Vue 的 `<script>` 块（`//` 与 `/* */`）。
- **Makefile 按文件名匹配**（`Makefile`/`GNUmakefile`/`kbuild`，无扩展名也扫），不靠扩展名。
- **Vue 文件双重扫描**：既扫 `<template>` 里的 `<!-- -->` HTML 注释，也扫 `<script>` 块内的 `//` / `/* */` 注释（脚本块是实际命中高发区）。
- 对 Markdown：检查所有正文行，但**跳过「变更记录 / 决策记录 / CHANGELOG / ADR」类章节**（那些是合法去处）。
- 输出 `文件:行号 | 命中模式 | 该行内容`，方便逐条复核。
- `--json` 输出机器可读结果，便于接入 CI 或批量处理。

（脚本详细用法见同目录 `scripts/detect_change_narrative.py`。）

## 反例 ↔ 正例对照

| 场景 | ❌ 变更叙述（违规） | ✅ 只描述现状（合规） |
| --- | --- | --- |
| 并发结构 | `// 原来用 map，改成 sync.Map` | `// sync.Map：本结构被多 goroutine 并发读写` |
| 存储选择 | `// 不要用 localStorage，改用 sessionStorage` | `// sessionStorage：关闭页面需清除登录态` |
| 废弃路径 | `// 旧逻辑已废弃，不再走这里` | （删掉注释；所附代码按下方说明处置） |
| 接口调整 | `// 之前返回 string，现改为返回 number` | 函数签名即现状；若非直觉，加一行：`// 返回 number：上游只认数值状态码` |
| 文档正文 | `本章原先描述的是 v1 流程，已更新为 v2` | （直接写 v2 流程；v1→v2 记入变更记录） |

## 语言

注释 / 文档语言跟随项目现状（看代码库与既有文档用什么），不强制中文或英文。本规范约束的是「是否描述变化」，与用哪种语言无关。
