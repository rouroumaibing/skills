## 2. 维度检查清单（补漏用）

推演抓不到不挂在具体步骤上的东西（清理策略、授权边界、完成定义），用这张表扫一遍：

| 维度 | 检查问题 | 典型谁填 |
|---|---|---|
| 目标与完成定义 | 做到什么算完成？覆盖哪些用例？ | B |
| 期望值来源 | 断言以文档 / 需求 / 现状为准？谁说了算？ | B |
| 环境与访问 | 地址、网络、依赖的上下游服务？ | A 或 B |
| 账号与权限 | 测试账号、角色、凭证放在哪？ | B |
| 测试数据 | 是否存在、归谁、可否重复、怎么清理？ | B（状态本身是 C） |
| 调用顺序与状态依赖 | 哪个操作必须先做？用例间是否共享状态？ | C |
| 副作用与授权边界 | 哪些环境和数据允许动？ | B |
| 执行方式 | 命令、参数、工具版本？ | A |
| 已知坑与不稳定点 | 历史上出过什么问题？（有上下文文件先查它） | B，有记录则 A |
| 非功能约束 | 超时、并发、幂等、限流？ | C |
| 资源命名链追溯 | 资源由谁创建（声明式模板 / 插件 / 手动）？名字规则是模板变量前缀还是固定名？是否跨实例共享？名字能否用其它字段反推（不能反推 = 只能运行时确认）？ | A 或 C |
| 业务术语与技术字段对齐 | 用例名 / 步骤里的业务术语对应到技术字段时是否字面一致？断言应体现技术实现（真实字段名 / 真实状态值），而非业务说法 | A |
| 交付约束 | 目录结构、代码风格、是否接 CI？ | B |
| 条件分支覆盖 | 有可选依赖、特性开关、dry-run 分支时，每条分支是否都实际跑过一次？ | A |
| 产出物验收 | 生成的配置 / 文件文本，是否按真实消费方的语法验过，而不只是查关键字、看退出码、看命令被调用？ | A 或 C |
| 不可逆操作护栏 | 执行不可逆操作（真实扣款 / 下单、对外发送、删除生产数据、消耗一次性资源）的路径，是否有显式确认开关 + 代价上限 + 期望值核实三件套（或注释声明豁免理由）？ | A |
| 依赖声明 | 新增 import 的第三方依赖是否写入项目依赖清单（requirements / pom / package.json 等）？有条件时是否在干净环境跑过安装 + 收集 / 编译冒烟？ | A |
| 消耗型资源归还 | 用例消耗的不可再生外部资源（配额池 / 许可 / 一次性额度 / 占用型资源）如何归还（回收 / 释放 / 删除 API 或过期机制）？无归还 API 时是否声明「单次消耗」并标注耗尽风险？ | B |

分流规则：

- **A** → AI 直接自查（读代码 / 文档 / 跑命令），不必问人；进表只为留痕。
- **B** → **阻塞的 B 类，解决前不得动手；非阻塞的 B 类，可先做不依赖它的部分，同时等回复**；全部汇入 §4 一轮集中提问，每题的「阻塞：是/否」就是判定依据，不用另加字段。
- **C** → 改写成探针：「假设 <X>，探针：<真实调用 / 对比动作>」，排进 Phase 1。
- **D** → 写入 §6「已采用的默认假设」，**不算待确认项，不阻塞**，交付时汇总给人事后确认。
