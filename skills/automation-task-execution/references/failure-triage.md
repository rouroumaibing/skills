# 失败分类与授权细则

Phase 3 / Phase 4 里每一次报错都走这一套。目标是让人只在**语义问题**上被打断，其余的 AI 自己消化掉。

## 一、三类失败与判定顺序

三类失败**不互斥**。典型叠加：登录过期导致接口返回 401，而文档写的是 200 —— 同时属于「环境或前提问题」和「文档与实际不符」。所以必须按顺序判定，不能按直觉挑一个。

### 判定顺序

1. **能否用确定性手段判定原因？**
   确定性手段 = 读代码、查配置、看日志、查数据、重跑一次。
   **不能 → 归入「语义不确定」，停下来问人。** 这一步是硬闸：判不出来的原因不要硬凑一个听起来合理的解释。

2. **能判定 → 归因到下面三类之一**（见下表），并写下**证据**（哪段日志、哪行代码、哪次重跑）。

3. **按归因处理，且处理动作必须落在授权边界内**（见第二节）。边界外的动作一律先问人。

### 归因表

| 归因 | 判定依据 | 处理动作 | 记录 |
|---|---|---|---|
| **环境或前提问题** | 缺配置、缺数据、登录过期、服务未启动、依赖不可达 | 在授权边界内自行修复 | 追加到上下文文件（类别：环境 / 认证 / 数据 / 依赖） |
| **文档过时或版本差异** | 当前代码 / 实际响应证明文档描述的是旧版本行为；或服务版本与文档版本对不上 | 以实际行为为准，并记录差异 | 追加到上下文文件（类别：文档差异） |
| **疑似产品缺陷** | 实际行为与**当前版本**的合理预期不符，且无法用版本差异解释 | 停下并上报，**不得把缺陷固化成期望值** | 缺陷单 / 报告，不进上下文文件的差异条目 |

### 疑似缺陷的上报格式

```
[疑似缺陷] <接口 / 功能点>
实际行为：<实际响应 / 结果，原文>
预期行为：<预期，及其来源：文档 §x / 用例第 n 步 / 业务规则>
最小复现：<步骤 1..N，可直接照做>
环境：<服务版本 / 环境地址>
已排除：<已验证不是环境、认证、数据、顺序问题>
```

上报后**继续推进其余用例**，不要因为一个缺陷停住整批工作；把该断言标为「待缺陷确认」。

## 二、授权边界

「自行修复」不等于无限授权。下面四类操作都可能不可逆或影响外部，**必须先问**：

| 必须先问 | 为什么 |
|---|---|
| 写入或删除共享库 / 生产库的数据 | 不可回滚，且影响他人 |
| 使用他人账号、修改密码 | 可能触发账号风控、影响真实使用者 |
| 修改流水线、CI、部署等全局配置 | 影响所有人，且常在版本控制之外 |
| 改动他人环境里的任何东西 | 同上 |

**可自行做**（不改既有环境状态，或只改本次任务自己的产物）：

- 读代码、查配置、看日志、查数据
- 起本地服务（本次任务用得上的）
- 修改测试代码与本地配置（本次任务范围内的）

边界不清楚时，**默认按「必须先问」处理**。问的成本是一次对话，猜错的成本可能是不可逆的数据损失。

操作类之外还有**信息类**缺口，同理不得自行处理：凭证、授权范围、期望值来源、完成定义属于只能由人提供的信息，**不允许假设，只能问人**（缺口分类与集中提问方式见 SKILL.md「Phase 0.5 缺口分析」的 B 类）。

## 三、重试边界

- 运行报错时先自行排查修复，**最多重试 3 次**（建议起始值，按项目实际调整）。
- **重试只对瞬时故障有意义**：超时、网络抖动、锁竞争、临时资源未就绪。
- **逻辑错误不重试**：断言不匹配、字段名不对、参数写错 —— 重试一百次结果一样，重试只是在掩盖问题。
- 超过上限仍失败 → 停下汇报，附三样东西：
  1. 错误信息（原文，不要转述）
  2. 已尝试的方法（逐条列出，含结果）
  3. 自己的判断（倾向哪一类原因 + 依据 + 下一步建议）
- 修复之后**说明改了什么、为什么改**——这是上下文文件条目的原料。

## 四、断言强度守恒

**跑通 ≠ 正确。** 这是自动化任务里最容易发生、也最难事后发现的退化：为了让用例通过，断言被悄悄放宽。

### 典型退化动作

| 退化 | 例子 |
|---|---|
| 精确相等 → 模糊包含 | `assertEqual(resp["code"], 0)` → `assertIn(0, str(resp))` |
| 删字段校验 | 断言 `data.qty` 的那行被删掉 |
| 精确匹配 → 正则 / 通配 | `assertEqual(name, "SKU-001")` → `assertRegex(name, r"SKU-\d+")` |
| 只校验状态码 | 原本校验业务字段，现在只 `assertEqual(status, 200)` |
| 跳过用例 | 加 `skip` / `xfail` / 注释掉用例 |
| 吞掉异常 | `try: ... except: pass`，让失败静默过去 |

### 规则

1. **不得为让用例通过而放宽断言**（`equal` 改 `contains`、删字段校验、把精确匹配改成模糊包含、跳过用例、吞异常）。确需放宽（例如后端确实只返回部分字段，且已确认这是设计如此），须**人工确认并记录理由**。
2. 实际结果与期望不一致时**先归因**（缺陷 / 版本差异 / 文档过时）。只有后两类允许"以实际为准"；**疑似缺陷必须上报**，不能把缺陷写成期望值再让用例绿。
3. 提交前跑机械核对：
   ```bash
   python3 scripts/check_assertion_strength.py --diff <base> -- <测试目录>
   ```
   脚本只报告候选、不改文件，候选需逐条复核（可能是合理的重构）。

> **脚本是线索，不是结论。** 它基于正则识别断言写法，覆盖的是常见形态（Python unittest / pytest、JS jest、JUnit / AssertJ、Go testify、chai），跨行书写的调用也会合并后再判断。未覆盖的框架或写法会**漏报**，合理的重构会被**误报**。「脚本没报」不等于「没有弱化」——事前只有规则在拦，脚本只做事后兜底。

### 什么时候必须做

- 批量实现完一轮（P4 结束）
- 修 flaky 用例时（最容易顺手改断言）
- 任何"为了让 CI 变绿"而动的断言

## 五、汇报格式（停下来问人时）

```
【停下来 · 语义不确定 / 越界】
现象：<报错原文或实际表现>
已尝试：<方法 1 → 结果；方法 2 → 结果>
我的判断：<倾向哪类原因 + 依据；若是语义不确定，说明卡在哪一句业务规则>
需要你决定：<一个具体问题，不要抛"你看怎么办">
影响范围：<阻塞哪些用例；不阻塞的照常推进>
```

**只问一个具体问题。** 把决策点收敛成"接口 A 在订单已取消时应返回 0 还是 3？"这样的句子，而不是"这块怎么处理？"。人回答一个具体问题的成本远低于回答一个开放问题——这正是本 skill 减少介入次数的关键。
