# 端到端示例（虚构项目）

一个完整的迷你走查，用来对齐各产物的形态与语气。项目是虚构的库存查询服务，只为说明格式。

## 场景

人给的目标：「把『查询 SKU 库存』这条手工用例自动化，再把另外两条一起做了。」环境：本地开发环境可用，接口文档在 `docs/api.md`。

## Phase 3：冒烟后沉淀的踩坑说明

真实跑起来时暴露了两条文档里没有的东西，它们直接进入上下文文件：

### E-001 服务启动后端口随机

- 类别：环境
- 现象：文档写 `localhost:8080`，实际启动后监听 `localhost:53127`
- 归因：本地开发模式随机分配空闲端口
- 解法：启动日志第一行打印端口，测试从日志读；不要硬编码端口
- 类型：临时 workaround
- 适用范围：本地开发环境
- 记录日期：2026-10-29
- 复核状态：待复核
- 最近复核：2026-10-29

### E-002 token 30 分钟后返回 401

- 类别：认证
- 现象：跑第二批用例时全部 401，报文 `{"code":4010,"msg":"token expired"}`
- 归因：token 有效期 30 分钟，测试没做刷新
- 解法：用例前置统一调一次登录刷新 token（`tests/conftest.py` 的 fixture）
- 类型：根因修复
- 适用范围：所有需要认证的用例
- 记录日期：2026-10-29
- 复核状态：待复核
- 最近复核：2026-10-29

E-001 是 workaround、E-002 是根因修复 —— 两者的复核优先级不同，前者腐化更快。

## Phase 4：断言强度回退的机械核对

冒烟跑通后有人为了让第二批用例过，把断言改了：

```diff
- self.assertEqual(resp.json()["data"]["qty"], 12)
+ self.assertIn("12", str(resp.json()))
```

`scripts/check_assertion_strength.py --diff HEAD -- .` 会把它标出来（以下为脚本实际输出）：

```
发现 1 处候选（需人工复核，脚本不自动修改）：

tests/test_stock.py:42 | [高] 字段断言消失
    针对具体字段的强断言被移除，且未见同主体的强断言补回
    - 移除：self.assertEqual(resp.json()["data"]["qty"], 12)
    - 断言主体：resp.json()["data"]["qty"]
```

弱化后的 `assertIn("12", str(resp.json()))` 断言的是**整个响应**，不再是 `data.qty` 这个字段 —— 主体从「字段」变成了「整体响应」，所以脚本报的是「字段断言消失」而不是「断言降级」。两者都是高优先级候选，必须由人复核后决定是否恢复。

> 附：若弱化时保留原主体（如改成 `assertIn("12", str(resp.json()["data"]["qty"]))`），分类才会是「断言降级」，并额外给出「新增」一行。
