# 提示词模板

四段可直接复制的提示词。〇 段用于探索前的缺口分析，一 段用于启动探索，二 段用于进入实现与自检，四 段是项目约定。

如果环境不可用（连不上测试环境），把探索段改成「静态探索」：读后端代码 + 读文档 + 构造契约快照，产出同样的三部分，但每条结论标注【未运行验证】。

## 〇、缺口分析阶段（Phase 0.5，探索之前）

> 先做缺口分析，不要直接写代码。把流程拆成步骤逐步推演：每一步需要什么输入？输入由谁产生（前一步 / 文档 / 人）？结果怎么验证？**没有产生者的输入就是缺口，没有验证方式的输出也是缺口**；再用维度清单补漏（清理策略、授权边界、完成定义这类不挂在具体步骤上的项）。
>
> 每个缺口按谁能补分四类：
> - **A 类（AI 可自取）**：读代码 / 读文档 / 查配置 / 跑命令，不要问我；
> - **B 类（只能人提供）**：凭证、授权范围、期望值来源、完成定义、优先级取舍——不允许假设，只能问我；
> - **C 类（只能运行时发现）**：接口实际行为、隐含调用顺序、数据真实状态——不要问我，改写成探针（"假设 X，探针：真实调用一次对比"）排进探索阶段；
> - **D 类（可假设并标注）**：写入「已采用的默认假设」，不算待确认项，不阻塞，交付时汇总给我事后确认。
>
> 所有 B 类合成**一轮**集中提问，每题带默认建议、给选项或填空。**阻塞的 B 类，解决前不得动手；非阻塞的 B 类，可先做不依赖它的部分，同时等回复。**产出缺口表（格式见 `templates/gap-analysis.md`）后再进入探索阶段。

## 一、真实探索阶段

> 先不要写自动化代码。请阅读【文档 / 用例 / API / 后端代码】，然后拿**第一个**手工用例，用 curl 或脚本逐步真实执行。每一步记录：实际请求、实际响应、与文档或代码推测不一致的地方、需要的隐含前提。
>
> **把记录写入 `exploration.md`**（请求与响应对照表、与文档的差异表、前提清单），后续所有步骤以该文件为唯一事实来源——不要凭记忆重述探索结论。
>
> 最后输出：执行方案（用例步骤拆解：前置条件 / 操作 / 断言；每条断言标明期望值来源）、运行前提清单、待确认项（不确定的地方不要自行猜测）、已采用的默认假设（低风险默认值，不算待确认项，格式见 `templates/execution-plan.md` §4b）。
>
> 本阶段不要写测试代码、不要改业务代码、不要写或删共享 / 生产数据。

**为什么强调"落文件"**：探索结论只留在对话里，写方案时会被重新想象一遍，而想象出来的前提和实测出来的前提长得几乎一样——这就是"AI 看着自己写的方案说没问题"的来源。

## 二、实现与自检阶段

> 方案已确认。请**先只实现并跑通最简单的一个用例**。运行报错时按以下顺序处理：
>
> ① 先用确定性手段判定原因（读代码、查配置、看日志、重跑）；判定不了就停下来问我。
> ② 判定得了则归因处理：
> - **环境或前提问题**：仅当修复动作可逆且不触及外部时自行修复并记录；涉及写入或删除共享库 / 生产库数据、使用他人账号或修改密码、修改流水线 / CI / 部署等全局配置、改动他人环境时**先问我**；
> - **文档过时或版本差异**：以实际行为为准并记录差异；
> - **疑似产品缺陷**：停下并上报，**不得把缺陷固化为期望值**。
> ③ 语义不确定时停下来问我。
>
> 最多重试 3 次（只对超时、网络、锁竞争这类瞬时故障重试，逻辑错误不重试），超过后汇报错误信息、已尝试方法和你的判断。
>
> **不得为让用例通过而放宽断言**（`equal` 改 `contains`、删字段校验、把精确匹配改成模糊包含、跳过用例、吞异常）。确需放宽须先经我确认并记录理由。
>
> 跑通后用原始手工用例和文档做一次**对照抽样回归**，确认断言强度未被削弱；再把遇到的问题和解法按「类别 / 现象 / 归因 / 解法 / 类型 / 适用范围 / 日期 / 复核状态」的格式整理进上下文文件。
>
> 批量实现剩余用例时，明确每个用例的幂等性与清理策略，并按完成判据逐条对账断言。

**为什么把断言规则单独加粗**：批量赶工时，为了让用例通过而放宽断言的诱惑最大，而且当场几乎看不出问题——脚本能事后检出，但事前只有规则在拦。

## 三、校验命令

```bash
# 断言强度机械核对（提交前；只报告，不改文件）
python3 scripts/check_assertion_strength.py --diff HEAD -- <测试目录>

# 上下文文件条目结构与时效核对
python3 scripts/check_context_entries.py <上下文文件> --max-age-days 30
```

两个脚本都以「发现问题则退出码 1」结束，可挂到 CI 做软门；候选需人工复核后再决定是否改。

## 四、给 AI 的一次性项目约定

每个项目开工时值得先写一遍（可直接抄进上下文文件）：

```
本项目的自动化任务按「探索 → 方案 → 冒烟 → 批量 → 沉淀」执行。
探索记录写在 exploration.md，是唯一事实来源。
失败按「确定性手段判定 → 归因 → 授权边界内处理」处理。
越界操作（写/删共享或生产数据、他人账号与密码、CI/部署全局配置、他人环境）一律先问我。
不得为让用例通过而放宽断言；放宽须先经我确认并记录理由。
测试数据必须可清理，用例应能乱序执行。
```
