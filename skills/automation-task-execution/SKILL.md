# Automation Task Execution — AI 辅助自动化任务执行协议

> **上一步**: 无（由用户请求触发）| **下一步**: 无（本 skill 交付自动化用例、执行方案与上下文文件；缺陷修复类工作交给排查 / 实现类流程承接）

## 这个技能解决什么问题

让 AI 把手工用例、接口文档或后端代码转成自动化用例时，反复出现同一类消耗：AI 一次性生成整套代码 → 第一次跑起来卡在环境问题上 → 人纠正 → 继续 → 下一个问题 → 串行的消耗战。表现为三件事：耗时预估严重失准、人反复被打断、最终"跑通了"但没人敢信。

根因不是 AI 能力不足，也不是人写得不够详细，而是**隐性知识没有显式化**：环境变量、登录态、测试数据准备、命令参数、接口调用的隐含顺序——这些信息对人是常识，对 AI 全是需要现场摸索的未知数。让人逐条写清楚既费人力，人自己也会漏掉"对自己不算问题"的细节；而 AI 只能检查它**想得到**的条件，对"不知道自己不知道"（接口实际返回字段与文档不一致、某个操作隐含前置步骤）无能为力。

所以本 skill 的方向不是"让人把流程写得更详细"，而是**让 AI 的真实失败过程去暴露隐性知识，再由 AI 自己整理成结构化文档，人只做审核**。

### 为什么 Plan（前置方案）不够

Plan 必要但不充分。真正省时间的是「**真实探索 + 冒烟跑通 + 经验沉淀**」这条链路，加上「**失败分类授权**」把人的介入次数压到只剩语义问题。

各类手段的"能治什么 / 治不了什么"对照表，以及"为什么不是让人把流程写得更详细"等设计论证，见 `references/design-rationale.md`。

## 适用判定

| 场景 | 启用方式 |
|---|---|
| 把手工用例 / 接口文档 / 后端代码转成自动化用例，环境可用 | **完整协议**（Phase 0–5，含 0.5 缺口分析） |
| 已有自动化用例的日常修补（改断言、修 flaky、补用例） | **简化**：跳过 Phase 0.5 与 Phase 1–2，直接按「失败处理」归因处置；铁律 3、4 仍然适用 |
| 环境不可用（连不上测试环境 / 无测试数据） | **降级**：缺口分析照做（C 类探针改为静态核对假设并标注【未运行验证】）；Phase 1 改为静态探索（读代码 + 读文档 + 构造契约快照），每条结论标注【未运行验证】；不得假装跑通 |
| 只有文档、没有可运行环境 | 同上；方案里显式写出"未运行验证"的条目 |
| 一次性脚本（不要求可维护、不需要断言） | 可只用 Phase 1 + Phase 3，跳过缺口分析，只把 B 类里会碰坏东西的项（授权边界、共享数据）快速确认一遍 |
| 纯调研 / 探索（不产出自动化代码） | **不适用**，直接回答即可 |

**不确定该不该用 → 用。** 误用本 skill 的成本（多写一份探索记录）远小于漏用的成本（再来一次消耗战）。

## 四条铁律

1. **先探索，后编码**：Phase 1 期间禁止写自动化测试代码。没见过真实响应就动手写断言，等于用想象当契约。
2. **探索记录必须落文件**：Phase 1 的发现写进 `exploration.md`，它是后续所有步骤的**唯一事实来源**。只留在对话里的探索结果，会在写方案时被重新想象一遍——这是"AI 看着自己写的方案说没问题"的主要来源。
3. **先归因，后动手；副作用越界必问人**：报错先按「失败处理」判定类型与授权边界，再决定是自行修复还是停下来问人。判断"缺配置 / 缺数据 / 登录过期"就动手，可能改的是共享环境。
4. **断言强度守恒**：**跑通 ≠ 正确**。不得为让用例通过而放宽断言（`equal` 改 `contains`、删字段校验、把精确匹配改成模糊包含）。确需放宽须人工确认并记录理由。

> 违反第 3、4 条比"多花两小时"危险得多：前者是把不确定的事偷偷做了，后者只是慢。

## 主流程（Phase 0–5，含 0.5）

### Phase 0：任务骨架（约 5 分钟）

人提供目标、用例来源、关键约束，**不要求写到极致详细**（人自己写也会漏掉"对自己不算问题"的细节）。AI 补齐并回读确认：

```
目标：自动化覆盖哪些用例（用例清单）
用例来源：哪个文档 / 哪次手工执行
运行前提：环境、账号、数据、依赖（未确认的先标"待确认"）
完成判据：什么样的结果算完成（可判定的一句话）+ 对照基准（原始手工用例 + 文档）
禁区：不可写的数据、不可用的账号、不可改的全局配置
```

"完成判据"必须在这一步定死。批量实现阶段最容易出的错，就是把"跑通"当成"做完了"。

### Phase 0.5：缺口分析（10–15 分钟，不依赖运行）

目标：把未知提前变成"已知的未知"并**分对流向**——该问人的一次问清，该运行探测的排进 Phase 1，该 AI 自己查的不来打扰人。人只给了粗略流程时，这一步决定 Phase 1 能否少走弯路。

每个缺口按**谁能补**分四类：

- **A 类，AI 可自取**：读代码 / 读文档 / 查配置 / 跑命令。不问人。
- **B 类，只能人提供**：凭证、授权范围、期望值来源、完成定义、优先级取舍。**不允许假设，只能问人。阻塞的 B 类，解决前不得动手；非阻塞的 B 类，可先做不依赖它的部分，同时等回复。**
- **C 类，只能运行时发现**：接口实际行为、隐含调用顺序、数据真实状态。问人没用——转成 Phase 1 的探针（"假设 X，探针：真实调用一次对比"）。
- **D 类，可假设并标注**：低风险默认值，写入「已采用的默认假设」，**不算待确认项，不阻塞**，交付时汇总给人事后确认。

做法：**数据流推演**（每步问三个问题——需要什么输入？由谁产生：前一步 / 文档 / 人？结果怎么验证？**没有产生者的输入就是缺口**，没有验证方式的输出也是缺口）→ 用模板的**维度清单补漏** → **分流成缺口表**。细则、维度检查表与产出格式一律见 `templates/gap-analysis.md`。

**衔接**：所有 B 类合成**一轮**集中提问，每题带默认建议、给选项或填空，不问"还有什么要补充的吗"（判定依据就是每题的「阻塞：是/否」）；B 类未解决项并入 Phase 2 待确认项——**待确认项仅指 B 类未解决项和 AI 无法判断的项，D 类默认假设不在此列**；C 类探针排进 Phase 1；Phase 1–3 暴露但本步没预见的坑，逐条回填模板的检查维度——清单只会越用越准。*（时间盒是经验值，先按 10–15 分钟试，按实际调整。）*

### Phase 1：真实探索（只探索，不写自动化代码）

拿**第一个**手工用例，用 curl 或脚本逐步真实执行，直到链路走通一次。逐步记录三类信息：

- **实际请求与实际响应**（原文，不要转述、不要美化）
- **与文档、代码推测不一致的地方**
- **需要的隐含前提**（环境、账号、数据、调用顺序）

产出 `exploration.md`（模板：`templates/exploration.md`），固定三部分：请求与响应对照表、与文档的差异表、前提清单。

- **停止条件**：第一个用例端到端跑通一次（返回 4xx 也算跑通——它同样暴露了真实契约），或触到一个必须由人回答的语义点。
- **本阶段禁止**：写自动化测试代码、改业务代码、写/删共享或生产数据。
- **环境不可用时**：改为静态探索（读后端代码 + 读文档 + 构造契约快照），产出同样的三部分，但每条结论标注【未运行验证】。静态探索能拿到"代码怎么写的"，拿不到"线上实际返回什么"——后者才是差异的主要来源，所以要在方案里显式留出这一风险。

### Phase 2：执行方案（Plan）

基于 `exploration.md` 产出 `execution-plan.md`（模板：`templates/execution-plan.md`）：

- 每个用例的步骤拆解：**前置条件 / 操作 / 断言**（断言要写明期望值的来源：文档 or 实际行为）
- 用到的接口或命令、参数来源
- **运行前提清单**：环境、账号、数据、依赖
- **待确认项**：AI 无法判断的地方，**禁止自行猜测**；低风险默认值放「已采用的默认假设」（Phase 0.5 D 类），不在此列
- **已采用的默认假设**：Phase 0.5 登记的 D 类默认值汇总进 `execution-plan.md` §4b，**不算待确认项**，交付时随方案汇总给人事后确认

人只审这一份方案，纠正方向性问题，成本远低于调试代码。

**必须停下来等确认的情形**：待确认项非空；断言的期望值来源是"实际行为"且疑似产品缺陷；需要写/删共享库数据；用例之间存在顺序或共享数据依赖但幂等与清理策略未定义。

### Phase 3：冒烟跑通一个最简用例

选**依赖最少、路径最短**的一个用例，端到端真实执行：真环境、真断言、真数据。

- 遇到的问题逐条解决并按「失败处理」归类，把解法沉淀成「环境与踩坑说明」。
- 本阶段结束时应拿到三样东西：一条能独立跑通的用例、一份踩坑说明、可复用的初始化 / 清理代码片段。
- **时间盒**：给第一个用例设上限（建议 60–90 分钟或 N 次重试），超时即停下复盘（多半是前提清单漏项），不要无限打转。*（60–90 分钟是经验起点，按项目实际环境调。）*

### Phase 4：批量实现剩余用例

基于已沉淀的说明复制模式，细碎问题大幅减少，剩余工作量也更容易准确估算。

- **状态隔离**：多个用例共享登录态与测试数据时，明确每个用例的幂等性与清理策略（自造数据 or 显式 cleanup），避免互相污染。共享状态的用例应当**乱序执行也能通过**——否则它测的是执行顺序，不是业务。
- **完成判据对账**：实现前先确认每个用例的断言清单，跑完逐条对账，而不是看退出码。
- **抽样回归**：方案审核不是一次性的，批量实现过程中也要抽查。首批实现完抽 20–30%，之后每新增 N 个用例抽 1 个；抽样对象优先选**断言最弱**和**依赖最浅**的用例。*（比例是经验值，按项目规模与风险调整。）*
- **断言强度守恒**在这里最容易被违反——批量赶工时，"把这条断言改松一点好让它过"的诱惑最大。提交前用 `scripts/check_assertion_strength.py --diff` 做机械核对。

### Phase 5：持续沉淀与定期复核

每次纠正后，只需一句话让 AI 把问题和解法追加进上下文文件，人不需要自己整理文字。用一段时间后，这份文件就成了"足够详细的流程说明"——而且是从真实失败过程里长出来的，不是人凭空写出来的。

- **条目格式**：类别 / 现象 / 归因 / 解法 / 类型 / 适用范围 / 记录日期 / 复核状态（模板：`templates/context-file.md`）。
- **区分「临时 workaround」与「根因修复」**：workaround 腐化得更快，复核优先级更高。
- **定期复核**：用当前代码或命令复核每条是否仍然成立（端口变了、接口下线、临时 workaround 变成长期方案）。`scripts/check_context_entries.py` 可查出字段缺失与过期未复核的条目。

### 备选路线：先录制再生成（与主流程并列，不是后续步骤）

"手工用例 → AI 转成代码"这一步本身有损。更省力的做法是由人完整做一遍并**录制 trace**（请求、响应、操作过程），AI 基于录制产物生成代码并补断言：隐性知识的采集成本更低，天然带着真实请求 / 响应样本，可直接当契约快照。是否可行取决于所用工具能否录制。主流程照常用，录制产物只是探索阶段的输入替代品。

> 录制路线的详细取舍见 `references/design-rationale.md`。

## 失败处理（细则见 `references/failure-triage.md`）

三类失败并不互斥（登录过期导致 401、而文档写 200，同时属于三类），所以**按顺序判断**：

1. 能否用确定性手段判定原因（读代码、查配置、看日志、重跑）？**不能 → 归入「语义不确定」，停下来问人。**
2. 能 → 归因：**环境或前提问题** / **文档过时或版本差异** / **疑似产品缺陷**。
3. 按归因处理，且处理动作必须落在授权边界内。

| 归因 | 处理方式 |
|---|---|
| 环境或前提问题（缺配置、缺数据、登录过期） | 可自行修复（仅限授权边界内），并记录到上下文文件 |
| 文档过时 / 版本差异 | **先归因再处理**：确属此类则以实际行为为准并记录差异；疑似产品缺陷时停下上报，**不得把缺陷固化成期望值** |
| 疑似产品缺陷 | 停下并上报，附最小复现步骤、实际 vs 期望 |
| 语义不确定（业务逻辑拿不准） | 停下来问人 |

### 授权边界

**可自行做**：读代码、查配置、看日志；起本地服务；修改测试代码与本地配置。

**必须先问**：写入或删除共享库 / 生产库的数据；使用他人账号、修改密码（可能触发账号风控）；修改流水线、CI、部署等全局配置；改动他人环境里的任何东西。

边界不清楚时默认按「必须先问」处理。

> 这条边界靠**执行者自觉**遵守，没有机制强制。涉及共享库、生产数据、CI / 部署配置的操作，应当在工具层另外加权限限制或沙箱约束，别只依赖「AI 应该知道要问」。

### 重试边界

运行报错时先自行排查修复，**最多重试 3 次**（建议起始值）。重试只对超时、网络、锁竞争这类**瞬时故障**有意义，逻辑错误重试无意义。仍失败则停下汇报，附：错误信息、已尝试的方法、自己的判断。修复后说明**改了什么、为什么改**。

### 断言强度守恒

**跑通 ≠ 正确。** 不得为让用例通过而放宽断言（`equal` 改 `contains`、删字段校验、把精确匹配改成模糊包含）；确需放宽须人工确认并记录理由。实际结果与期望不一致时先归因（缺陷 / 版本差异 / 文档过时），只有后两类允许以实际为准，缺陷必须上报。

提交前跑 `python3 scripts/check_assertion_strength.py --diff <base> -- <测试目录>` 做机械核对（只报告、不改文件；退出码 1 表示有待复核候选）。

> 脚本是**正则启发式**，输出是**线索不是结论**：它只认得它认识的断言写法，可能漏报（未覆盖的框架 / 写法）或误报（合理重构被当成退化）。所以「跑完没报」不等于「没有弱化」——该人工看的还得看；反过来，报出来的每一条都要复核，可能是合法重构。

## 上下文文件（经验沉淀的载体）

**位置**：跟随项目既有约定；无则建 `docs/automation-context.md`（或项目偏好的 `AGENTS.md` / `README_for_AI.md` 独立章节）。

**内容**：环境启动方式、测试运行命令、认证 / 登录 / 测试数据的准备方法、常见报错及对应处理方式、接口与文档不一致的已知差异、代码风格与目录约定、禁止事项。

**维护**：由 AI 在每次踩坑后自行追加（条目格式见 `templates/context-file.md`）；定期用当前代码或命令复核每条是否仍成立。

**复核辅助**：`python3 scripts/check_context_entries.py <file> [--max-age-days 30]` 报告字段缺失、类型不合规、过期未复核的条目（只报告，不改文件）。

## 时间预估

- 把任务拆成**确定性部分**（读文档、出方案、写代码）与**探索性部分**（环境调通、联调）。
- 探索性部分单独留缓冲，起步可参考 **1.5–2 倍**——这只是经验值，应以自己前几次任务的实际耗时校准。
- 设**时间盒**：第一个用例跑通最多花多长时间，超时即停下复盘。
- 第一个用例跑通后，再对剩余工作量做正式估算。

## 提交前自查表

- [ ] 探索记录是否**落成了文件**，而不是只留在对话里？
- [ ] 每个断言的期望值来源是否写明（文档 / 实际行为）？来源为"实际行为"的是否已归因确认不是缺陷？
- [ ] 待确认项是否已清零或明确留给人决策？
- [ ] 失败是否都按「确定性手段判定 → 归因 → 授权边界内处理」的顺序走过？
- [ ] 有没有为了让用例通过而放宽断言（`equal`→`contains`、删字段校验）？
- [ ] 是否跑过 `scripts/check_assertion_strength.py --diff`，且候选均已复核？
- [ ] 若改动涉及规则措辞（SKILL.md / failure-triage.md / prompt-templates.md 三处），是否跑过 `scripts/check_rule_consistency.py` 确认三处取值一致？
- [ ] 用例之间共享登录态 / 数据时，幂等与清理策略是否明确？乱序执行是否仍能通过？
- [ ] 是否按完成判据逐条对账，并做了抽样回归？
- [ ] 新踩的坑是否按结构化条目格式追加进上下文文件？
- [ ] 踩坑条目是否标注了「临时 workaround」还是「根因修复」？
- [ ] B 类缺口是否已集中提问，且阻塞项已答复后才动手？
- [ ] D 类默认假设是否已汇总交付（而不是混进待确认项）？
- [ ] Phase 1–3 暴露但缺口分析没预见的坑，是否已回填 `gap-analysis.md` 的检查维度？

## 工具与依赖

- `python3` ≥ 3.8（仅 `scripts/` 需要，stdlib only，无第三方依赖）。
- 一个可执行的测试环境 + `curl` 或等价 HTTP 客户端。
- `git`（仅 `check_assertion_strength.py --diff` 模式需要）。

三个脚本都是**只报告、不改文件**的核对工具：

| 脚本 | 作用 |
|---|---|
| `scripts/check_assertion_strength.py` | 扫描 git diff，报告断言强度回退候选（`equal`→`contains`、删字段校验、吞异常、跳过用例） |
| `scripts/check_context_entries.py` | 检查上下文文件条目的字段完整性、类型合法性与过期未复核 |
| `scripts/check_rule_consistency.py` | 核对规则措辞与取值在 SKILL.md / failure-triage.md / prompt-templates.md 三处是否一致 |
