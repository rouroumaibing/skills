# 求职辅助全流程 (jd-hunting)

辅助用户完成从简历分析到面试准备的全链路求职工作。每一步产出落盘为 Markdown 文件，便于编辑与复用。

## 触发场景

- 用户想要找工作 / 求职 / 投递简历
- 用户提供简历或工作经历，希望分析适合岗位
- 用户想按地点、政府优秀企业名单筛选公司并检索岗位
- 用户需要针对具体岗位定制简历或准备面试问答

## 前置依赖

- **检索（主路径）**：`WebSearch`、`WebFetch`、`Task`（子代理调度）—— 默认免登录、无浏览器依赖
- **简历解析**：`pdf`、`docx` skill（第一步解析 PDF/Word 简历）；不可用时按 L0 探针结果回退（见 L0 环境探针章节）
- **操作系统**：跨平台兼容（macOS/Windows/Linux），无 Chrome 依赖。L0 环境探针的命令需适配当前 OS（见探针章节跨平台适配说明）。

## 前置输入

- 用户的简历文件（PDF/Word/纯文本/Markdown）或工作经历自述（学历、项目、职责、技能，越详细越好）
- 目标办公地点（例如「某某市某某路」，用于地图范围筛选）
- 期望薪资范围（可选）
- 可接受的通勤半径（默认以开车半小时路程为准）
- 通勤方式（可选，默认驾车）：驾车/地铁/公交；影响第五步半径计算（驾车 15km / 地铁 20km / 公交 12km）
- 是否接受远程岗位（默认否；接受时远程岗位不受地点过滤约束）
- 求职状态（在职-看机会 / 离职-随时到岗，默认在职-看机会）
- 所在省市（用于第四步定位政府优秀企业名单）
- 排除公司名单（可选）：用户永不投递的公司全称列表，第三步检索后直接过滤
- 学历红线公司追加（可选）：用户认为明确卡全日制本科的公司全称或关键词列表，追加到内置学历红线名单（24 家）
- token 预算（可选）：用户自定义全流程 token 预算上限（如 100k）；留空则不设上限，仅显示累计消耗
- 海投模式（可选）：是/否，默认否；是则第八步生成 100+ 岗位海投清单
- 海投数量目标（可选）：海投清单岗位数量目标，默认 100
- 面试问答范围（可选）：默认"9+分"，可选 Top 10/15/20/全部；控制第七步 7b 面试问答生成范围

## 招聘网站登录规则

完整清单见同目录 `jb-web.md`。核心规律：
- **浏览岗位**：绝大多数网站无需登录即可查看岗位标题、薪资等基础信息
- **投递简历 / 查看联系方式 / 深度浏览**：基本都需要登录
- **国家官方平台**浏览门槛最低，信息权威

> 网站登录由用户自己完成。本 skill 仅通过 WebSearch + WebFetch 检索公开岗位信息，不替用户输入账号密码。

## L0 环境探针（第一步之前必做）

详见 [refs/env-probe.md](refs/env-probe.md)。探针结果写入 `outputs/00-index.md` 头部。

## 工作流程

### 第一步：收集简历与工作经历

- 读取用户提供的简历文件或自述文本。**按 L0 探针结果（`outputs/00-index.md` 的环境探针字段）选择解析路径，禁止直接 Read 二进制文件（必报"Binary file - content not provided"）。**

**PDF 简历兜底链**：
1. `pdf_skill: yes` → 调 `pdf` skill
2. `pdf_skill: no` + 在线 PDF URL → WebFetch 提取
3. 都不可用 → 报错，请用户提供文本版

**Word 简历兜底链**：
1. `docx_skill: yes` → 调 `docx` skill
2. `docx_skill: no` + `pandoc: yes` → `pandoc -t markdown {文件路径}` 转 Markdown
3. `docx_skill: no` + `pandoc: no` + `python_docx: yes` → 用 python-docx 提取文本
4. 都不可用 → 报错，请用户提供 PDF 或文本版

**纯文本/Markdown**：直接 Read。
- 提取关键字段：学历、工作年限、技术栈、项目经历、职责、成果、证书。
- 若信息不全，主动追问补充，尤其学历与年限。
- 画像须按固定 Schema 结构化输出，确保后续步骤数据基准一致：

```json
{
  "核心技能标签": ["Go", "Kubernetes"],
  "工作年限": 5,
  "学历": "本科/非全日制",
  "期望城市": "杭州",
  "期望薪资": "20-30k·14薪",
  "求职状态": "在职-看机会",
  "允许远程/跨城市": false,
  "项目履历摘要": [{"项目": "", "角色": "", "成果": ""}]
}
```

- **缺省容错**：所有字段允许 `null`。若 `期望薪资` 或 `期望城市` 为空，向用户发起一次交互询问补全；用户未答则取简历最近一段工作的地点/薪资作默认推论值，并在画像中标注 `来源: 推论`。`求职状态` 缺失默认 `在职-看机会`。
- 产出 `01-profile.md`：结构化的个人画像。

### 第二步：初步分析适合岗位

- 基于画像分析，给出 **5 个建议岗位**，每个附理由（匹配的能力点、行业、发展空间）。
- 岗位名称需贴近市场通用叫法，便于后续检索。
- 推荐前用 WebSearch 校验每个岗位名在主流招聘网站是否真实存在且为热门叫法，避免推荐市场没有的岗位名。
- 产出 `02-recommended-roles.md`。
- **Checkpoint**：必须等用户确认/调整岗位列表后再进入第三步，不自动续跑。

### 第三步：招聘网站检索岗位

- 按第二步推荐的岗位名称，在各招聘网站查找 **以执行当日为基准往前 1 个月** 内发布的岗位（执行时填入今日日期）。
- 识别岗位名称相近的招聘信息（如「Go 开发」「Golang 工程师」「后端开发(Go)」视为同一类）。
- **时间过滤软化**：超过 1 个月的丢弃；发布时间不明但其他条件匹配的，单列"待核实"区，不直接丢弃。
- 按用户指定的办公地点过滤；若用户接受远程，远程岗位不受地点约束。
- **数量上限**：每个网站每个岗位名抓取前 30 条。
- **数量不足扩大范围**：某岗位方向检索结果 <5 条时，提示用户「当前 1 个月范围内结果不足（{N} 条），是否扩大到 3 个月？」用户确认后扩大范围重检索，不自动扩大。

#### L1 主路径：WebSearch + WebFetch（默认）

第三步默认走 L1 主路径，不调子代理。

**WebSearch 查询模板**（每个网站独立查询，至少用 1 个变体，可组合）：
```
查询1：site:{站点域名} {岗位名} {地点}
查询2：{站点名} {岗位名} 招聘 {地点}
查询3：{岗位名} {公司名} 招聘（第四步政府名单公司）
查询4：{岗位名} {地点} 猎头 急招
查询5：{岗位名} {地点} 内推 {当前年份}
```

**WebFetch 抓取策略**：
- WebSearch 拿到列表页 URL → WebFetch 抓列表页提取岗位条目
- 每条岗位的详情页 URL → WebFetch 抓详情页**提取 JD 内容 + 验证有效性**（4 信号检查，见下）+ **提取学历要求字段**
- WebFetch 失败的条目标注"详情页抓取失败，待核实"
- **双端链接采集**：每条岗位同时采集 PC 端和手机端链接
  - PC 端：WebSearch/WebFetch 默认返回的详情页 URL
  - 手机端：站点移动版 URL（如 `m.zhipin.com`、`m.51job.com`、`m.zhaopin.com`），通过 WebSearch 搜"site:m.{站点域名} {岗位名}"或 URL 规则推断（`www.` → `m.`）
  - 两端链接可能不同，分别记录

**学历岗位级过滤**：
- 第三步 WebFetch 抓取 JD 后，新增**两个**学历字段提取：
  - `学历硬性门槛`：明确标示"最低学历：硕士"或"硕士及以上学历"等硬性要求
  - `学历优先条件`：标示"硕士优先"、"硕士加分"等非硬性偏好
- 学历值归为：博士 / 硕士 / 本科 / 大专 / 不限
- **岗位级过滤规则**：
  - 候选人学历 = 本科（非全日制）
  - `学历硬性门槛` = 硕士/博士 → 第三步直接剔除，不进入候选池
  - `学历优先条件` = 硕士/博士 → **不剔除**，保留进入候选池，第六步评分时扣分（适配度 -2 分）
  - `学历硬性门槛` = 本科 → 保留（需进一步判断是否卡全日制，由公司红线名单处理）
- **误杀控制**：仅当 JD 明确使用"最低学历""及以上学历""学历要求：硕士"等硬性措辞时判定为硬性门槛；"优先""加分""亦可"等措辞一律归为优先条件
- **与公司红线名单的关系**：公司红线名单（24 家）= 公司级过滤；岗位级学历过滤（本组）= 岗位级过滤；两层过滤互补

**岗位有效性验证（4 信号，任一命中即判"已关闭"）**：

| 信号 | 检测方式 | 判定 |
| :--- | :--- | :--- |
| 关闭关键词 | 详情页正文含"岗位已关闭"/"职位已下线"/"该职位不存在"/"职位已过期" | 已关闭 |
| 404/重定向 | WebFetch 返回 404，或最终 URL 重定向到列表页/首页（非详情页 URL） | 已关闭 |
| 内容空 | 详情页无 JD 字段（职责/要求/薪资均为空），或面经页提示"该职位已下架" | 已关闭 |
| 时间超期 | 发布时间 >1 个月且"最近更新"也 >1 个月 | 按发布主体分类处理（见下） |

**跨网站独立验证**：同一个公司在不同网站的同一岗位，每个网站的详情页都独立验证。某网站的详情页命中关闭信号，仅该网站的该条记录判"已关闭"，不影响其他网站的同一岗位。

**时间超期的发布主体分类例外**：

许多大型企业（国企、大厂校招/社招常态岗位、政府事业单位）的 JD 长期挂在官网或招聘平台上（如"长期招聘 Go 架构师"），更新时间可能停留在半年前但岗位依然有效且持续接收投递。时间超期信号按发布主体分类处理：

| 发布主体来源 | 时间超期处理 | 理由 |
| :--- | :--- | :--- |
| 三方平台（BOSS/智联/猎聘/前程） | 直接判"已关闭"，剔除 | 三方平台 JD 通常短期有效，超期多为已关闭 |
| 第四步政府/国企名单公司 | 降级为"⚠️ 存量超期岗位（待投递复核）"，**不剔除** | 政府/国企 JD 长期挂网是常态 |
| 企业官方招聘站 | 降级为"⚠️ 存量超期岗位（待投递复核）"，**不剔除** | 企业官网"长期招聘"岗位是常态 |

**降级标注的岗位处理**：写入 03 文件"待核实"区（非"已关闭"区），保留候选，第六步评分时标注"建议投递前官网复核"。

**防爬拦截处理**：详见 [refs/anti-scrape.md](refs/anti-scrape.md)

#### L1 失败判定与站点黑名单

| L1 返回条数 | 处理 |
| :--- | :--- |
| 0 条（完全没拿到） | 加黑名单（站点本身无匹配或反爬拦截） |
| 1-4 条（拿到但不足） | 保留已抓条目，标注"该站结果不足，建议用户手动补充" |
| ≥5 条 | L1 成功 |

**WebFetch 失败处理**：WebFetch 抓详情页返回 403/Captcha/验证码/登录重定向时，一律标注"待核实（反爬拦截）"，保留候选，**不触发任何浏览器回退**。仅当页面明确显示"职位已关闭/已下线"或链接 404 时才判"已关闭"。

**站点黑名单**：某站连续多次 WebSearch 返回 0 条或 WebFetch 全部失败时，将其加入本次运行黑名单（写入 `outputs/00-index.md` 黑名单区），后置步骤不再重试该站，跳过。

- 产出 `03-jobs-from-sites.md`：按网站分节汇总，含"有效岗位"区、"已关闭岗位"区、"待核实"区与"失败/黑名单站点"说明。

### 第四步：政府优秀企业名单筛选

- 按政府官网公布的优秀企业名单检索公司：
  - 专精特新中小企业
  - 专精特新「小巨人」企业
  - 高新技术企业
  - 独角兽企业
  - 瞪羚企业
  - 科技型中小企业
- 名单来源：
  - 工信部、各省/市经信委、科技局官网公示（专精特新/小巨人/高新/独角兽/瞪羚/科技型中小企业）
  - 万物生长大会榜单（杭州独角兽/准独角兽）
  - 胡润独角兽榜单
  - 雨前科技（硬科技企业榜单）
  - **取最近一年公示版**，过期名单不纳入。
- 按用户前置输入的所在省市定位名单，不全国撒网。
- 对名单中的公司，找到其 **官网招聘页**，检索是否有匹配岗位。通过 WebSearch + WebFetch 检索官网招聘页。
- **政府名单优先级筛选**：
  1. 行业过滤：专精特新小巨人 + {省市} + 软件信息技术
  2. 规模排序：按融资轮次（D轮 > C轮 > B轮）/ 社保人数（>100 优先）排序
  3. 数量限制：优先检索 Top 50 家
- **批量检索替代方案**：用 WebSearch 批量搜"专精特新 {城市} {岗位关键词} 招聘"（适用于 2167+ 家名单无法逐一检索的场景）
- 产出 `04-gov-list-companies.md`。

### 第五步：地图范围筛选公司

- 以用户指定地点（如「某某市某某路」）为圆心，按前置输入"通勤方式"确定半径：
  - 驾车（默认）：15km（约 30 分钟车程）
  - 地铁：20km（约 45 分钟地铁）
  - 公交：12km（约 40 分钟公交）
- **园区类型过滤**：第五步 L1（本地园区检索）新增前置过滤：
  - 保留类型：科技 / 软件 / 信息技术 / 互联网 / 电子通信
  - 过滤类型：智能制造 / 生物医药 / 食品加工 / 纺织服装（与运维无关的园区类型）
  - L1（本地园区）失败原因新增"园区类型不匹配" → 直接跳到 L2（半径内科技公司检索），不浪费 token 检索不匹配园区
- **地图检索 4 级降级路径**：
  1. L1（首选）：WebSearch 搜"{地点} 产业园区 入驻企业" + WebFetch 抓园区官网企业名录（**含园区类型过滤**）
  2. L2（L1 <5 家）：WebSearch 搜"{地点} 科技公司 招聘 {岗位}" 补充
  3. L3（L2 仍不足）：WebSearch 搜"{地点} {半径}km 公司" 模糊匹配
  4. L4（L3 仍不足）：半径扩大到 1.5 倍（如 15km → 22km → 33km），重跑 L1-L3
  5. L4 仍不足：标注"地图范围检索不足，建议用户手动补充"，跳过第五步
- **优先用地图网页版"驾车路线/测距"按实际通勤时间筛选（半小时内）**；地图无此能力时退化为半径近似，并在产出标注"近似半径，实际通勤以地图导航为准"。
- **实际通勤标注**：半径为直线距离近似，实际通勤以地图导航为准；推荐用高德/百度地图网页版"驾车路线"按实际通勤时间筛选（用户可手动核查）。
- **地图模糊退化机制**：

  L1（WebSearch/WebFetch）纯文本环境下无真正的地图测距 API，LLM 靠"幻觉"估计距离会导致过滤结果严重不可靠。退化策略（按精度从高到低）：
  1. **精确地址匹配**（首选）：JD 含完整地址（如"余杭区文一西路 XXX 号"）→ WebSearch 查"驾车距离 {用户地点} {JD 地址}"，返回数值 ≤ 半径则保留
  2. **地标匹配**：JD 含明确地标（如"未来科技城/海创园/阿里中心"）→ WebSearch 查"驾车距离 {用户地点} {地标}"，返回数值 ≤ 半径则保留
  3. **区级匹配**（退化）：JD 只写到区（如"余杭区/西湖区"）→ 判断该区是否在用户半径覆盖范围内 → 在覆盖范围内则保留，否则剔除
  4. **城市级标注**（最末退化）：JD 只写"杭州"无具体区域 → 保留但标注"⚠️ 需确认区域"，不参与距离判定

  **海投模式比例溢出处理**：海投 100+ 岗位中 50%-70% 可能只写城市。城市级标注岗位单独成节，不计入"已过滤"数量；08 文件头部标注"城市级岗位 N 条需用户确认区域，不参与半径过滤"。

  **禁止行为E5-1**：
  - ❌ 不可靠 LLM 幻觉估计距离——无 WebSearch 距离数据时一律降级到区级/城市级匹配
  - ❌ 不可把"无具体地址"等同于"超出半径"而剔除

  **过滤结果透明化**：记录过滤前 N 条 → 过滤后 M 条，剔除 X 条 + 区域分布统计。
- 对范围内的公司，在招聘网站、官网招聘页检索是否有匹配岗位。
- 产出 `05-nearby-companies.md`。

### 第六步：岗位信息汇总与适配度评估

对第三、四、五步收集到的候选岗位，先 **去重** 再评估：

对去重后的每个岗位，整理：

| 字段 | 说明 |
| :--- | :--- |
| 公司名称 | 全称 |
| 岗位名称 | 招聘网站原标题 |
| 岗位描述 | 职责与要求 |
| 工作地点 | 详细地址 |
| 薪资范围 | 最低–最高 |

| 胜任要点 | 该岗位需具备的能力点，用户已具备/欠缺 |

| 薪资对标 | 该岗位市场均价（优先 `WebSearch` 检索公开行业薪资报告/同岗位交叉对比；看准网登录壁垒强，仅作补充），标注 JD 薪资"高于/持平/低于市场" |

**投递链接双端四态标注**：

每条岗位必须同时标注 PC 端和手机端链接状态：
- ✅ 可直接浏览：无需登录即可查看完整 JD（含岗位职责/要求/薪资）
- ⚠️ 需登录（浏览拦截）：登录墙拦截**JD 内容**，无法查看岗位职责/要求
- ⚠️ 无直接链接：WebSearch 未返回详情页链接
- ❌ 已关闭/失效：页面显示已关闭或链接 404

**双端标注格式**：`PC: {状态} / 手机: {状态}`
- 示例：`PC: ✅可直接浏览 / 手机: ⚠️需登录`
- 示例：`PC: ❌已关闭 / 手机: ✅可直接浏览`（手机端仍可投递）
- **综合判定**：取两端中更好的状态作为该岗位的有效性判定（任一端可访问即岗位有效）

**四态语义（区分浏览拦截 vs 投递拦截）**：
- **浏览拦截**（归为 ⚠️ 需登录）：看不见 JD 内容 → 无法判断是否在招
- **投递拦截**（归为 ✅ 可直接浏览）：能看完整 JD 正文，但投递需登录 → 岗位有效

**四态判定路径（走实测，不硬编码站点结论）**：
- ❌ 不按站点名硬编码判定结论——PC 端和手机端浏览拦截程度可能不同，需分别实测
- ✅ PC 端和手机端分别走**实测路径**：WebFetch 拿到的内容里是否实际包含完整职责/要求正文字段
  - 有完整 JD 正文 → ✅ 可直接浏览
  - 仅有标题/薪资无正文 → ⚠️ 需登录（浏览拦截）
- 不同端、不同站点的浏览拦截程度需在检索时分别实测判定

**禁止编造链接**：
- 所有链接必须来自 WebSearch/WebFetch 真实返回
- 无链接时明确标注"无直接链接，需到{站点名}搜索{公司名}+{岗位名}"
- 不提供"自己去登录查找"的模糊指引

**反爬误杀防护**：
- 强反爬站点（BOSS/智联）返回 403/Captcha/验证码 → 一律归为"待核实"，**严禁直接标 ❌ 已关闭**
- 反爬拦截的岗位保留在清单中，附链接供用户手动验证
- 仅当页面明确显示"职位已关闭/已下线"或链接 404 时才标 ❌ 已关闭/失效

**链接核查产出**：
- 06 文件新增"链接核查结果"section
- 08 文件每条岗位的链接状态列
- 需登录岗位单独列出，附链接供用户手动验证

**适配度打分表**（各 0–3 分，合计 0–12）：

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
| :--- | :--- | :--- | :--- | :--- |
| 技能匹配 | 完全不沾边 | 沾边 <30% | 匹配 30–70% | 匹配 >70% |
| 年限匹配 | 差距 >2 年 | 差距 1–2 年 | 差距 ≤1 年 | 完全符合 |
| 地点匹配 | 超出可接受半径 | 远程可接受 | 半径边缘 | 半径内 |
| 薪资匹配 | 低于期望 >30% | 低于 10–30% | 低于 <10% | 达到/超过期望 |

**学历与年限放宽规则**：
- 岗位要求「全日制本科」但工作年限要求低（如 1–3 年），若用户为非全日制但经验匹配，可纳入投递范围。

产出 `06-jobs-summary.md`，按适配度评分从高到低排序，保留 top 20。

**排名表规范**：剔除岗位后**保留原排名**，不连锁重编号；新增"实际排名"列，剩余岗位按顺序重新编号（1, 2, 3...）：

**链接核查 Checkpoint**：第六步评分完成后、第七步生成简历前，强制插入链接核查 Checkpoint：
- 所有 Top N 岗位必须链接有效才能进入第七步
- 已关闭岗位在此剔除，不进入第七步
- **批次化核查**：按 Top 5 一批分批核查，避免一次性触发 20 次网络请求导致 Context 暴增
  - 每批核查完成后输出该批汇总，再启动下一批
  - 单批核查超时（5 分钟无响应）→ 自动接受当前已核查结果，未核查岗位标注"待核查"保留
- 核查完成后输出"链接核查汇总表"：公司/岗位/URL/状态（在招/已关闭/需手动/待核查）

- **链接失效回退（A3）**：WebFetch 404 / 重定向至搜索页 → WebSearch 搜 "{公司名} {岗位名} 招聘 {当前年份}" → 找到新链接后重新验证 → 未找到则标注"链接失效，需用户手动查找"
- 用户确认后方可进入第七步（超时兜底见 Checkpoint 交互模板）

1. **岗位源头已关闭/失效**：第六步链接核查 Checkpoint 发现岗位已关闭（BOSS 页面显示"职位已关闭"或链接 404）
2. **用户主动取消**：用户手动标记"不投递"某岗位

**移除的触发条件**：
- ❌ 学历不匹配（应在前置步骤拦截，不应走到文件清理阶段）
- ❌ 链接失效但能找到新链接（应更新链接而非删除文件）

**批量汇总确认**：
- 检测到多个已关闭岗位 → 汇总为"清理清单"一次性提示：

  ```
  是否批量删除以上 N 个岗位的关联文件？（回复"确认"或"保留"）
  ```

- 用户回复"保留" → 不删除，仅在 06 文件标注"岗位已关闭，简历保留待用户决定"
- **超时兜底**：5 分钟无响应 → 默认保留（避免误删），在 00-index.md 标注"清理清单待确认"

**文件清理日志**：00-index.md 新增"文件清理日志"section
- 记录：删除时间 / 文件名 / 删除原因（岗位已关闭/用户主动取消）

## 第八步：海投岗位清单生成（可选）

**触发条件**：`海投模式=是` 或用户显式要求"海投"/"100 个岗位"

**输入**：候选人画像 + 地点过滤（半小时车程半径）+ 已有 Top 20 岗位（去重基准）

**执行**：
1. 跨岗位方向批量 WebSearch（云原生/SRE/运维开发/AI Agent/架构师/Go 后端等）
2. 每个方向 2-3 次查询变体
3. 跨站点覆盖（BOSS/猎聘/智联/前程/企查查/企业官网）
4. 并行子代理检索（按岗位方向分派，套用 `prompts.md` 模板 E）
5. 去重：与 03 + 04 + 05 + 06 全部已收集岗位去重（见去重算法）
6. 地点过滤：按半小时车程半径过滤（见地图模糊退化机制）
7. 链接状态：每条标注四态（见链接明确性）
8. 产出 `08-broad-application-list.md`，按类别分节，每条含公司/岗位/薪资/地点/投递链接 + 链接状态
9. 数量目标：100+ 条

**与 Top N 的关系**：海投与 Top N 同时输出，不互斥。06 文件从第三步独立检索评分筛选，08 文件是海投全量池，两者数据源独立。

**分批次落盘与 Context 瘦身**：

海投模式跨 6+ 方向 × 2-3 查询变体 × 跨站点，实际 Token 消耗 150-250k，主对话 Context 会极速膨胀导致上下文溢出。

**分批次落盘策略**：
- 按岗位方向分批（每批 1 个方向），子代理检索完成后**立即落盘到 08 文件对应章节**，不把原始文本塞回主对话
- 子代理返回仅含 JSON 关键字段（公司/岗位/薪资/地点/链接/链接状态），**禁止返回 DOM snapshot 或 JD 原文**
- 主对话仅汇总每批数量（如"云原生方向 20 条已落盘"），不持有详细列表
- 08 文件采用追加写入模式，每批完成后追加对应章节

**Context 瘦身规则**：
- 子代理单次返回 ≤ 10 条岗位（超出截断）
- 主对话仅持有 08 文件的 INDEX-HEAD + 各方向计数，不持有岗位详情
- 续跑时读 08 文件 INDEX-HEAD 判断已完成方向，跳过已完成

**08 文件索引一致性**：
- 08 文件采用分批追加写入，顶部 INDEX-HEAD 的 `摘要` 和 `地点过滤` 统计数据在第一批次落盘时是未完全体
- **每完成一个方向的批次追加后，同步更新 08 文件顶部的 INDEX-HEAD 计数与摘要信息**（如"云原生 20 / SRE 18 / ..."逐批累加）
- 最终所有方向完成后，INDEX-HEAD 反映全量统计

**全局动态去重**：

跨 6 个方向并行检索，方向间（如"云原生"与"SRE"、"SRE"与"运维开发"）存在大量交叉重叠，仅与 Top 20 去重不够。

**全局动态去重算法**：
1. **公司名归一化**：去除"有限公司/股份/集团"等后缀，统一简称（如"阿里巴巴（中国）技术有限公司" → "阿里"）
2. **岗位名相似度**：同公司下岗位名相似度 > 80% 视为同一岗位（如"云原生运维工程师" vs "云原生运维"）
3. **去重时机**：每批子代理返回后，与以下全部已收集岗位做全局去重：
   - 08 文件已落盘岗位
   - 03 + 04 + 05 文件中已抓取但未进入 Top 20 的"陪跑"岗位
   - 06 文件 Top 20 岗位
   - **去重基准 = 03 + 04 + 05 + 06 全部已收集岗位**（不仅 Top 20）
4. **去重日志**：08 文件头部记录"去重剔除 N 条（方向间重叠 X 条 + 与 03/04/05 陪跑重复 Y 条 + 与 Top 20 重复 Z 条）"
5. **实现方式**：主对话在触发第八步前，先读取 03/04/05 的 INDEX-HEAD + 结构化表格（不读全文），构建一份"公司+岗位"去重键集合，作为子代理批次去重的输入参数

**08 与 06 文件数据流向**：
- **08 文件**：海投全量池（100+ 岗位，粗粒度，无适配度评分/背景调查）
- **06 文件**：Top 20 精致汇总（含适配度评分/背景调查/薪资对标）

### 最终链接验证（第八步后强制执行）

无论是否启用海投模式，06 汇总表 + 08 海投清单（如有）生成完成后，强制执行最终链接验证：

**验证范围**：
- 06-jobs-summary.md 的 Top 20 岗位
- 08-broad-application-list.md 的全部岗位（如存在）

**验证方式**：逐条 WebFetch 访问 PC 端和手机端投递链接，分别检查：
1. 链接可正常访问（非 404/非重定向到首页）
2. 岗位仍在开放中（页面未显示"已关闭/已下线/已过期"）
3. **双端分别记录**：PC 端和手机端可能表现不同（如 PC 端 403 但手机端可访问），分别标注状态
4. **综合判定**：任一端可访问且岗位开放 → 岗位有效；两端均不可访问 → 标注"需用户手动核查"

**批次化执行**：按 Top 5 一批分批验证，避免一次性大量网络请求
- 每批验证完成后输出该批结果汇总
- WebFetch 失败（403/Captcha）→ 标注"待核实（反爬拦截）"，不剔除
- WebFetch 确认已关闭 → 标注"❌ 已关闭"，从推荐清单中剔除

**验证产出**：
- 06/08 文件中每条岗位的链接状态列更新为最终验证结果
- 00-index.md 新增"最终链接验证"section，记录验证时间/总数/有效数/已关闭数/待核实数
- 已关闭岗位在汇总表中标灰，不进入后续简历生成

**Checkpoint**：验证完成后输出汇总，用户确认后流程结束（或进入第九步简历生成）。

## 第九步：定制简历生成（可选，用户触发）

**触发条件**：用户明确要求生成定制简历。不自动生成。

**触发方式**：
- 用户指定范围："帮我生成 Top 5 的定制简历" / "对 9+ 分的岗位生成简历"
- 用户指定岗位："帮我定制 {公司} {岗位} 的简历"
- 用户未要求 → 跳过本步，流程结束

**生成范围**：
- 用户指定 Top N → 对 Top N 岗位生成定制简历
- 用户指定 9+ 分 → 对 9+ 分岗位生成
- 用户指定具体岗位 → 仅对指定岗位生成

**产出**：`07-resume-{公司}-{部门/JobID}-{岗位}.md` 或 `07-resume-{公司}-{岗位}-{序号}.md`

**Token 预估 Checkpoint**：
- 每份定制简历约 8-12k Token
- 批量生成前输出预估，用户确认后执行

**前置检查**：
- 仅对链接验证通过的岗位生成（已关闭岗位不生成）
- 岗位 JD 内容需完整（WebFetch 已抓取或可重新抓取）

## 成功标准 (Definition of Done)

满足以下任一即视为本次流程完成：
- 用户对至少 3 个高适配度岗位确认收到面试问答 + 公司背景报告 + 投递链接；或
- 用户主动终止。

定制简历为可选交付物，不纳入完成标准强制要求。

## 执行约定

- 所有产出 Markdown 文件统一放在 `outputs/` 目录下（按上述文件名）。
- **看板更新强制化**：每步完成后**必须**更新 00-index.md 的"快速摘要"+"产出索引"+"执行状态"区，与主对话通知规范（✅/📄/📊/👉）并列执行，漏更新视为执行失败。
- **token 预估与 Context 瘦身**：详见 [refs/context-slimming.md](refs/context-slimming.md)。
- 检索统一走 WebSearch + WebFetch，不调浏览器子代理。仅第八步海投通过 `Task` 调子代理并行检索。第九步简历生成由用户显式触发。
- **子代理 prompt 套用 `prompts.md` 模板 E（仅第八步海投使用），填入变量后发起，禁止临场自由发挥。**
- **并发上限**：同时运行子代理 ≤ 3，超出排队。
- **成本提示**：七步全跑 token 消耗大；第三步**必须**先跑 1 个高优先站点（默认 BOSS直聘）试水，确认 WebSearch 查询模板有效后再扩量到其他站点。

  **试水触发范围**：
  | 场景 | 试水触发 | 理由 |
  | :--- | :--- | :--- |
  | 首次执行第三步 | ✅ 触发串行试水 | 验证查询模板有效性 |
  | 断点续跑（第三步未完成） | ❌ 不触发，直接增量跑 | 已有试水结果，无需重复 |
  | 补充检索（用户要求扩量） | ❌ 不触发，直接并发 | 用户显式要求扩量，无需再试水 |
  | 用户显式要求"全量并发检索" | ❌ 不触发，直接并发 | 用户明确放弃试水 |

  **试水验证点**：试水站点跑完后，主对话检查 WebSearch 是否拿到 ≥5 条结果 + WebFetch 详情页是否可抓。若试水失败 → 调整查询模板，不直接扩量。
- **跨平台**：产出文件路径交由 Write/Edit 工具处理（自动适配分隔符）；文案不出现 macOS 独占假设（不写「Cmd+T」，改用「新开标签页」）。
- 涉及多个独立网站的检索，并行发起子代理任务提升效率（受并发上限约束）。
- 任何需要账号密码的操作一律交还用户完成，skill 不代填凭据。
- 政府名单、地图 POI 检索用 `WebSearch` + `WebFetch`。
