# 求职辅助全流程 (jd-hunting)

辅助用户完成从简历分析到面试准备的全链路求职工作。每一步产出落盘为 Markdown 文件，便于编辑与复用。

## 触发场景

- 用户想要找工作 / 求职 / 投递简历
- 用户提供简历或工作经历，希望分析适合岗位
- 用户想按地点、政府优秀企业名单筛选公司并检索岗位
- 用户需要针对具体岗位定制简历或准备面试问答

## 前置依赖

- **检索（主路径）**：`WebSearch`、`WebFetch`、`Task`（子代理调度）—— 默认免登录、免 CDP
- **浏览器（可选增强）**：`TRAE-browseruse-external`（用户本机 Chrome，复用登录态）—— 仅在 L2 触发时需要
- **简历解析**：`pdf`、`docx` skill（第一步解析 PDF/Word 简历）；不可用时按 L0 探针结果回退（见 L0 环境探针章节）
- **操作系统**：主路径（WebSearch/WebFetch）跨平台兼容；L2 浏览器增强 macOS 和 Windows 均支持，需用户确保 Chrome 以 9222 启动。L0 环境探针的命令需适配当前 OS（见探针章节跨平台适配说明）。
- **CDP 连接约定（仅 L2 触发时）**：若用户希望启用浏览器增强，本机 Chrome 须以远程调试端口启动（统一 `--remote-debugging-port=9222`），`prompts.md` 与子代理一律通过该端口连接。连接失败即回报"Chrome 未以调试端口启动"，交用户重启 Chrome 或继续走 L1 主路径。

  **Chrome 9222 启动方式**：

  macOS：
  ```bash
  /Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome --remote-debugging-port=9222
  ```

  Windows（PowerShell）：
  ```powershell
  & "C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222
  ```
- **用户前提**：执行前需在本机 Chrome 登录目标招聘网站（仅当用户希望启用 L2 浏览器增强时需要）；L1 主路径（WebSearch + WebFetch）无需登录态。

## 前置输入

- 用户的简历文件（PDF/Word/纯文本/Markdown）或工作经历自述（学历、项目、职责、技能，越详细越好）
- 目标办公地点（例如「某某市某某路」，用于地图范围筛选）
- 期望薪资范围（可选）
- 可接受的通勤半径（默认以开车半小时路程为准）
- 通勤方式（可选，默认驾车）：驾车/地铁/公交；影响第五步半径计算（驾车 15km / 地铁 20km / 公交 12km）
- 是否接受远程岗位（默认否；接受时远程岗位不受地点过滤约束）
- 求职状态（在职-看机会 / 离职-随时到岗，默认在职-看机会）
- 所在省市（用于第四步定位政府优秀企业名单）
- 排除公司名单（可选）：用户永不投递的公司全称列表，第三步检索后直接过滤
- 学历红线公司追加（可选）：用户认为明确卡全日制本科的公司全称或关键词列表，追加到内置学历红线名单（24 家）
- token 预算（可选）：用户自定义全流程 token 预算上限（如 100k）；留空则不设上限，仅显示累计消耗

## 招聘网站登录规则

完整清单见项目根 `jb-web.md`（可选）；核心站点见下表，脱离本项目亦可用。核心规律：

- **浏览岗位**：绝大多数网站无需登录即可查看岗位标题、薪资等基础信息。
- **投递简历 / 查看联系方式 / 深度浏览**：基本都需要登录。
- **国家官方平台**（中国公共招聘网、中国国家人才网、24365、国聘网等）浏览门槛最低，信息权威。
- **企业官方招聘站**可浏览，投递需登录。

> 网站登录由用户自己完成。在用户已登录的浏览器会话中，通过 `Task` 调用 `TRAE-browseruse-external` 子代理控制浏览器检索岗位，不替用户输入账号密码。

## L0 环境探针（第一步之前必做）

用户触发 skill 后、第一步之前，主对话直接执行（不调子代理）。探针结果写入 `outputs/00-index.md` 头部。

| 探针项 | 检测方式（macOS/Linux） | Windows PowerShell 等价命令 | 00-index.md 字段 |
| :--- | :--- | :--- | :--- |
| docx skill 可用性 | LS `~/.trae-cn/skills/docx/` | 同左（LS 工具屏蔽平台差异） | `docx_skill: yes/no` |

**cookie 检查范围**：L0 探针**不检 cookie**（L1 纯 WebSearch 不涉及 cookie）。cookie 检查只在 L2 模板 A step 0 做（浏览器子代理触发时）。

## 工作流程

### 第一步：收集简历与工作经历

- 读取用户提供的简历文件或自述文本。**按 L0 探针结果（`outputs/00-index.md` 的环境探针字段）选择解析路径，禁止直接 Read 二进制文件（必报"Binary file - content not provided"）。**

**PDF 简历兜底链**：
1. `pdf_skill: yes` → 调 `pdf` skill
2. `pdf_skill: no` + 在线 PDF URL → WebFetch 提取
3. 都不可用 → 报错，请用户提供文本版

**Word 简历兜底链**：
1. `docx_skill: yes` → 调 `docx` skill
2. `docx_skill: no` + `pandoc: yes` → `pandoc -t markdown {文件路径}` 转 Markdown
3. `docx_skill: no` + `pandoc: no` + `python_docx: yes` → 用 python-docx 提取文本
4. 都不可用 → 报错，请用户提供 PDF 或文本版

**纯文本/Markdown**：直接 Read。
- 提取关键字段：学历、工作年限、技术栈、项目经历、职责、成果、证书。
- 若信息不全，主动追问补充，尤其学历与年限。
- 画像须按固定 Schema 结构化输出，确保后续步骤数据基准一致：

```json
{
  "核心技能标签": ["Go", "Kubernetes"],
  "工作年限": 5,
  "学历": "本科/非全日制",
  "期望城市": "杭州",
  "期望薪资": "20-30k·14薪",
  "求职状态": "在职-看机会",
  "允许远程/跨城市": false,
  "项目履历摘要": [{"项目": "", "角色": "", "成果": ""}]
}
```

- **缺省容错**：所有字段允许 `null`。若 `期望薪资` 或 `期望城市` 为空，向用户发起一次交互询问补全；用户未答则取简历最近一段工作的地点/薪资作默认推论值，并在画像中标注 `来源: 推论`。`求职状态` 缺失默认 `在职-看机会`。
- 产出 `01-profile.md`：结构化的个人画像。

### 第二步：初步分析适合岗位

- 基于画像分析，给出 **5 个建议岗位**，每个附理由（匹配的能力点、行业、发展空间）。
- 岗位名称需贴近市场通用叫法，便于后续检索。
- 推荐前用 WebSearch 校验每个岗位名在主流招聘网站是否真实存在且为热门叫法，避免推荐市场没有的岗位名。
- 产出 `02-recommended-roles.md`。
- **Checkpoint**：必须等用户确认/调整岗位列表后再进入第三步，不自动续跑。

### 第三步：招聘网站检索岗位

- 按第二步推荐的岗位名称，在各招聘网站查找 **以执行当日为基准往前 3 个月** 内发布的岗位（执行时填入今日日期）。
- 识别岗位名称相近的招聘信息（如「Go 开发」「Golang 工程师」「后端开发(Go)」视为同一类）。
- **时间过滤软化**：超过 3 个月的丢弃；发布时间不明但其他条件匹配的，单列"待核实"区，不直接丢弃。
- 按用户指定的办公地点过滤；若用户接受远程，远程岗位不受地点约束。
- **数量上限**：每个网站每个岗位名抓取前 30 条。

#### L1 主路径：WebSearch + WebFetch（默认）

第三步默认走 L1 主路径，不调子代理。

**WebSearch 查询模板**（每个网站独立查询，至少用 1 个变体，可组合）：
```
查询1：site:{站点域名} {岗位名} {地点}
查询2：{站点名} {岗位名} 招聘 {地点}
查询3：{岗位名} {公司名} 招聘（第四步政府名单公司）
查询4：{岗位名} {地点} 猎头 急招
查询5：{岗位名} {地点} 内推 {当前年份}
```

**WebFetch 抓取策略**：
- WebSearch 拿到列表页 URL → WebFetch 抓列表页提取岗位条目
- 每条岗位的详情页 URL → WebFetch 抓详情页**提取 JD 内容 + 验证有效性**（4 信号检查，见下）+ **提取学历要求字段**（阶段 4 新增）
- WebFetch 失败的条目标注"详情页抓取失败，待核实"

**学历岗位级过滤（阶段 4 新增，C9）**：
- 第三步 WebFetch 抓取 JD 后，新增**两个**学历字段提取：
  - `学历硬性门槛`：明确标示"最低学历：硕士"或"硕士及以上学历"等硬性要求
  - `学历优先条件`：标示"硕士优先"、"硕士加分"等非硬性偏好
- 学历值归为：博士 / 硕士 / 本科 / 大专 / 不限
- **岗位级过滤规则**：
  - 候选人学历 = 本科（非全日制）
  - `学历硬性门槛` = 硕士/博士 → 第三步直接剔除，不进入候选池
  - `学历优先条件` = 硕士/博士 → **不剔除**，保留进入候选池，第六步评分时扣分（适配度 -2 分）
  - `学历硬性门槛` = 本科 → 保留（需进一步判断是否卡全日制，由公司红线名单处理）
- **误杀控制**：仅当 JD 明确使用"最低学历""及以上学历""学历要求：硕士"等硬性措辞时判定为硬性门槛；"优先""加分""亦可"等措辞一律归为优先条件
- **与公司红线名单的关系**：公司红线名单（24 家，阶段2）= 公司级过滤；岗位级学历过滤（本组）= 岗位级过滤；两层过滤互补

**岗位有效性验证（4 信号，任一命中即判"已关闭"）**：

| 信号 | 检测方式 | 判定 |
| :--- | :--- | :--- |
| 关闭关键词 | 详情页正文含"岗位已关闭"/"职位已下线"/"该职位不存在"/"职位已过期" | 已关闭 |
| 404/重定向 | WebFetch 返回 404，或最终 URL 重定向到列表页/首页（非详情页 URL） | 已关闭 |
| 内容空 | 详情页无 JD 字段（职责/要求/薪资均为空），或面经页提示"该职位已下架" | 已关闭 |
| 时间超期 | 发布时间 >3 个月且"最近更新"也 >3 个月 | 按发布主体分类处理（见下） |

**跨网站独立验证**：同一个公司在不同网站的同一岗位，每个网站的详情页都独立验证。某网站的详情页命中关闭信号，仅该网站的该条记录判"已关闭"，不影响其他网站的同一岗位。

**时间超期的发布主体分类例外**：

许多大型企业（国企、大厂校招/社招常态岗位、政府事业单位）的 JD 长期挂在官网或招聘平台上（如"长期招聘 Go 架构师"），更新时间可能停留在半年前但岗位依然有效且持续接收投递。时间超期信号按发布主体分类处理：

| 发布主体来源 | 时间超期处理 | 理由 |
| :--- | :--- | :--- |
| 三方平台（BOSS/智联/猎聘/前程） | 直接判"已关闭"，剔除 | 三方平台 JD 通常短期有效，超期多为已关闭 |
| 第四步政府/国企名单公司 | 降级为"⚠️ 存量超期岗位（待投递复核）"，**不剔除** | 政府/国企 JD 长期挂网是常态 |
| 企业官方招聘站 | 降级为"⚠️ 存量超期岗位（待投递复核）"，**不剔除** | 企业官网"长期招聘"岗位是常态 |

**降级标注的岗位处理**：写入 03 文件"待核实"区（非"已关闭"区），保留候选，第六步评分时标注"建议投递前官网复核"。

**WebFetch 防爬红线**：

招聘平台（BOSS 直聘、智联招聘等）有严格反爬机制，WebFetch 详情页大概率遇到 403 Forbidden、验证码或 JS 渲染阻塞。

| 情况 | 处理 |
| :--- | :--- |
| WebFetch 返回 403 / Captcha / JS 渲染阻塞 | 直接视为失败，标注"待核实（反爬拦截）" |
| 单站点连续 2 次 WebFetch 失败 | 该站 WebFetch 阶段终止，仅保留 WebSearch 摘要 |
| 严禁 | 频繁重试 WebFetch 导致 IP 被封 |

**强反爬站点默认策略**：

| 站点 | WebSearch 能拿到 | WebFetch 详情页 | 默认策略 |
| :--- | :--- | :--- | :--- |
| BOSS 直聘 | 索引页摘要（公司/岗位/薪资） | 大概率 403/Captcha | WebSearch 摘要为主，详情页标"待核实（强反爬，建议 L2 或手动）" |
| 智联招聘 | 索引页摘要 | 可能失败 | WebSearch 摘要为主，WebFetch 失败标"待核实" |
| 猎聘 | 索引页摘要 | 可能失败 | 同上 |
| 国家队平台 | 完整信息 | 通常可抓 | WebFetch 正常抓取 |
| 企业官方招聘站 | 完整信息 | 通常可抓 | WebFetch 正常抓取 |

**防爬红线与有效性验证的协同**：

| WebFetch 结果 | 处理 |
| :--- | :--- |
| 成功 + 含关闭关键词 | 已关闭，剔除 |
| 成功 + 404/重定向 | 已关闭，剔除 |
| 成功 + 内容空 | 已关闭，剔除 |
| 成功 + 时间超期（三方平台） | 已关闭，剔除 |
| 成功 + 时间超期（政府/国企/企业官网） | ⚠️ 存量超期岗位，保留候选 |
| 成功 + JD 内容正常 | 有效，保留 |
| 403/Captcha（防爬） | 标"待核实"，**保留候选（不能判断是否关闭）** |
| 超时/网络错误 | 标"待核实"，**保留候选（不能判断是否关闭）** |

**关键原则**：防爬拦截/网络错误**不能**判定为"已关闭"——岗位可能仍然有效，只是抓不到。只有明确关闭信号才能剔除。

#### L1 失败判定（区分 0 条 vs 不足 5 条 + 登录壁垒检测）

| L1 返回条数 | 登录壁垒检测 | 处理 |
| :--- | :--- | :--- |
| 0 条（完全没拿到） | 未检测到登录重定向/登录拦截 | 按阶段 1 处理：加黑名单，**不触发 L2**（站点本身无匹配） |
| 0 条（完全没拿到） | 检测到明确的登录重定向/登录壁垒 | **优先触发 L2**（若 `chrome_cdp: yes`）；`chrome_cdp: no` 时加黑名单 |
| 1-4 条（拿到但不足） | - | 触发 L2 增强（若 `chrome_cdp: yes`）；`chrome_cdp: no` 则标注"浏览器增强未启用" |
| ≥5 条 | - | L1 成功，不触发 L2 |

**0 条登录壁垒检测方式**：WebSearch 返回 0 条时，主对话 WebFetch 该站列表页 URL，检查是否重定向到登录页（URL 含 login/passport/sso）或返回登录弹窗 HTML。

**逻辑环修正说明**：阶段 1 规定"0 条直接加黑名单，不触发 L2"。阶段 2 修正为"0 条 + 登录壁垒 → 优先触发 L2"——避免登录壁垒导致的 0 条被误判为"站点无匹配"。

#### L1 登录壁垒分级标注

WebSearch 拿到的列表页 URL 若重定向到登录页（URL 含 login/passport/sso），或 WebFetch 详情页返回登录重定向：

| 情况 | 处理 |
| :--- | :--- |
| WebSearch 拿到摘要（公司/岗位/薪资）但详情页需登录 | 保留摘要，详情页标"待核实（需登录）"，触发 L2（若 chrome_cdp=yes） |

| L2 触发后登录态也丢失 | Fast-Fail，标"登录态丢失"，转 WebSearch 摘要兜底 |

## L1.5 浏览器子代理路径（browser_use，阶段 4 新增）

在 L1（WebSearch/WebFetch）和 L2（TRAE-browseruse-external + Chrome CDP 9222）之间，新增 L1.5 路径：`browser_use` 子代理 + 反检测注入。

**触发条件**（全部满足）：
1. L1 失败：WebFetch 返回 403/Captcha/需登录/空内容
2. `chrome_cdp: no`（L2 不可用）
3. 用户同意使用 browser_use 子代理浏览器

**stateless 特性声明**：
- browser_use 子代理每次调用独立，浏览器实例随子代理返回关闭
- 不可跨调用复用会话/登录态
- 子代理返回 = 任务结束 = 浏览器关闭

**禁止行为**：
- ❌ 不可用 `browser_wait_for` 等待用户操作（子代理无法暂停等待用户）
- ❌ 不可假设前一次子代理的登录态在新调用中可用

**推荐模式**：
- ✅ 单子代理串行处理所有链接，一次调用完成全部核查
- ✅ 子代理内部完成反检测注入 → 串行访问所有链接 → 一次性返回全部结果

**已知限制**：
- 需反检测注入（见下）
- 无法复用登录态（全新浏览器实例）
- BOSS 直聘等站点可能随反爬升级再次拦截
- 不适合投递操作（无登录态）

### 反检测注入技巧

```javascript
// 反检测注入（add_init_script 注册，导航前生效）
Object.defineProperty(navigator, 'webdriver', {get: () => undefined});
Object.defineProperty(navigator, 'plugins', {get: () => [1,2,3,4,5]});
Object.defineProperty(navigator, 'languages', {get: () => ['zh-CN','zh','en']});
window.chrome = {runtime: {}};
```

- **BOSS 直聘反爬机制**：前端 JS 检测 `navigator.webdriver === true` → 重定向至 `verify.html` 安全验证页
- **适用范围**：BOSS 直聘已验证有效；其他站点（猎聘/智联）待验证
- **时效性**：此技巧可能随站点反爬升级失效，需定期验证
- **注入机制（Page-Level 预注入）**：
  - ❌ 不可仅用 `browser_evaluate` 单次注入——跨域跳转/新页面加载时 `window` 作用域会被清空，`navigator.webdriver` 恢复默认值 `true`，导致关键跳转节点失效
  - ✅ 必须使用 `add_init_script`（Playwright）或 `evaluateOnNewDocument`（Puppeteer）实现 **Page-Level 预注入**：所有页面加载及 iframe 创建的第一时间自动注入，确保跨域跳转后反检测仍有效
  - 注入时机：在子代理启动浏览器后、第一次 `browser_navigate` 之前注册 `add_init_script`，此后所有导航自动生效

### 断点续跑

- 每个 outputs 文件即为该步的完成标记。续跑时先 LS `outputs/`，按编号判断进度。
- **续跑读取规则**：续跑时主对话用 Read 读每个 outputs 文件**前 10 行**（INDEX-HEAD），不读全文，节省 token。仅当需要续跑某步时才读全文。
- **INDEX-HEAD 鲁棒性匹配**（不要求严格 HTML 注释格式）：LLM 写入时格式可能有微小偏差（换行、空格、引号差异）。续跑读取时采用宽松匹配：
  - 前 10 行内出现 `INDEX-HEAD` 字符串即识别
  - 匹配 `step:` 或 `步骤:` 后的非空文本
  - 匹配 `状态:` 后的非空文本（完成/进行中/失败/待跳）
  - 匹配 `摘要:` 后的非空文本
  - 匹配 `黑名单:` 后的文本（可为空）
- **降级策略**：若前 10 行无法匹配到 `INDEX-HEAD` 标识，回退到读取文件标题（第一个 `#` 开头行）+ 前 30 行正文判断进度。
- 已存在的文件：默认询问用户「覆盖 / 跳过 / 续跑」；用户未明确则跳过该步。
- Checkpoint 点（必须等用户确认才前进）：第二步后（岗位列表）、第六步后（汇总表确认进入定制）。
- 续跑时优先读 `outputs/00-index.md` 看板的"当前阶段"和"黑名单"区，再读各 outputs 文件索引头。

**续跑恢复逻辑**（阶段 3 状态机）：

续跑时主对话读 00-index.md 执行状态区：
- 步骤状态 = "完成" → 跳过
- 步骤状态 = "进行中" + 子状态含"子代理执行中" → 重新调子代理（**增量跑**，见下）
- 步骤状态 = "进行中" + 子状态含"未落盘数据" → 从未落盘点重跑
- 步骤状态 = "中断" → 从该步开头重跑
- 步骤状态 = "待执行" → 正常执行
- 步骤状态 = "跳过" → 跳过（尊重用户上次选择，不重跑）

**子代理增量跑（断点续跑去重）**：

主对话重新调子代理时，读取 03 文件（或对应产出文件）中**已落盘/已完成的站点/公司列表**，作为 `exclude_sites` 或 `processed_items` 参数传入子代理。子代理跳过已完成站点，仅跑未完成站点。

```
续跑调子代理流程：
  ① 主对话读 03-jobs-from-sites.md 的 INDEX-HEAD + 已落盘站点列表
  ② 提取已完成站点（如 BOSS/智联已完成）
  ③ 调子代理时传入 exclude_sites=["BOSS", "智联"]
  ④ 子代理仅跑未完成站点（如猎聘/前程）

```

**幂等性保证**：子代理对同一站点的检索结果以"站点+公司+岗位"为主键去重，避免重复写入。

| 工作年限差距 >2 年 | ❌ 学历不匹配（建议跳过） |
