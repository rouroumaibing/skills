# Context 瘦身与 Token 预估 — jd-hunting

> 本文件是 `SKILL.md` 的 token 管理参考。

## token 预估强制化

- ✅ 每步开始前必须输出 token 预估（理想/实际两档）
- ✅ 每步完成后必须更新 00-index.md 的 token 消耗表（预估 vs 实际对比）
- ✅ 累计消耗达到预算 80% 时主动提示用户

## 断点续跑 Token 累加规则

- 续跑时读取 00-index.md 现有 Token 统计值作为**基数**
- 新产生消耗采取增量累加：`旧消耗 + 新 Session 消耗 = 最终实际消耗`
- ❌ 不可清零覆盖（丢失历史消耗导致预算监控失真）
- ❌ 不可重复叠加（同一步骤中断前后不重复计算）
- **步骤级去重**：续跑时已标记"完成"的步骤不重新累计 Token；仅"中断"/"进行中"步骤的新增消耗累加
- **预算预警连续性**：80% 预警基于累计实际消耗，不因续跑重置

## 每步 token 预估规范

每步开始前主对话输出：

```
📊 第 {N} 步 token 预估
- 预估消耗：{X}k token（基于 {依据}）
- 预估耗时：{Y} 分钟
- 累计消耗：{Z}k token {/ 预算 {W}k token}
{若用户设定预算且超 80%} ⚠️ 剩余预算不足，建议跳过低优先步骤
```

## 超时提示

单步实际耗时超预估 2 倍时，主对话提示"⚠️ 第 {N} 步耗时超预期（预估 {Y} 分钟，已用 {Z} 分钟），是否继续或跳过？"

## 预算提示逻辑

- 用户设定预算 → 累计消耗达 80% 时提示"剩余预算不足，建议跳过低优先步骤"
- 用户未设定（默认）→ 每步显示累计消耗，不提示超预算
- 任何情况都不强制中断

## 主对话 Context 瘦身约定

预估表和看板只是事中/事后统计。如果用户不设 token 预算上限，随着第三/四/五步跑完，主对话 Context 仍会积累数万 token，导致第六步（汇总评分）和第七步（定制简历）推理变慢、费用暴增或超出模型最大上下文。

**主对话 Context 瘦身规则**：

| 步骤 | Context 读取约束 | 理由 |
| :--- | :--- | :--- |
| 第六步前 | **禁止重新 Read 前几步产生的原始抓取文件全文**，只能通过 `03-jobs-from-sites.md` 等文件的 INDEX-HEAD 摘要 + 结构化表格完成评分 | 原始抓取文件含完整 JD，单文件可达数千 token |
| 第六步 | 仅对"待核实"岗位和 Top 10 候选岗位按需 WebFetch 完整 JD | 按需读取，不批量预载 |
| 第七步 | 仅对用户指定批次的岗位 WebFetch 完整 JD | 每批 5 份，不超载 |
| 续跑时 | 读 00-index.md 看板 + 各 outputs 文件 INDEX-HEAD（前 10 行），不读全文 | 节省 token |

**强制约束**：主对话进入第六步前，若检测到 Context 已含第三/四/五步的原始抓取文件全文（非 INDEX-HEAD），应提示"检测到上下文含原始抓取文件，建议跳过 Read 全文，仅读 INDEX-HEAD 摘要"。
