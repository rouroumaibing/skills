# 聊天模式轻量审计清单（无仓库 / 无 CI / 无工程实装）

> 适用场景：被审对象贴在会话里（diff 截图、代码片段、文档、报告摘要），没有可执行的
> 仓库、CI 或治理配置。这是**最常见的审计形态**，也是能力上限最低的形态——本清单的
> 作用是把有限输入用到最有效的核对顺序上，并如实标注天花板。

## 天花板（先对自己说，再写进报告）

- 无法运行任何检查器 → 所有结论都是**人工核对**，报告须标注"无工程实装，全项人工核对"。
- 无法验证证据 → 证据只做了"形式核对"（有没有、自洽不自洽），不是"真实性核验"。
- 无法核对完整范围 → 只能审**给定片段**，报告须写明"审计范围 = 提供的材料，
  仓库其余部分未审"。
- 禁止措辞：报告里不得出现"门禁通过 / 全部绿 / 已验证 / 已实装"。

## 核对顺序（按信息收益排序，逐项在报告中标 ✅/⚠️/❌/未审）

1. **契约与判据先行**：有没有明确的目标、范围、不可触碰项、验收判据？
   没有 → 这本身就是第一条修改建议（无契约审计 = 无基准比较），并提议用
   `goal-contract.md` 模板起草（作为建议，不代写锁定版）。
2. **范围与红线**：给定改动是否越出声称的范围？是否触及明显受控对象
   （认证/支付/迁移/密钥/公共接口）？比对 `risk_floor_check` 的判定条件做
   **人工推算风险下限**，与声明等级对照（E-17 的人工版）。
3. **证据链**：结论有没有证据？证据有没有来源（谁产出、何时）？AI 自报的
   "测试都过了 / lint 干净"一律按无证据处理（E-11）。
4. **红绿顺序**：声称 TDD 的，看能否从材料中分辨测试先于实现；不能分辨 →
   标注"无法核验红绿顺序"而不是默认通过。
5. **对抗推演**：对每条修改建议，按 `attack-cases.md` 案例库问一遍
   "被治理的 AI 会怎么绕过这条建议"；建议附【对抗推演】【建议可信度】两字段
   （可信度只有"已验证模式 / 纯推测"两档，判据见 attack-cases.md 分级表）。
6. **升级与转人**：命中 `escalation.md` 任何触发条件 → 停下按升级格式输出，
   不推断继续。高风险材料在聊天模式下**只能转人**，不存在"独立验证 Agent"
   （本会话不是干净上下文）。

## 报告交付与归档

- 报告按 SKILL.md 模板输出；被审项目有仓库 → 归档到 `<项目>/audits/`；
  无仓库 → 在会话内交付并**主动询问**使用者要保存到哪（不代选位置、不写盘）。
- 报告末尾固定附一节「工程化建议」：列出若该项目建立最小工程骨架
  （契约只读 + AI 可写区分离 + 范围检查 + 契约锁定哈希，见 `framework.md`
  最小可行集）后，本报告哪些人工核对项可以升级为机器检查——这是聊天模式
  审计最有长期价值的输出。
