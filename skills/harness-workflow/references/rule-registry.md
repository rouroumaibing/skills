# 模板二：规则登记表（Rule Registry）

**用途**：全项目一份，登记**本包可取证的审计判据**（产物级 + CI 门禁级）与
**AI 行为规范**（软规则）。治理建设要求（强制设施怎么建：合入账号、预授权、
放行绑定、凭据隔离等）**不在此登记**——审计者只能核"有没有证据"，不能规定
组织怎么治理；这类内容作为设计要点归入 `attack-cases.md`「治理机制设计要点」，
在审计报告中以修改建议的形态出现。

> **定位（设计建议属性 + 采纳边界）**：本表是消费项目自建强制设施时的
> **规则判据建议**——"建议等级 = 硬 / 拦截点 = 服务端"等列描述的是建议项目
> 建成后的形态，采纳哪些、如何实现由消费项目自行决策；本审计 skill 只按
> `audit/scripts/` 检查器可机检的产物级字段出具报告与修改建议，**不实施、
> 不托管任何拦截机制**。
>
> **采纳边界**：只有消费项目在 `governance/redlines.yaml` 的 `required_rules`
> 里列出的规则，才是该项目的**审计判据**；未列出的规则不构成缺口，只以修改
> 建议出现。`required_rules` 未设或为空时，审计运行于**建议模式**（报告为
> 建议清单并明示"非合规判定"，退出码 0）。
>
> 已采纳但未实装的规则按"未实装"如实降级（退出码 42，fail-closed），
> 不得当作已强制。

**本表写作规范**（入库条目的写作要求，不是对消费项目的强制门槛）：

1. **描述为可判定的一句概括**（不含无判定标准的形容词）；具体判定细节放入「判定方式」列。禁用词表：`适当、尽量、等等、大概、合理、关键、重要、必要时`；描述须可被判定为真或假。
2. 有明确的判定方式（命令退出码 / 文件检查 / 脚本比对 / AI 复核 / 人判断）。
3. 有明确的执行者（固定工程 / AI / 人）。
4. 建议等级列填 `硬` / `软`，仅描述建议形态；建议等级为"硬"的条目标注拦截点（`服务端` / `客户端` / `混合`，定义见下）。
5. 实装状态**不在本表维护**（防止两处漂移）：机器权威是项目自建的 `governance/rule-map.yaml`（可选，属服务端配套、不在本包内），实时结论以 `.workflow/probe-results.json` / 平台 attestation 为准。`script_pass` 不得单独作为"已实装"依据；自动推进（E-18）只认 `probe_pass`。
6. **建议"硬"规则的拦截机制为服务端强制**（见下方「拦截点」列与「实装探针」说明）：本地 hook / 本地文件系统权限可被绕过，**不得单独作为"已实装"依据**。

> **单一事实源声明**：本文件是"规则语义"的人读权威；**机器可读的权威源是 `governance/redlines.yaml`**（含 `required_rules`、`protected_paths`、`review_required_paths`、`ai_writable_paths`、`risk_patterns`、`thresholds`、`forbidden_words`）。本 MD 表格为该 YAML 的人读镜像，不得与 YAML 数值矛盾；YAML 为准。禁止在第三处再抄写这些列表（维护纪律见本文末尾「单一事实源纪律」）。

**存放位置**：随审计 skill 发布（`references/rule-registry.md`）；消费项目落地时置于 `references/` 下（或并入 `governance/`），对 AI 只读，改动需人批准。其他文档只引用规则 ID，不复制规则内容。

**拦截点取值（与写作规范 6 对应）**：
- `服务端` = pre-receive hook、合入必需 CI 检查、分支保护、CODEOWNERS，AI 无法用 `--no-verify`、不安装或同用户绕过。
- `客户端` = 本地 pre-commit hook、本地文件系统权限，可被绕过，**只能作本地快速反馈，不得单独作为"已实装"依据**。
- `混合` = 服务端为主、客户端辅助。
- 软规则填 `不适用（软）`。

### 实装探针（防"声称硬规则却没实现" + 防 AI 伪造）

> 本模板只定义判据，不预设实装结论：规则的拦截机制与实装状态由项目自建映射维护。项目落地脚本 / hook / CI 后，由 CI / 人运行探针并把结果写入 `.workflow/probe-results.json` 或 CI attestation（消费侧约定见 `schemas.md` §6），再更新项目自建 `rule-map.yaml`（如有）中对应规则的实装状态。
>
> **执行主体（关键）**：被治理的 AI（含本 harness 自身）**不运行、也不重新生成探针**，更**不自行验签或比对平台指纹**——它无平台权限、够不到仓库外的验证公钥。探针由 CI 运行、签名，或由平台原生 check-run / attestation 产出；harness 只读取 CI 已签署的"逐规则结论"并转述，不得声称自己验过。

按拦截机制类型分别定义探针：

- **脚本 / hook 类**（如 `audit/scripts/check_contract.py`、`governance/hooks/pre-commit-scope`）：
  - 存在且可执行：`test -x <path>`。
  - `--self-test` 通过，且**必须带反例夹具**：夹具提供"已知违规输入"，脚本必须**拒绝**它；仅证明"脚本能跑、返回退出码 0"不算通过。夹具目录本身也在 `protected_paths` 内，AI 不能改夹具凑过。
  - 例：`audit/scripts/check_contract.py --self-test`（内部含"含禁用词的契约样本"应被拒、"越界范围样本"应被拒等断言）。
- **CI / 服务端类**（如 `coverage-gate`、`mutation-gate`、`type-check`、`dep-secret-scan`、`test-not-weakened`、`pre-receive`、分支保护）：
  - **查该检查已作为"合入必需检查"（required status check）且启用**（branch protection / required check 中存在、状态为 required 且当前通过），而不是"最近一次通过"或"脚本文件存在"。`make lint --dry-run` 只证明命令存在，不证明 lint 有效。
  - **CI 必须从可信引用运行治理脚本**：必需检查必须使用**组织级 required workflow / ruleset**；治理脚本**从目标分支（base）取，不从 PR 分支取**。若 CI 检出 PR 分支后运行 `governance/scripts/*` 或 `audit/scripts/*`，或 workflow 文件取自 PR 分支，AI 改一个脚本就能让检查永远通过——因此脚本来源必须钉死到目标分支（见 `schemas.md` §6）。
- **权限 / 分支保护类**（如服务端仓库权限，设计要点 R-SEC-001、R-REL-001/004，见 `references/attack-cases.md`「治理机制设计要点」）：
  - 查**仓库权限 / 分支保护策略存在且生效**（AI 对受保护路径无写权限由**服务端仓库权限**保证，而非本地文件系统权限；本地 fs 权限在同用户场景下不成立）；合入账号≠AI 身份、分支保护启用。
- **拦截点标注为"客户端"的规则**（本地 hook、本地 fs 权限）：探针仅验证其存在，**但因其可被绕过，不得单独计入"已实装通过"**；必须另有同规则的"服务端"拦截已作为合入必需检查，该规则才算真正实装。

> **禁用词适用范围（本表为权威定义）**：R-GOAL-001 的禁用词表（适当、尽量、等等、大概、合理、关键、重要、必要时）**仅约束契约中与客观判定直接相关的字段**（成功判据、边界情况、范围表），目的是让这些字段可被客观判定；检查由 `governance/redlines.yaml` 的 `forbidden_words` 控制，**契约不得用开关关闭**。本登记表、framework 篇、SKILL 自身的说明性文字不受该规则约束。

## 红线配置（`governance/redlines.yaml`，AI 只读）

七类列表（`required_rules` / `protected_paths` / `review_required_paths` / `ai_writable_paths` / `risk_patterns` / `thresholds` / `forbidden_words`）的**机器权威是实体文件 `governance/redlines.yaml`**（起步模板见本 skill `audit/templates/redlines.starter.yaml`：四类产物级判据；protected_paths 等服务端配套三类由项目按需增设）。本文件不再内嵌副本，杜绝"第三处复制"导致的漂移；消费项目应把该文件复制到自己仓库根的 `governance/` 并按基线覆写阈值。

`required_rules` 即**采纳边界**：项目声明哪些登记规则对它生效，审计就按哪些规则出具合规结论；未列出的规则只以修改建议出现。`required_rules` 的逐条映射与实装状态由消费项目自建台账维护（可选，如 `governance/rule-map.yaml`）；映射校验与文档一致性检查由消费项目按需实现（设计要点见 `references/attack-cases.md`「治理机制设计要点」，退出码约定 0/1/42 与本包各检查器一致）。

## 枚举与纪律

- **枚举映射**：`risk_level` 取值 `low | medium | high`，对应契约表格"低 / 中 / 高"；`status` 取值 `draft | locked | changed | closed`，由 `state.json` 派生；`judge` 字段填"固定工程"或"人"（中文），与英文枚举分开。
- **单一事实源纪律**：`required_rules` / `protected_paths` / `review_required_paths` / `ai_writable_paths` / `risk_patterns` / `thresholds` / `forbidden_words` 七类列表的**唯一权威在 `governance/redlines.yaml`**；本 MD 表格与 SKILL.md 中的同主题列表均为镜像，出现矛盾以 YAML 为准；禁止在第三处再抄写。
- **规则生命周期由消费项目自建**：软规则何时升级、哪些规则定期复核、零触发规则是否删除——这些是治理决策，不是审计职责；消费项目可参照 `references/attack-cases.md`「治理机制设计要点」自建流程，本表不做规定。
