# 推荐落地计划规格（Landing Plan）——把审计报告的建议翻译成施工顺序

审计报告回答"缺什么、为什么、证据在哪"；落地计划回答"先做什么、怎么算做完、哪里要人拍板"。
两者的视角不同：报告是审计视角（证据、对抗推演、可信度分级），计划是施工视角（顺序、动作、验收）。
建设期体检在报告通过后按本规格另出一份落地计划，作为独立文件与报告同目录归档。

## 一、为什么需要它（要解决的真实症状）

一份有 10~11 条建议的审计报告交给使用者时，如果只说"采纳与否由人决策"，使用者面对的是
一张平铺的清单，必须自己回答三个他不该回答的问题：

1. **先做哪个**——建议按 P0/P1/P2 成熟度排，但成熟度不是施工顺序。照 P0→P1→P2 施工，
   会先做"证据协议/升级策略"这类需要平台设施配合的项，卡在没有地基的地方。
2. **怎么算做完**——建议写"加验证门""建 verify 资产"，没有可执行的验收动作，做完与否靠自述。
3. **哪些要我拍板**——如果把"三类性质不同的改动（纯仓库内 / 需决策 / 需组织配合）"整个
   抛给使用者选，他无法判断，因为分类语言是审计者的、不是使用者的。

落地计划消除这三个问题：给出**唯一推荐顺序**、每批**可执行的验收 gate**、需拍板项
**单列并附推荐值与默认动作**。使用者只需要说"按计划走"或指出哪一批要改。

## 二、定位与边界

- 落地计划**仍是建议**：它推荐顺序与验收方式，不实施、不替人决定采纳与否。报告里
  "非合规判定、采纳由人决策"的口径同样适用于计划。
- 落地计划**不改变报告结论**：先出报告、后出计划；计划失败不回头改报告证据。
- **不是所有审计都要出计划**。产物级审计（审一个 diff / 契约 / 证据包）的结论是合规
  判定，没有"施工顺序"问题；只有建设期体系体检（"验证体系缺什么 / 报告怎么落地"）才走本规格。

## 三、核心纪律：成熟度阶段 ≠ 施工顺序

这是最容易踩的坑，必须先讲清：

- 蓝图的 **P0 / P1 / P2 是成熟度归属**（这个维度建设到什么程度），用于报告的建议标题
  标注与阶段一致性机检（见 `verification-program.md` §3 权威表）。
- 落地计划的**批次是按依赖排的执行顺序**（先做什么才不卡住），与 P0/P1/P2 是两套坐标。
  一个 P0 建议可能排在第三批（如升级策略 E-05 要等验证门有消费者），一个 P1 建议
  可能排在第一批（如 verify 资产是所有后续机制的地基）。

计划里**不得**把"P0/P1/P2"当成"第一批/第二批/第三批"的别名。批次用"第一批/第二批"
编号，成熟度阶段只在"吸收建议"列里作为建议本身的标注出现。

## 四、五层依赖顺序（批次划分的依据）

按依赖从下往上，承重墙是第 1 层的 verify 循环——它对应文章那句
"Verification means running the change"，是整套效果的地基。没有它，上面各层的门
拦的都是空转。

| 层 | 名称 | 为什么在这一层 | 典型建议维度 |
| --- | --- | --- | --- |
| 0 | 静态地基 | 便宜、可逆、先清障，让后续门有干净的起点 | CI 格式/lint 门、修存量格式问题、修失实注释与死链 |
| 1 | verify 循环（承重墙） | 定义"done 长什么样 + **真跑一次完整用户流 + 落外部证据**"，是上面所有机制的消费者前提。这里只写声明式 `verify.yaml`、验收 gate 只到"build 绿 / 字段齐"不算过关——声明不是运行，后面的门会拦在空转上 | 声明式 verify 资产（build/start/done + hands + feature map rubric）**+ 一次真实运行的端到端结果（外部可查的日志/截图/响应）作验收 gate** |
| 2 | 复制到其余对象 | 一个模板做透再横向铺开，避免三个仓库各写一套；复制的门槛同样是"真跑过一遍"，不是抄一份 yaml | 其余仓库的 verify 资产 + 各自真跑一次 E2E 冒烟、属性测试 |
| 3 | 独立判卷 | 有了可跑的验证，才谈得上"谁来判、怎么防自欺" | REVIEW 判卷清单、五条独立性机制、从 diff 读 trigger |
| 4 | 平台设施（先 observe） | 需要 harness/组织配合，直接 enforce 会误拦；先观察再收口 | 验证戳 + 三档门 + 拦截谓词、branch protection、golden set eval、漏检回流 |

层数不是批次数：一个批次可以覆盖一层的全部建议，也可以把一层的地基与其余对象拆成
两批（先做一个当模板、再复制）。批次划分见下节模板。

## 五、落地计划文件模板

固定章节，便于机检解析与使用者阅读。文件名 `<报告基名>.landing-plan.md`，与报告同目录。

```markdown
# <项目名> 推荐落地计划

> 配套报告：<审计报告文件名>
> 口径：本计划为建议，按依赖排序；采纳与否由人决策。

## 一句话结论

<当前地基停在哪一层；第一批做什么；为什么先做它。一到两句，使用者读完就知道从哪下手。>

## 批次总览

| 批次 | 目标 | 吸收建议 | 前置 | 验收 gate | 需拍板 |
| --- | --- | --- | --- | --- | --- |
| 第一批：<动词短语> | <这批解决什么> | 建议 1/2 | 无 | <可执行的命令 + 期望输出> | 无 |
| 第二批：<动词短语> | ... | 建议 3/4 | 第一批 | ... | 见"需拍板项"① |

## 各批次明细

### 第一批：<与总览一致的名称>

- **做什么**：<具体动作，落到文件/命令/配置，不用抽象词>
- **吸收建议**：建议 N（原文标题）、建议 M（原文标题）
- **验收 gate**：
  - `<命令>` → 期望 <退出码 0 / 具体输出 / 文件产物>
- **完成定义**：<看到上述 gate 全过即算本批完成，不靠自述>

### 第二批：...

## 需拍板项（单列）

<每项给推荐值与默认动作，使用者不逐项选也能推进；这里不放"三类改动选哪类"这种问题。>

| 编号 | 决策点 | 推荐值 | 理由 | 默认动作 |
| --- | --- | --- | --- | --- |
| ① | <要人决定的具体事> | <推荐选项> | <一句理由> | 按推荐值执行；要改请指出 |

## 当前不适用（不进批次）

| 建议 | 不适用理由 |
| --- | --- |
| 建议 N | <条件不满足，如纯后端无前端界面 / 无可并行旧实现> |
```

### 模板字段约束（机检据此判定）

- **批次总览**必须是 markdown 表，列头依次为：批次 / 目标 / 吸收建议 / 前置 / 验收 gate / 需拍板。
- 每个批次在"各批次明细"有同名二级标题（`### 第一批：...`），且总览与明细一一对应。
- "吸收建议"栏引用建议编号（`建议 N`，多个用 `/` 分隔）；报告里每条建议必须出现在
  某批次的吸收栏或"当前不适用"表里，不能沉默漏带。
- 每批的"验收 gate"栏与明细的"验收 gate"段都非空，且含可执行的命令或可观察的输出
  （反引号命令、退出码、文件路径）；写"验证通过"这类不可核的话不算。
- **承重墙批次（verify 循环那一批）的 gate 必须含"真跑系统"的证据**：命令要驱动
  真实系统跑完整用户流（浏览器驱动 / API harness / 端到端场景），并落外部可查产物
  （响应体、截图、带时间戳的日志），不能只写"`build` rc=0""manifest 三字段齐"这类
  静态声明——声明齐 ≠ 跑通过，用静态项冒充真跑会让上面所有门拦在空转上。
- **需拍板项只圈"必须人定的具体值"**：阈值、容差、首版人确认、何时转 enforce 这类。
  它不表示"整批不做"——仓库内能落的执行骨架（驱动入口、证据落点、比对脚本）照常
  进批次，只需把待定值标成参数；把整批推给"组织配合/pending"会让承重墙塌掉。
- "需拍板"栏写"无"或"见需拍板项①"这类引用；每个需拍板项必须有**推荐值**与**默认动作**，
  不允许只有选项没有推荐。
- 正文只写现状：不出现"新增/改为/原来是/v1/v2/本版"等版本叙述，不出现"已在正文带出"
  这类不可核自证断言。

## 六、使用者导向的语言纪律

面向的不是审计者，是要动手的人。三条：

1. **批次名用动词短语**（"跑通地基门"、"做一个仓的 verify 模板"、"铺开到另两仓"），
   不用维度编号（"D4/D8 阶段"）当名称。
2. **不抛分类选择题**。不说"三类改动请选一类"，直接给推荐顺序；真正要人决定的，
   收进"需拍板项"并附推荐值。审计者内部的分类（仓库内/需决策/需组织配合）可以写进
   理由，但不能作为让使用者回答的问题。
3. **验收写成人能跑的动作**：命令 + 期望输出，而不是"门生效""验证完成"这类结论词。

## 七、一个填满的样例片段

以一份"修 CI 注释 + 加格式门 → verify 资产 → 复制到余仓"的体检为例：

```markdown
## 一句话结论

地基停在"静态门可用"层：CI 有 vet/build/test 但 AS-IS 注释失实、无格式门。
第一批先修注释漂移并把格式门接进 CI（便宜可逆），随后第二批做一个仓的 verify
循环当模板——它是后面所有门的消费者前提。

## 批次总览

| 批次 | 目标 | 吸收建议 | 前置 | 验收 gate | 需拍板 |
| --- | --- | --- | --- | --- | --- |
| 第一批：修注释与接格式门 | 让 CI 说真话、门能拦住 | 建议 1/10 | 无 | `pnpm lint` rc=0；`git diff --exit-code` 干净 | 无 |
| 第二批：做一个仓的 verify 模板 | 定义 done 并真跑一次完整用户流 | 建议 4/5 | 第一批 | `<verify start>` 起服务；hands 驱动真实用户流（浏览器/API harness）跑通并落截图+响应+带时间戳日志到 `evidence/`，退出码 0 | 无 |
| 第三批：铺开到另两仓 | 复用模板，不各写一套 | 建议 4/9 | 第二批 | 两仓各跑一次 verify done 全绿 | 无 |
| 第四批：判卷与平台设施 | 防自欺、先 observe | 建议 7/8/6 | 第三批 | REVIEW.md 存在；门 observe 模式运行一周无误拦 | 见① |

## 需拍板项（单列）

| 编号 | 决策点 | 推荐值 | 理由 | 默认动作 |
| --- | --- | --- | --- | --- |
| ① | 验证戳门何时从 observe 转 enforce | 观察满一周且误拦为零再转 | 直接 enforce 会拦住未接钩子的历史提交 | 按推荐值；要提前转请指出 |
```
