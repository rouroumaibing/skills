# 验证体系蓝图（Verification Program）——「项目验证体系」的诊断判据与建设规格

> **定位（建议素材，非强制）**：本文件是被审对象「项目验证体系」（AI 交付链路的
> 验证实装形态）的诊断维度表与建设蓝图。产出的报告内容一律是**修改建议**
> （缺口 + 证据 + 建议改动 + 由谁决策）；判据层可机检的部分已登记为
> R-VER-008 / R-VER-009（登记表），其余维度按人工核对出具建议。
> **本 skill 不施工**：本蓝图给出 AI 可照做的资产规格（§4），实施由执行方
> AI / 工程按建议清单进行；落地后的资产（verify manifest、CI 门、判卷规则）
> 即成为后续审计的判据输入。
> 知识来源：Claude Code 团队验证实践（claude.dev blog, 2026-11）+ 通用 Agent
> 落地转译；对抗视角的设计约束见 `attack-cases.md`「验证体系设计要点 VP-01~09」。

## §0 为什么验证体系是一等审计对象

三个已实证的事实，构成验证体系建设的经济学依据：

| 事实 | 含义 |
| --- | --- |
| 独立 grader 按 rubric 判卷，任务成功率最高 +10 分（最难任务收益最大） | 判卷人与做题人分离是最便宜的提分手段 |
| 测试/基准/E2E 一经生成就以软件形态反复运行，边际成本趋近于零 | 验证从人力成本变成**固定资产**：先把验证器做扎实，而不是多写几遍代码 |
| 可靠性清单 39 项，每次 diff 只命中 3~10 项 | 规则要挂在「可从 diff 判定的触发器」上，不做全量人肉背诵 |

对审计的直接含义：**AI 自述"测试通过"不构成证据**——退出码、日志、截图由
harness（agent 之外的执行环境）收集，agent 只能引用不能转述；每条判卷规则
与评审结果绑定具体 commit，推新提交即作废。

## §1 三种值得投资的测试（选择依据）

| 类型 | 本质 | 为什么对 Agent 交付特别有效 | 适用条件 |
| --- | --- | --- | --- |
| E2E | 真实用户流整条跑通（有明确 done 判据） | **难以欺骗**：要么整个功能工作要么不工作；可给 agent 手和眼（浏览器驱动 / 模拟器 / API harness）直接操作真实系统 | 有可启动的真实系统；.feature map 可当评分 rubric |
| 属性测试 | 声明"不可能失败"的约束，用生成器造上千输入证伪 | 边界输入**不来自与被测代码同源 bias 的 mind**（独立生成器），专治 agent 系统性盲区 | 存在可表述的 round-trip / 不变量 / 幂等 / 等价约束 |
| 差分测试 | 旧系统当 oracle，同输入比对新旧输出 | 迁移 / 重写场景的守门员；spec 漂移时旧系统仍是可靠基准 | 存在可并行运行的旧实现 |

前置警告（三者共同）：

- **flaky 测试会把 agent 训练成"重跑而不是修复"**（机检判据 R-VER-009 / 升级 E-05）；
- **慢测试会降低验证频次**，agent 每轮改完该跑的门不跑了；
- **重的测试放在提交边界跑**，本地与 agent 内环只跑便宜的门（cheap-first，见 §3）。

> --survey` 探测并输出 JSON；其余为人工核对（报告如实标注）。

## §3 建设优先级（cheap-first，从零到成熟）

> 实施顺序的经济逻辑：先把**便宜且高频**的门做扎实（agent 每轮都跑），
> 再上**贵而难以欺骗**的门（提交边界跑）。每阶段的验收判据列在右侧——
> 落地后由本 skill 的检查器 / survey 复核。
>
> **阶段归属权威表**（建议标题的 P0/P1/P2 按此标注，机检判据见 §6）：
>
> | 阶段 | 对应 D 维度 |
> | --- | --- |
> | P0 | D1 静态门、D7 证据协议、D10 升级策略 |
> | P1 | D4 verify 资产（含 §4.10 视觉判据）、D8 验证戳、D9 判卷独立性 |
> | P2 | D3 属性测试、D5 差分测试、D11 flaky 铁腕、D12 漏检回流、元验证 |
>
> 三处纪律，缺一处报告就会"阶段自相矛盾"（实测：某报告摘要称"P0 基本成型"，
> 却把 D7/D10 两项 P0 判 ❌；又把 D4 verify 资产标成 P0、把 P0 的 D10 塞进 P2 建议）：
>
> 1. **摘要阶段判定与 D 表一致**：说"PX 成型/达标"时该阶段 D 维度须全部达标；
>    任一 ❌ 只能说"部分成型"并点名缺项，不得笼统说该阶段成型。
> 2. **建议标题阶段与所修 D 维度一致**：一条建议横跨多阶段，在【缺口】行显式
>    写"主阶段=PX，附带 Y 属 PZ"并拆成多条建议各自标注——把 P0 的 D10 埋进
>    P2 建议，会让升级策略在 P0 阶段缺席。
> 3. **证据引用与判定信号的检查器一致**：D11 须引用 `static_risk_check.py`
>    实跑输出；D8 须引用 `verification_gate_check.py`；不得拿相邻扫描的
>    "0 命中"冒名（见 §6 机检）。

| 阶段 | 做什么 | 验收判据 |
| --- | --- | --- |
| P0（当天可做） | D1 静态门 + D10 升级策略（连续失败阈值默认 3）+ D7 证据协议（结论必须带退出码/日志，由 harness 收集、agent 只能引用不能转述；"本地先跑"用**agent 无关的本地强制点**：改动交给下游前自动跑 test/build/lint 并留痕——git `pre-commit` hook 是通用做法；各 agent 生态的完成时事件（如 Claude 的 Stop hook / `/goal`）属**可选加速器**，写进报告时只作示例、不作为能力判据） | agent 不再自述"完成"；E-05 生效 |
| P1 | D4 verify 资产 + E2E 冒烟 + D8 验证戳（含 none）+ D9 判卷独立性 + 新门先 observe（VP-05） | "未验证"变成可查询状态（R-VER-008 可机检） |
| P2 | D3 属性测试 + D5 差分测试（如有迁移）+ D11 flaky 铁腕治理 + D12 漏检→规则闭环 + 元验证（VP-07） | 同一个坑只踩一次 |
| 成熟态 | 人从"读每个 diff"退到"定义 done + 抽查证据" | 验证体系自身被治理（§4.8） |

## §4 落地资产规格（AI 可施工模板）

> 以下规格是修改建议的「建议改动」栏可直接引用的目标形态。施工方（执行方
> AI / 工程）按规格落地后，资产列入 `protected_paths` 或 `review_required_paths`
> （变更须人审），成为下一轮审计的判据。

### 4.1 verify 资产（声明式 manifest）

一个仓库内约定位置的可执行验证说明：**怎么 build、怎么起、done 长什么样**。
放哪里不重要（常见的有 agent 技能目录下的 verify 入口、`verify/` 目录、
`verify.yaml`、构建工具里名为 verify 的 target），重要的是三个字段齐全、
agent 在提交前知道要跑它、**harness 本身被压测到 rock solid**（它是全部
下游验证的地基）：

```yaml
# verify manifest 最小 schema（schema_version 演进规则同 schemas.md 总则）
schema_version: 1
build: "<一条命令，产出可运行产物>"
start: "<一条命令，后台拉起真实系统，含就绪判定方式>"
done:                 # done 判据必须是机器可判定的，不接受"看起来正常"
  - command: "<一条命令，退出码 0 = 通过>"
    evidence: "<证据落点：日志/截图/JSON 报告的路径>"
hands:                # 可选：给 agent 的"手和眼"（怎么驱动真实系统）
  driver: "<浏览器驱动 / API harness / 模拟器入口>"
timeout_s: 600        # 超时 = fail，不重试
```

### 4.2 验证戳协议（R-VER-008 的判据形态）

commit message 末尾的固定 trailer，**`none` 是合法取值**（查得出未验证提交
是特性，不是违规；只有"没盖戳"才违规）：

```
Verified: <e2e|unit|property|differential|manual|none>
Evidence: <证据路径或 CI job 链接，none 时可省略>
```

- 由提交工具链 / hook 自动盖戳优先；agent 手动盖戳时报告标注"自报"。
- 白名单之外的 method 取值视为**无效戳**（按未盖戳计，防伪造）。
- 查询口径：`git log --grep` 按 trailer 过滤，覆盖率 = 带有效戳的 commit 数 /
  回看窗口内 commit 总数（窗口与下限阈值配置在 `redlines.yaml` 的
  `thresholds.verification_stamp`，见 starter 注释）。

### 4.3 判卷规则（REVIEW 清单）与判卷独立性

- 规则条目三要素：**触发器（可从 diff 判定）× 检查内容 × 背后事故/PR 链接**。
  每次评审只核对触发器命中的条目（对照清单 39 项命中 3~10 项的实测）。
- 独立性三原则（防"考生改判卷规则"）：
  1. 判卷规则文件从 **base 分支**读取，PR 内的修改不影响本次审判；
  2. 评审结果**绑定 commit**：评审期间推新提交，评审作废；
  3. 拉人来看时必须说得出 **why**（触发的是哪条规则、什么证据），不让人
     从 diff 里倒推。
- 检查由 code owner 自己写并迭代到"owner 会拦的它也拦"。
- **单一 reviewer、多轮累积**：不靠堆叠第二个更贵的 reviewer 提升评审质量
  （原文：增加第二 reviewer 往往不如调优主 reviewer），而是把注意力放在
  调优 REVIEW.md 上；评审/验证分多轮时，每轮把**前轮上下文与历史失败**喂
  进去，而不是从头重查一遍——更便宜且发现更多。这是 REVIEW 机制的运行
  形态，报告在 §4.3 覆盖行须能指出"是否只做单轮 / 是否堆叠 reviewer"。

### 4.4 属性测试骨架

四类通用属性模式（各语言选一个属性测试库即可，如 JS/TS、Python、Rust、
JVM 生态都有成熟候选）：

| 模式 | 陈述模板 |
| --- | --- |
| Round-trip | 若 `decode(encode(x)) == x` 对生成器产出的任意 x 成立 |
| 不变量 | 若某约束（如"余额非负"）对任意合法操作序列成立 |
| 幂等 | 若 `f(f(x)) == f(x)`（迁移 / 归一化 / 重试类操作） |
| 等价 | 若优化实现与朴素正确实现对任意输入产出一致 |

要点：**输入由属性库生成器产生**（与被测代码的作者 bias 解耦）；agent 提交
属性陈述、人审一次后固化；spec 与实现漂移时属性测试仍可用（约束比 spec 稳）。

### 4.5 门禁灰度（off → observe → enforce）+ 拦截谓词

新门上线**三档**，防误报卡死流程后被人关掉；报告须点明当前处于哪一档
（原文是 off / observe / enforce 三档，只写 observe→enforce 会漏掉"先完全
关闭、确认开关本身无害"这一档）：

0. **off**：门不启用、不记录、不拦截，用于上线前确认不会误伤构建；
1. **observe**：只记录"本会被拦的提交"，不拦；观察误报，确认无误伤再进下一档；
2. **enforce**：拦截；commit message 里可附豁免理由；**同一会话内被拦两次后
   下一次放行**（防 agent 死循环卡死——门要硬，但要有逃生门）。

**拦截谓词（拦什么，须与三档一起写）**：档位只决定"拦到之后怎么处理"，
还必须定义"门拦哪些提交"。原文的门拦的是**该次提交所在会话内没有执行过
约定的验证动作**（原文用 `/code-review` 或 `/verify` 举例；落地时由消费项目
定义具体命令，不要写死某个 slash command）。要点：

- 谓词看的是**会话内事实**（有没有跑过验证动作），不是 commit message 上
  的戳——戳（§4.2）是结果标记（含 `none`，可查询未验证提交），谓词是门禁
  用来判定拦不拦的依据。原文是两套机制并用：给每个 commit 盖验证戳 +
  用会话内是否验证过来拦提交；只写戳不写谓词，AI 施工时知道怎么标记却
  不知道门该拦谁。
- 报告建议正文须点明**当前门拦什么**（哪个验证动作、以什么会话内事实判定），
  并讲清谓词与验证戳如何配合；只写"off→observe→enforce 三档"而不定义
  谓词，等于给了开关却没接电线。

### 4.6 flaky 治理协议（R-VER-009 的规则形态）

- 禁止：sleep 凑等待（改显式条件等待）、重跑到绿（rerun/retry 装饰器）、
  skip 绕过（已由 R-IMP-004 覆盖）；
- 修不好根因 → **删除该测试并写下删除理由**（记录在案，供漏检回流评估）；
- 升级线：同一门禁连续失败达阈值（E-05）即停止重试转人——agent 不得在
  "重跑碰运气"上停留。

### 4.7 漏检 → 规则的准入门槛

原文给出**两套**并行方法，任一命中都可产出 REVIEW.md 规则候选，报告不得
只带第一套：

**第一套：从评审意见/revert 提炼模式**

真实漏检（事故 / revert / 人审捞到的 bug）转化为规则前必须过三道门槛，
缺一道就退化成规则垃圾场：

1. **准入**：同类问题 ≥2 个 PR 出现，且可从 diff 识别（单次事故不成规则）；
2. **对抗**：≥3 个独立 agent 会话尝试证伪该规则（规则本身也会过拟合）；
3. **人审合入**：规则进判卷清单须人批准（与 R-PRC-004 登记表改动审批同构）。

**第二套：bug finder 回放已知事故**

对**已知关联事故**的 PR，用 3 个 bug finder 回放：**≥2 个命中**才算"这个
bug 可检测"；若它在**小 diff 上也被漏掉**，就是值得转成 REVIEW.md 规则的
缺口。与第一套的差别：第一套从"人已经发现的模式"归纳，第二套从"机器能否
复现发现"反向验证探测能力——小 diff 漏检是重点信号。

### 4.8 元验证（review the reviewers）

验证器自己也是软件，需要被验证：

- **持续度量（review the reviewers 的体检指标）**：除一次性评测外，定期统计
  **merged 后被 revert 的数量**、**maintainer 在合入前拒绝的数量**，以及一组
  **体量相当且一直干净的变更**做对照——这是判断验证器是否正在漏检 / 过度
  拦截的长期体温计；报告须能指出项目有没有这类持续统计，只有一次性 golden
  set 不算齐。
- **golden set**：用真实事故 / revert 复现当时的仓库状态，每例带一句话答案；
  另取体量相当的干净变更做对照组（防过度拦截）。**评分口径：只有正确描述
  该 bug 的发现才得分**（原文：each example's one-sentence answer key，只给
  正确描述 bug 的 finding 计分）——否则"随便报一条就算命中"会让 recall 虚高，
  报告须能指出评测是否按此口径计分；
- **分阶段 recall**：原始发现 → 验证后 → 终审分别统计（看系统有没有把已经
  找到的 bug 弄丢；合并成一个端到端分数看不见这个）；
- **发现分级**（原文实证）：除了"是不是真 bug"，还要标注**重要度**——
  `Important`（must-fix）/ `Nit` / `Pre-existing`（问题早于本次变更，不该让
  作者背责）。否则一堆 nit 会淹没真正该拦的发现。这是 §4.8 覆盖行
  `Important/Nit/Pre-existing` 的依据。
- **数据集隔离**：调参集（tuning set）从固定评测集（fixed test set）中**分离**，
  评价系统只用固定集；否则"调参即过拟合"无法察觉。
- **调参边界**：调到"再调就是过拟合评测集"的边缘即停；
- **修剪**：判卷清单、验证步骤、文档只增不减会拖慢每次验证——列入例行维护。

### 4.9 差分测试落地规格（D5 的建设规格）

适用前提：存在**可并行运行的旧实现**（迁移 / 重写 / 协议 / 存储引擎替换）。
没有旧系统可对照时本节不适用——报告按"当前不适用"标注并写明理由，
**不算缺口、也不允许沉默缺项**（见 §6）。

- **oracle 与采样**：旧系统当基准（oracle）；输入用**随机生成或生产流量采样**
  （脱敏后），不用人工挑选的"典型输入"——实现方 agent 的 bias 会集中在它
  想过的用例上，恰恰漏掉它会犯错的边界。
- **对拍协议**：同一输入分别打到新旧系统，逐字段比对响应；迁移场景下旧系统
  在 spec 漂移后仍是可靠基准（生产行为 > 文档）。
- **归一化**：比对前先剥离无关差异（时间戳、请求 id、空白、字段顺序、浮点
  尾数），否则噪音淹没真差异；归一化规则本身要人审一次后固化。
- **允许变更白名单**：新旧环境理应不同的字段（新系统多出的字段、版本号、
  排序稳定性）显式列出并逐条注明理由；白名单文件进 `protected_paths`——
  AI 不能悄悄往里加字段让差异"合法消失"（RT-17 同型：变更不能修改审判
  自己的标准）。
- **收敛判据**：白名单外差异 = 0 且持续若干采样窗口（窗口数写入 redlines
  阈值），才允许切换流量 / 下线旧系统；期间旧系统保持只读可回放。

### 4.10 视觉验证与异常流程规格（前端交互项目的 E2E 落地形态）

适用前提：被审对象有**前端交互界面**（浏览器 UI / 桌面客户端 / 移动端）。
纯 API / CLI 项目本节不适用——报告按"当前不适用"标注并写明理由，**不算缺口
也不允许沉默**（与 §4.9 同纪律）。这是 E2E「给 agent 手和眼」在界面项目上的
具体形态：原文 FIG A 的关键对比是单测只报 `Timeout`，而 E2E 给出一张截图
加"哪里坏了"的描述——**截图不是装饰，是 done 判据的一等证据**。

蓝图 §4.1 的 `hands.driver` 与 `evidence` 字段在界面项目必须落到下面三件
可施工的规格，否则执行方 AI 只会得到占位符、落地必然漂：

**① 基线管理（baseline）**

- 基线截图是判卷标准的一部分，列入 `protected_paths`：变更须人审；
  **禁止 AI 把基线改成"当前实际渲染"让差异合法消失**（RT-18，同 §4.9
  白名单的判卷独立性逻辑）。
- 每张基线须记录：对应场景 id、视口尺寸、浏览器/驱动与版本、**稳定时刻的
  定义**（如"网络空闲 + 动画结束 + 关键元素可见"时截取，避免截到过渡态
  导致假阴性）、以及基线文件 sha256。
- 基线首版由人确认，不由 agent 当次截图直接转正。

**② 比对协议（diff）**

- done 判据不是"截图存在"，而是**比对结果机器可判定**：报告须含
  `baseline_sha256`、`actual_sha256`、`diff_metric`（像素差比例 / 感知阈值）
  与容差阈值（抗锯齿、字体渲染、动效帧等已知无关差异），字段名与
  `schemas.md` §3 的 `screenshot` item 保持一致，执行方不必自行发明字段。
- 容差与阈值由人审一次后固化进 redlines / verify manifest；超阈值 = fail，
  不接受"看起来差不多"，也不重试碰运气（§4.6）。
- 漂移处置分岔必须写清：**代码回归 → 修代码**；**有意的 UI 变更 → 人审后
  更新基线**，且同一变更附新旧对比与理由。禁止把更新基线当成修测试的捷径。
- 截图按 `schemas.md` §3 的 `screenshot` 一等证据类型写入证据包（带 sha256、
  基线引用、场景 id、比对指标），由 harness 收集；agent 自述"界面正常"
  不算证据。

**③ 异常态驱动清单（feature map 的可执行形态）**

- 验收场景清单（§4.1 的 feature map rubric）在界面项目必须显式覆盖
  **异常流程**，不只是 happy path：网络失败、空数据、超时、权限不足、
  表单校验错误、确认弹窗 / 抽屉的 open→confirm→close 各态、加载 / 错误 /
  空状态之间切换。
- 每个场景写明四件事：怎么触发（`hands.driver` 的浏览器 / API 动作）、
  截哪个状态点、断言什么（可见文本 / 元素 / URL / 状态码）、对应哪个
  基线 id——**截图 ↔ 用例一一映射**，否则截图无法判卷。
- 超时 = fail 不重试（`timeout_s`，§4.1）；异常态的"预期报错"是 done，
  不是测试失败——判据要在场景里写明，避免 agent 把正确报错当 bug 修掉。

### 4.11 Agent 调用适配层（平台无关的"完成事件"替代）

适用前提：有 agent（不止人）在改代码、且验证必须发生在"改动交给下游前"。
纯人工仓库本节不适用——报告按"当前不适用"标注并写明理由。

原文章用"完成事件"（某生态的 Stop hook / `/goal` / 专属 skill）在 agent 收尾时
自动跑 cheap checks，并留下"本会话已验证"的会话事实供 §4.5 拦截谓词读取。
这些事件是**平台专有的触发器，不是能力本身**；把"有没有某个专有命令 / 某生态
skill 目录"写成能力判据，会把"没接该生态钩子"误判成"没有验证能力"——这违反
平台无关纪律。能力本体是三件与 agent 生态无关的事：

① **可调用入口**（§4.1 已有）：仓库内一个声明式 verify 资产 + 一条 shell 可
   调用的入口（`verify.yaml` + `scripts/verify*`）。任何能执行命令的 agent 都能
   调用它，不依赖任何生态的钩子注册或 skill 加载。

② **会话事实**（§4.5 已有）：一个与 agent 无关的状态存储，记录"本会话是否跑过
   验证"（如状态文件 + git：`start-session` / `mark-verified` / `check`）。拦截
   谓词读这个事实，不读 agent 的自述"已完成"。

③ **触发绑定（本节新增的适配重点）**：把"何时调 ①、何时写 ②"绑到 **agent
   无关的生命周期**上——git 提交边界（`pre-commit` 本地钩子做快速反馈，可被
   `--no-verify` 绕过、只作本地反馈；服务端 `pre-receive` / CI required check
   才是真强制，见 RT-12）与 CI 作业。这一步与 agent 用哪个工具无关：任何 agent
   提交代码都会经过 git / CI。仓库还应放一份**平台中立的 agent 指令文件**（约定
   链：`AGENTS.md` → `CLAUDE.md` / `.cursor/rules` / `.github/copilot-instructions.md`），
   用命令式写明"改完代码 → 调 ① → 成功后写 ②"；各生态的 skill / Stop hook /
   `/goal` 只是对这份指令的**薄适配器**。

**薄适配器纪律**：生态完成事件与内核分离，适配器只做两件事——检测本会话改了
代码就调用 ①、① 成功后写 ②；**不在适配器里复制第二套验证逻辑**。理由：同一套
verify 资产要在所有 agent 生态复用，适配器里复写逻辑会立刻漂移；薄适配层整个
删掉后，git/CI 绑定仍能让闭环成立。因此生态 skill 是③的**可选加速器、不作
判据**；"三仓有 verify 入口但没有 agent skill 封装"判为"入口已备、适配器未接"，
不是"无验证能力"，补法按本节③的薄适配形态给建议。

**审计可核（survey `agent_adapter` 段）**：探测四类候选——`callable_entry`
（verify 资产候选，复用 §4.1）、`git_lifecycle_hook`（`.githooks/pre-commit` /
`.husky/pre-commit`）、`ci_lifecycle` 与 `ci_invokes_verify`（CI 配置是否调用
verify）、`ecosystem_adapter`（`AGENTS.md` / 生态 skill 目录 / 指令文件）。全是
形态候选链，miss 不构成违规。报告在 §4.11 覆盖行须逐条标注 ①②③ 的处置，并
点明**当前仓库由哪个 agent 无关的生命周期点兜底**：只写了生态 skill 而无
git/CI 绑定的，判"适配器已接、强制点未接"，不能算闭环。

### 4.12 证据留存边界（generated evidence ≠ committed artifact）

适用前提：done 判据会产出**落盘证据**（日志 / 截图 / 响应体 / cookie jar）。
无落盘证据时按"当前不适用"标注并写明理由。

"外部可查的证据"指证据生成在 agent 自述之外、可被独立核对（§0、§4.10），
但**可查 ≠ 入库**。把运行时证据提交进代码库会同时引入两个真实损害：带真实
会话凭据的证据文件进 git 历史（不可逆泄露，事后 `--no-verify` 也救不回），
以及每次跑出的时间戳目录无限膨胀。留存边界按三类资产分别规定：

① **运行时证据（evidence/ 的时间戳子目录：日志 / 截图 / 响应 / cookie）** —
   默认的临时核对产物，**不提交进版本库**：仓库根的忽略规则须覆盖证据目录
   （候选链 `.gitignore` / `.git/info/exclude` / 平台全局 ignore），使 `git add -A`
   不会把它带进索引。需要长期留存时走 CI artifact / 对象存储并绑定 commit sha，
   代码库里只留指向它的路径与 sha256。

② **会话凭据（cookie jar / token / Authorization 值）** — 比 gitignore 更根本：
   harness 在采集端就**不把它写进证据文件**，或写入前脱敏（清空 cookie 值、
   剥掉 Authorization 头）。理由：忽略规则只挡上传，本地文件仍在，打包外发 /
   `git add -f` / 换机器 copy 都会泄露；从源头不落盘才能根治。

③ **判卷基线（baseline 截图 / golden 集）** — 与①相反，**应入库**且列入
   `protected_paths`（§4.10 ①）：基线与容差是判卷标准，变更须人审，agent 不得
   把基线改成"当前渲染"。忽略规则若用 `evidence/` 整目录通配，须给
   `evidence/baseline/` 开白名单例外（`!evidence/baseline/`），否则基线被一起
   忽略，判卷标准无法跨机器复现。

**审计可核（survey `evidence_retention` 段）**：探测四类形态候选——
`evidence_dirs`（落盘证据目录）、`gitignore_covers`（忽略规则是否覆盖证据目录）、
`credential_files`（证据目录内疑似凭据文件名，如 cookies/token/secret）、
`git_tracked`（已被 git 跟踪的证据文件）。全是形态候选链，miss 不构成违规；
报告在 §4.12 覆盖行须逐条标注 ①②③ 的处置，并点明**凭据从源头是否落盘**
与 **baseline 是否有忽略例外**——二者是这节最常见的假阴性。

写作纪律：

- 处置**三选一**，缺一不可：`已建议`（指向建议编号）、`当前不适用`
  （必须写理由，如"无旧系统可对照"）、`待建设`（标 P0/P1/P2 阶段）。
- **「已建议」去向必须可核**：处置栏标 `已建议` 时，去向栏可写建议编号、
  「详见蓝图 §4.x（正文要点化，细节不重复）」，或两者都要（编号指"建议
  在哪"、详见指"细节去哪看"，**两者并存合法**）。实测教训：报告把「覆盖
  表点名了」误当「建议正文已带出」——如覆盖表列了 `hands/feature map`、
  `等价模式`、`误拦两次放行`、`删测试写理由`，但建议正文只有要点。
- **禁止不可核的自证断言**：去向栏**不得**写「已在建议正文带出 / 逐条列明 /
  列明」这类话——读者无从核验，且实测两份报告都栽在这句上：两份报告的
  §4.4 行都写「四模式已在建议正文带出」，但两份建议正文均无「等价」
  （其中一份连「幂等」也没有）；同一行又挂「详见蓝图（正文要点化）」
  免责——**既声称全带了又承认只写要点**，两个断言互斥。
  子项要么在建议正文里逐字出现，要么老实标"详见蓝图（要点化）"，
  不允许用一句无法核验的断言把两者混过去。
- **并列子项逐项标注，不允许整行合并**：§4.3 五子机制、§4.4 四模式 +
  spec 漂移、§4.7 双法、§4.10 四子项——每条须拆成独立行。实测教训：
  §4.4 是唯一曾被整行写的并列条目，于是「四模式择适」把「等价 / 幂等」
  吞掉了；拆行后每个子项都有一行去向，漏带即沉默缺项。这些子项是多条
  独立的绕过路径（RT-17 只覆盖 §4.3 的①②），合并等于放弃逐条核对。
- **阶段标注一致**：摘要的"当前处于 PX 阶段"须与 D 表逐项判定一致（该阶段
  有 ❌ 就不能说"成型"）；每条建议标题的 P0/P1/P2 须与 §3「阶段归属权威表」
  对得上，跨 D 维度的建议按 §3 纪律 2 拆。实测教训：某报告摘要称"P0 基本
  成型"却把 D7/D10 判 ❌，又给 D4 verify 资产挂 P0、把 P0 的 D10 塞进 P2
  建议——读者按阶段施工时会漏掉升级策略。
- **证据引用与判定信号同检查器**：D11 的证据必须来自 `static_risk_check.py`
  实跑，D8 来自 `verification_gate_check.py`，不得拿相邻扫描的 "0 命中" 顶替
  （实测：某报告 D11 写"无 sleep/rerun"却引用只扫过 skip 的 S5）。
- **可执行形态与证据核心措辞，要点化时不得丢失**：§3 的"本地先跑"是
  **agent 无关的能力**（改动交给下游前自动跑便宜门并留痕），通用落点是 git
  `pre-commit` hook；各 agent 的完成时事件（`/goal`、Stop hook 等）只是可选
  加速器，属平台示例、不作能力判据——报告里出现专有命令时必须标明这一点，
  不能让"没用某 agent 的某命令"被误判成缺能力；平台无关的等价替代形态见 §4.11（入口 + 会话事实 + git/CI 生命周期绑定，生态完成事件只作薄适配器）。§0 的"agent 只能引用不能转述"是证据协议的
  核心，§4.5 的拦截谓词（门拦什么）是门禁的接线——只写"开 PR 前本地门全绿"
  "由 harness 收集""off→observe→enforce"的要点化版本，AI 照着施工时会漏掉
  怎么落地。同型的还有**原文实证数字与评分口径**：§0 的"+10 分、最难任务
  收益最大"、§4.8 的"golden set 只有正确描述该 bug 才得分"——只写"独立
  grader 有效""建 golden set"的要点化版本，数字与计分规则会丢失，读者无法
  判断验证器是否在虚报 recall。这几项机检器管不到（属语义覆盖，机检不做
  语义理解以免把同义表述误报为缺项），须人工对照原文核；覆盖表 §0/§3/§4.5/
  §4.8 行已把它们列为要点化须保留项，生成报告时留意。
- **机检**：报告落盘前**只跑单一入口** `audit/scripts/report_gate.sh
  --report <报告.md>`——它一次跑完 `coverage_table_check.py`（覆盖表写作纪律：
  禁自证断言、并列子项拆行、处置三选一）与 `stage_consistency_check.py`（阶段
  标注与证据引用：建议标题阶段 vs §3 权威表含【缺口】行所有 D、摘要阶段判定
  vs D 表、D11/D8 证据来源），两道都跑完再聚合退出码（0/1/42，42 优先于 1）。
  用单一入口而非列两条命令，防"跑完第一道忘了第二道"。这是 review-the-reviewers
  的本地实例：报告自查的事实源自身必须被校验，否则下游对照会忠实放大它的错。
- 本表与 §2 的 D1~D12 诊断表互补：D 表回答"项目缺什么"，本表回答
  "蓝图每一项去了哪"。两表都齐，报告才闭环。
