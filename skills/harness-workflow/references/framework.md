# 框架篇：人 / 固定工程 / AI / 文档 的四方分工

> 本文件是 harness-workflow 的理论底座。读完能理解"为什么这么分、各方边界在哪、常见错配怎么纠正"。实操模板见 `goal-contract.md` / `rule-registry.md` / `escalation.md`；合入与门禁矩阵由消费项目按案例库设计要点自建（历史版本见 git 56ba8a7）。
>
> **禁用词适用范围（完整定义见 `rule-registry.md` 搜索"禁用词适用范围"）**：R-GOAL-001 的禁用词仅约束契约中与客观判定直接相关的字段（成功判据、边界情况、范围表）；本框架篇与 skill 自身的说明性文字不受该规则约束。禁用词检查由 `redlines.yaml` 控制，契约不得用开关关闭。

## 一、四者的本质与分配原则

分工的依据是各方的**本质属性**，而不是"谁看起来更适合"。

| 角色 | 本质属性 | 核心价值 | 根本局限 |
| --- | --- | --- | --- |
| **人** | 能承担责任、做价值取舍 | 定义"要什么"、接受风险、最终放行 | 注意力有限，慢，会疲劳和惰性 |
| **固定工程** | 确定性、可强制、不会被说服 | 让规则真正生效：门禁、状态机、权限、hook、脚本 | 只能判定写死的东西，不懂语义 |
| **AI** | 概率性的语义理解与生成 | 扩展、起草、扫描、执行、举证 | 会漂移、会作弊、会过度自信、不跨会话记忆 |
| **文档** | 持久化的、可被各方引用的事实 | 跨会话、跨角色传递目标与状态，是对齐的锚点 | 本身不执行，靠叮嘱的文档会被稀释 |

**分配决策顺序**，对每个动作依次问：

1. **能否用确定性规则判定或执行？** 能，就下沉给固定工程，不交给 AI。
2. **是否需要语义理解、生成或穷举？** 是，交给 AI，但必须有第 1 层的工程去验证它的产出。
3. **是否涉及价值取舍、风险接受、不可逆决定？** 是，交给人，AI 只提供选项和证据。
4. **结果是否需要跨时间或跨角色保留？** 是，落成文档，并指定谁写、谁读、谁能改。

**一句话**：工程管"强制"，AI 管"产出"，人管"决定"，文档管"记住和传递"。

## 二、各方的职责边界

### 人
- **做**：写目标契约；裁决歧义；定义风险分级标准和红线阈值；批准设计取舍；高风险项精读；最终放行（写"人放行记录"）；处理升级；配置超时升级链与代理人（见 `escalation.md` 第五章）。
- **不做**：逐行读全部代码；做机械检查（格式、重复、死链）；充当唯一的质量保障。
- **交付物**：签字确认的契约、裁决记录、放行决定（写入审计日志）。

### 固定工程
- **做**：状态机推进进度并记录时间/触发者/证据（该命令在开工前置未满足时拒绝推进，触发 E-18）；门禁（**测试、lint、类型检查（R-VER-006）、覆盖率、变异测试（R-VER-002）、依赖与安全/密钥扫描（R-VER-007）**）；权限（保护红线配置、状态文件、报告、CI、`governance/` 全套、`workflow/` 对 AI 只读；**判定命令与度量程序只允许调用 `governance/` 与 `audit/` 下的入口**，因此 `package.json` / `pyproject.toml` / `Makefile` 等通用文件不必整体受保护，AI 加依赖、改通用脚本不再触发 E-04；**项目自身的 `scripts/` 等保持正常读写**）；范围检查（对比改动文件与契约声明范围，**豁免 `ai_writable_paths`**，且须覆盖重命名/符号链接/子模块/文件模式/大小写/`.gitattributes`/`hook` 目录等边界情形）；追溯检查（需求↔设计↔代码↔测试有无断链）；偏离清单（从 diff 与契约工程推导，不依赖 AI 自报）；报告生成（证据由脚本写入，AI 不手填）；触发升级（连续失败 N 次、红线被改、越界改动）；**运行实装探针与合入放行记录校验（由 CI / 人执行，不由被治理 AI 执行；harness 只转述不验签）**；**CI 须从可信引用运行治理脚本（脚本取目标分支，不从 PR 分支取，组织级 required workflow / ruleset）**。
- **不做**：语义判断（"方案合理吗"）——这类问题只能转交 AI 或人。
- **原则**：凡是"AI 声称完成"的东西，都应改成"工程验证后给出结论"。

### AI
- **做**：复述目标，列出歧义/缺失/冲突，**不自行补全**（把遗漏作为建议写入 `ai_writable_paths` 下的 `proposals/`，由人合并）；起草需求细化、设计方案（多选项加利弊）、验收用例草稿；按设计实现，先写验收测试；在独立上下文中充当验证者，只看产出和契约；整理说明性草稿（偏离/未解决问题），**证据包由脚本生成，AI 只引用不生成**。
- **不做**：改红线、状态、报告、契约（只能提议）；自评风险等级；自行标记完成；遇到文档未覆盖的情形时自行推断继续；自行运行实装探针或写放行记录（也不自行验签/比对平台指纹）；写受保护路径下的任何文件；持有 merge/approve 凭据（R-SEC-005）。
- **权限边界**：AI 只能写 `ai_writable_paths`（`proposals/`、`.handoff/`、`ai-reports/`），只能读受保护路径；`ai-reports/` 下的产出（偏差、未决问题、违规事件草稿）视为"建议 / 草稿"，由人采纳后才生效。
- **默认行为**：遇到未覆盖情形或触发条件，停止并升级。

### 文档
文档不是一类东西，要按"谁写、谁改、谁读"分类，见下节。

## 三、文档的分类与权限

| 文档类别 | 示例 | 人 | 固定工程 | AI |
| --- | --- | --- | --- | --- |
| **契约类** | 目标契约、验收标准、红线配置、风险分级标准 | 写、批 | 强制引用、检测变更 | **只读**（改动只能经 `proposals/` 提议由人合并） |
| **设计类** | 设计文档、接口定义、追溯矩阵的设计部分 | 批准 | 校验一致性 | 起草、维护（受变更流程约束） |
| **状态类** | 进度状态、审计日志、任务清单 | 可查 | 唯一写入者 | 只读，仅经命令间接推进 |
| **证据类** | 测试报告、门禁结果、变异分数、追溯检查结果 | 抽查 | 生成 | 只能引用，不能改 |
| **提议类** | `proposals/`、`ai-reports/`、`handoff` | 批准、合并 | 校验 | **可写**（视为草稿 / 数据） |
| **知识类** | 规则索引、角色合约、经验教训 | 维护、批准 | 校验引用有效 | 可提议修改，由人批准 |
| **指令类** | 分层加载的 Agent 指令 | 维护 | 校验与规则库一致 | 读取 |
| **治理类** | `governance/` 与 `audit/` 下的脚本、hook、检查器、redlines、roles、probe-results | 维护、批准 | 运行 / 校验 | **只读**（受保护，含 scripts/hooks/redlines.yaml/roles.yaml/probe-results.json） |

**原则**：
- **单一事实源**：每条规则、每个阈值只写一处，其他地方引用（权威源见 rule-registry.md 末尾「单一事实源纪律」）。
- **写权限与责任对齐**：谁对内容负责，谁才能写入。AI 对产出负责，所以能写草稿，但只能写到 `ai_writable_paths`，不能直接改契约 / 红线 / 状态 / 报告 / 治理类文件。
- **文档变更本身要有门**：契约类和知识类的改动应触发工程检查，并需要人批准。

## 四、全流程分工矩阵

| 阶段 | 人 | 固定工程 | AI | 核心文档产出 |
| --- | --- | --- | --- | --- |
| **1. 目标与需求** | 写目标、范围、非目标、不可触碰项；裁决歧义 | 检查契约必填字段完整、无死链、无禁用词（仅限判据/边界/范围字段）；锁定契约版本并记录 sha256 | 复述并列出歧义、缺失、隐含假设；把遗漏写入 `proposals/`；扫描边界遗漏 | 目标契约（签字版）、歧义裁决记录 |
| **2. 验收标准** | 确认量化阈值；决定哪些必须人工验收 | 校验每条验收项能映射到自动检查或被标为"人工"（人工项须进 evidence_pack 的 manual_signoff） | 把验收标准转成可执行用例草稿 | 验收标准、用例映射表 |
| **3. 设计** | 选方案；批准需人拍板的取舍；定风险分级 | 检查设计条目是否都有需求来源；接口和字段一致性校验 | 出多方案及利弊；检查与既有实现的复用、冲突 | 设计文档、追溯矩阵（需求→设计） |
| **4. 实现** | 仅处理升级请求和红线变更 | 执行测试/lint/类型检查（R-VER-006）/依赖与密钥扫描（R-VER-007）；检查改动是否超出契约范围（覆盖边界情形）；拦截对只读文件的改动 | 先写验收测试再实现（以红绿证据判定，非提交顺序）；在授权范围内改动；越界 / 改红线 → 写入 `proposals/` 升级 | 代码、测试、追溯矩阵（设计→代码→测试） |
| **5. 验证** | 抽查高风险路径；评估测试是否真有效 | 跑门禁和变异测试（R-VER-002），自动写入报告；对比阈值（读红线配置）；从 diff 与契约推导偏离清单 | 独立验证 Agent 在干净上下文审查，只看产出和契约（含设计文档） | 门禁报告、独立审查报告、变异测试结果、工程推导偏离清单 |
| **6. 放行** | 看证据包和高风险项，决定合入并写"人放行记录"（绑定 commit/tree/base/evidence/contract_hash；低风险经预授权合入账号自动合入，AI 身份不得是该账号） | 汇总门禁结果；检查证据包完整性（含 manual_signoff）；校验"人放行记录"或 `PA-*` 存在且绑定对象匹配后由合入账号执行；**人放行记录由人写、不得由 AI 写** | 整理未解决问题、风险说明（说明性草稿，放第二阶段；证据包由脚本生成，AI 只引用不生成） | 证据包、放行记录（审计日志） |
| **7. 变更与异常** | 决定继续、改方向、终止 | 检测触发条件并强制暂停；记录事件 | 停下并给出现状、选项、影响 | 升级记录、契约变更记录 |
| **8. 沉淀** | 判断哪些经验值得固化 | 校验新规则可被机制执行或标注为软约束 | 提议规则和案例补充（写入 `proposals/`） | 规则库更新、复盘记录 |

## 五、四方如何保证目标一致

核心是形成一个**闭环互锁**，不依赖任何一方的自觉（图见 SKILL.md）。要点：

1. **文档是根**：目标契约由人写定，所有阶段的产出都必须能追溯回它。
2. **工程是锁**：契约里能机器检查的部分（范围、阈值、追溯关系、权限）全部变成机制，而不是叮嘱。
3. **AI 是执行者**：每个阶段开始先对照契约复述；产出必须附证据，而不是结论。
4. **人是放行者**：只看证据包和高风险项，用有限的注意力做有效的守门。
5. **反向路径**：工程检出漂移、越界、红线变更时，自动暂停并升级给人，不依赖 AI 自述。
6. **被治理的 AI 不是裁判**：实装探针、放行记录、合规结论必须由 CI / 人 / 系统身份产生，AI 不得自证、不得自行验签。

### 规则登记表（把对齐落到每条规则）

规则登记表是规则的人读权威；**机器可读权威源是 `governance/redlines.yaml`**（见 `rule-registry.md` 末尾纪律）。每条规则必须包含的字段（ID、描述、判定方式、执行者、强制等级、拦截点、违反处理、负责人等）**统一在 `rule-registry.md` 的「字段说明」中定义**，此处不重复；拦截机制位置与实装状态由项目自建映射维护。

没有判定方式的规则不准入库。这样"哪些规则真正生效、哪些只是叮嘱"一目了然。

## 七、落地中的常见错配

| 错配 | 后果 | 纠正 |
| --- | --- | --- |
| 让 AI 做该工程做的（统计覆盖率、标记完成、生成报告） | 虚报、编造 | 改为工程执行，AI 只引用 |
| 让人做该工程做的（逐行查格式、查重复、核对引用） | 注意力浪费，真正的风险项没看 | 下沉到工程 |
| 让文档承载该机制强制的（"请不要改阈值"） | 长上下文被稀释，被绕过 | 改成只读权限加变更触发门禁 |
| 让 AI 决定该人决定的（风险分级、阈值、范围变更） | 自评自放，目标漂移 | 标准由人事先写入契约类文档 |
| 让产出者同时验证自己 | 过度自信，系统性盲点 | 独立验证角色、干净上下文，高风险项换模型或交人 |
| 让被治理的 AI 当裁判（跑自己的探针、写自己的放行记录、自行验签） | 约束可被伪造 | 探针与放行记录、验签由 CI / 人 / 系统身份产生，harness 只转述 |
| 文档多处重复、没有单一事实源 | 修改后不一致，Agent 不知道以谁为准 | 单一事实源（见 rule-registry.md 纪律），其余引用 |

## 八、落地顺序建议

落地顺序与最小可行集由消费项目按需设计（历史版本见 git 56ba8a7）。核心提醒：先有最小工程骨架（契约只读 + AI 可写区分离 + 范围检查 + 契约锁定哈希），再放 AI；**最小集下一切转人、无自动合入**。运行模式矩阵见 `SKILL.md`「运行模式」。
