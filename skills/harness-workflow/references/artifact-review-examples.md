# harness-workflow 的「修改建议」示例清单（skill 无关）

> **⚠️ 非治理范围声明**：本文件是**体裁示范 / 附录**，**不在本 skill 的强制规则体系内**。本 skill 的强制规则只在 `rule-registry.md` 登记（"没有判定方式的规则不准入库"）。本文件提到的 PRD / DRD 渲染、图示解析、术语同义词检查等**仅为 harness 可能产出的「修改建议」示例**——登记表内无对应规则，harness 不得据此强制任何人；是否采纳由人决策。若未来要把其中某项变成硬规则，须先在 `rule-registry.md` 登记带判定方式的规则（如 `R-DOC-*`），再据此检查。

> 本文件列出 harness 在检查各类 artifact 时**可能产出**的「修改建议」示例。注意：这只是建议清单——harness 本身不修改任何上游产出或 skill，是否采纳、是否另行修改，由人决策。所有条目按 **artifact 类型** 分类，不绑定任何具体 skill 名；无论产物来自设计 skill、手写文档还是对话结论，只要字段能被契约 / 规则描述，就适用。

## 一、artifact 类型与可被检查的维度

| artifact 类型 | 典型内容 | harness 可检查的关键维度 |
| --- | --- | --- |
| 需求规格（PRD / Spec） | 目标用户、成功标准、Must-have、功能项编号 | 必填项齐全、待确认清零、功能项编号、需求→设计追溯 |
| 界面规格（DRD） | 页面、状态覆盖矩阵、跨组件接口 | 状态覆盖矩阵完整、需求追溯、跨组件接口编号一致 |
| 设计文档（Plan / 技术设计） | 设计目的、建模、接口、状态机、非功能 | 设计条目引用需求编号、关键结论附证据、接口错误场景、状态机矩阵完整 |
| 目标契约 | 范围、红线、成功判据、风险等级 | 范围表、受保护路径、阈值、风险等级 |
| 代码 / 提交 | diff、测试、CI | 范围外改动、门禁、失败测试先行、覆盖率 |

上面"典型内容"只是举例，不是强制分类；harness 只看契约字段与规则条目，不关心产物由谁、用什么工具产出。

## 二、harness 可能产出的「修改建议」示例（按维度）

### 追溯与越界
- **设计条目未引用需求编号** → 建议：每条设计条目补上对应契约 / 需求编号，使工程能做追溯检查（防"设计越界、需求漏实现"）。
- **需求无对应设计、设计无对应需求** → 建议：补齐双向追溯，或显式标注"本次不实现"。

### 状态与锁定
- **草案处于 draft 却要进入实现** → 建议：待确认清零并由人签字，把状态置为 locked 后再动手（由 state.json 的 status 字段控制，harness 只读该字段）。
- **批准后文档仍可被随意改** → 建议：批准后改为只读，变更走版本流程。

### 非功能与判据
- **非功能要求只"审视"无阈值** → 建议：安全 / 性能 / 可靠性要求写成契约里的判据与结构化阈值（metric/op/value/unit），才有可验收依据。
- **关键结论无证据** → 建议：设计 / 实现中的关键结论附命令输出或代码位置。

### 接口与可测试性
- **对外 / 关键内部接口缺错误场景** → 建议：补错误场景表，作为测试用例来源。

### 一致性（结构性，可脚本化）
- 约定必须出现的章节是否齐全（如设计文档缺"设计条目"章节，则追溯检查缺锚点）。
- 图示能否被对应渲染器解析（不依赖特定绘图语法，只检查能否解析成功）。
- 状态机"状态 × 事件"矩阵是否有空格（要求用结构化表格）。
- 术语是否出现同义异名（词表比对）。
- 标注的操作是否都有对应接口（操作带编号）。
- 标注的提交引用是否存在。

语义层（概念是否定义得当、层次是否越权）仍需独立 Agent 在干净上下文复核 + 人判断。

## 三、分工（人 / 工程 / AI / 文档在"检查"环节）

| 环节 | 人 | AI（harness 内） | 固定工程 | 文档 |
| --- | --- | --- | --- | --- |
| 检查 artifact 是否对得上契约 | 抽查高风险项、拍板取舍 | 对照契约复述、产出缺口 + 修改建议 + 证据 | 跑结构性脚本检查、卡门禁 | 契约 / 规则 / 证据包 |
| 一致性复核 | 决策 | 独立 Agent 在干净上下文复核语义 | 脚本跑结构检查 | 校验报告 |
| 采纳修改建议 | **决策是否改、怎么改** | 仅建议，不越权改上游 | 执行锁定的修改 | 变更记录 |

## 四、落地注意

1. **草案可交付，但 draft 状态不能进实现**：由 state.json 的 status 字段控制，harness 只读该字段，无需知道是谁产出草案。
2. **跨 artifact 的接口编号应互引**，用同一套编号，否则前后端 / 上下游设计对不上。
3. **自检标准本质是软约束**，按规则登记表分类：能转脚本的升级为硬规则，其余标 AI 复核或人判断。
4. **设计验证产物（如 HTML 原型）只做设计验证，不是验收依据**：验收以契约成功判据为准。
5. **所有建议由人决策**：harness 产出建议后停下，不自动去改任何 skill 或上游产出。
