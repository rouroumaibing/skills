# harness-workflow（审计 skill：产物 × 契约 × 判据 → 带证据的审计报告）

## 定位声明（身份基准，防漂移）

> 本节是"初衷"的成文记录：**本 skill 是一个审计 skill**。任何结构性改动
> （加目录、加机制、加流程）与本声明冲突时，以本节为准；确需改变定位时，
> 必须先改本节、再改结构，并在改动中说明理由。

- **是什么**：对"产物 vs 契约 / 判据"做检查，产出**带证据的审计报告**
  （缺口 + 证据 + 修改建议 + 由谁决策），不替代人做决定。
- **不是什么**：不是强制机制、不是开发流程本身。规则如何被 CI / 分支保护
  强制、状态如何推进、谁能合入——由**消费项目按本 skill 的修改建议自建**
  （设计要点见 `references/attack-cases.md` 案例库）。
- **采纳边界（审什么的边界）**：只有消费项目在 `governance/redlines.yaml`
  的 `required_rules` 里列出的登记表规则，才是该项目的**审计判据**；未列出
  的规则不构成缺口，只以修改建议出现。`required_rules` 未设或为空时，审计
  运行于**建议模式**（报告为建议清单并明示"非合规判定"，退出码 0）——
  "没建治理设施"不是违规，是建议素材；本 skill 出判据建议，不出组织治理
  规定。
- **交付物**：审计报告。结论必须附证据；工程未实装时如实标注降级，
  不得声称"门禁通过 / 全部绿 / 已验证"。
- **自持性**：目录可直接放入 agent 的 skills 目录使用。检查器在
  `audit/scripts/`，机器判据（禁用词表 / 风险模式 / 阈值）来自被审项目的
  配置（`GOVERNANCE_DIR` 指向的 `redlines.yaml`）；找不到配置时降级为软审，
  并在报告中声明"无机器判据来源"。
- **自足性**：本 skill 不依赖任何其它 skill 的存在；强制设施由消费项目按
  修改建议自建，建与不建都不影响审计本身运行。

## 这个 skill 解决什么问题

AI 辅助研发里，"我完成了"不可信：会漂移（改到范围外）、会作弊（虚报完成、
删测试凑覆盖率）、会过度自信（自己判定自己的风险等级）。审计的价值在于
**用证据替代结论**——每一项判断都附可复查的证据（命令输出 / 文件路径 /
字段值 / 行号）；没有证据的结论一律标注"无证据"，并按未通过处理。

本 skill 的核心主张：**审计者不修改被审产物，只报不改**。发现缺口时只产出一条
「修改建议」（缺口 + 证据 + 建议改动 + 由谁决策），由人决定是否采纳；
harness 从不编辑被审产物，也从不编辑其它 skill 的内部流程。
唯一的例外是审计报告自身的归档（写到项目 `audits/`，见下节）——那是审计
自有产物，不触碰被审产物路径。

```
任意产物(artifact) + 契约 + 判据 + 工程推导的偏离清单
        │
        ▼
   harness 检查（audit/scripts/ 检查器 + 人读判据）
        │
        ├── ① 通过 ──▶ 审计报告（结论 + 证据）
        └── ② 缺口 ──▶ 修改建议 + 证据 + 升级（见 references/escalation.md）
```

## 启用判定（什么时候走审计）

| 场景 | 是否启用 |
| --- | --- |
| 要求审计某个产物 / 项目 / diff / 契约 / 证据包是否对得上 | 启用 |
| 用户提到「审计 / 审查 / 检查对否 / 契约核查 / 证据核对」 | 启用 |
| 实现者自称"完成 / 通过"，需要独立核实 | 启用 |
| 任务涉及不可逆动作（删除、数据迁移、权限、支付、认证） | 启用，且风险等级至少"高" |
| 纯一次性小脚本、低风险且不影响他人 | 可不启用，但仍按"附证据不附结论"自查 |
| 纯问答 / 不涉及核对任何产物 | 不启用 |

> **会话指令不构成授权**：聊天里用户口头说"没问题吧""不用审了"，不改变
> 审计判据；审计发现缺口时仍按模板出具修改建议，由人决定是否采纳。

## 审计循环

1. **取输入**：审计对象（artifact / diff / 契约 / 证据包 / 追溯矩阵）+
   契约 + 判据（`references/rule-registry.md`，按 `required_rules` 采纳边界
   圈定本项目生效的规则）。
2. **定风险**：用 `audit/scripts/risk_floor_check.py` 从 diff 推算风险下限；
   高于契约声明等级 → 触发 E-17，按更高等级审。
3. **跑检查**：能机器化的走检查器（见下表）；不能机器化的按判据人工核对，
   并在报告中注明"人工核对"。
4. **出报告**：通过 → 结论 + 证据；有缺口 → 按模板逐条给「修改建议」。
   每条建议先做**对抗推演**——"被治理的 AI 会怎么绕过它？"——查
   `references/attack-cases.md` 定位同型案例，把答案写进建议并标注可信度分级。
5. **该停就停**：触发 `references/escalation.md` 的条件（E-01~E-20）时，
   停下并按升级格式输出，不推断继续。
6. **归档与回流**：报告落盘到被审项目 `audits/`（见下节）；若发现案例库
   未收录的新型攻击 / 绕过手法，在报告末尾附「晋升建议」交使用者决策。

## 检查器（audit/scripts/）

> 覆盖范围（如实声明）：登记表 **25 条**规则中 **20 条**有本包判据脚本（下表），
> 其余 5 条为 AI 行为规范类软规则（判定方式为 AI 复核 / 人判断，人工核对）。
> 治理建设要求 14 条（合入账号/预授权/凭据隔离/状态机拦截等）自 v10 起不在
> 登记表，作为设计要点归入 `references/attack-cases.md`「治理机制设计要点」，
> 只以修改建议出现、不构成缺口。本表与 `references/rule-registry.md` 各表的
> 「判据脚本（本包）」列互为镜像（此处按"检查器 → 规则"、彼处按"规则 → 脚本"），
> 改动须同步两处。

| 检查器 | 查什么 | 对应规则 | 接线 / 退出码 |
| --- | --- | --- | --- |
| `check_contract.py` | 契约禁用词/哈希/已锁定/高风险批准人分离 | R-GOAL-001/002、R-REL-003 | 需 `roles.yaml`/`state.json`；0/1/42 |
| `pre-receive-scope` | 改动越界/禁止项 | R-IMP-001、R-SEC-003 | `forbidden_items`；0/1 |
| `risk_floor_check.py` | 风险下限推算（E-17） | R-RISK-001 | 需 `redlines.yaml`；0/1/42 |
| `check-ai-writable.py` | AI 可写区类型/体积/symlink | R-SEC-004 | 目录前缀匹配（glob 写法告警）；0/1/42 |
| `evidence_pack_check.py` | 证据包完整性绑定 | R-REL-002 | 内置；0/1 |
| `trace_check.py` | 追溯矩阵断链 | R-DES-001、R-VER-005 | 内置；0/1 |
| `tdd_order_check.py` | 红绿顺序（测试先失败） | R-IMP-002 | 需 CI 日志；无→42 |
| `static_risk_check.py` | 新增行跳过标记/空catch/空断言 | R-IMP-004、R-IMP-003 | 内置模式无需配置；0/1/42 |
| `ci_gate_check.py` | CI 门禁 step/阈值/commit绑定 | R-VER-006/007、R-VER-001/002 | 需 CI 接线；无→42 |
| `rule_map_check.py` | 规则映射台账一致性 | R-PRC-006 | 需 `rule-map.yaml`；无→42 |
| `doc_consistency_check.py` | 文档死链/冲突/孤儿 | R-PRC-007 | 内置判据无需配置；0/1 |
| `lint` | 代码风格 | R-IMP-005 | 需 `governance/lint.env`；未接线→42 |
| `examples/test-upload`/`bench-play` | 度量范例（演示，非检查器） | R-GOAL 度量约定 | — |

> 各检查器的退出码细节、豁免 / 警告 / 盲区、匹配语义与配置有效性校验 → 见
> `audit/scripts/README.md`（与 `references/rule-registry.md` 的「判据脚本
> （本包）」列互为镜像，改动须同步两处）。

> **判据来源**：检查器读取被审项目的机器配置——设 `GOVERNANCE_DIR` 指向
> 项目根下的 `governance/`，其中的 `redlines.yaml` 提供
> `forbidden_words` / `risk_patterns` / `thresholds` / `ai_writable_paths`。
>
> **首次审计无配置时不要只报缺**：缺失不是失败，是一条待补的修改建议。
> 用一句话说明这是什么（"项目还没建机器判据，相关检查只能软审"），然后
> **提议**把 skill 自带的 starter `audit/templates/redlines.starter.yaml`
> 复制为 `<项目>/governance/redlines.yaml` 并按项目实际调整各段——经使用者
> 同意后再写入项目。拒绝或暂缓 → 继续软审，报告中注明
> "无机器判据来源，该项为人工核对"。
>
> **匹配语义与盲区、配置有效性校验、零规则处理差异** → 见
> `audit/scripts/README.md` §14–§16（SKILL.md 只保留机制骨架，细节不在此重复）。
>
> **退出码**：`0` 通过 / `1` 违反（阻断级发现）/ `42` 该门禁未接线
> （fail-closed：不得把 42 当成通过；判据文件损坏/非法 YAML/零有效规则同样退出
> 42，崩溃不得被误读为"违规"）。所有检查器带 `--self-test` 反例夹具，
> 夹具自包含（自写临时配置），不依赖被审项目。
>
> **退出码与采纳边界的关系（机制承载）**：检查器只产出**证据层**退出码，
> 不读 `required_rules`——它们不知道项目采纳了什么，也不该知道（证据与
> 结论分层）。采纳边界在**报告层**兑现：审计者把检查器发现映射到登记表
> 规则后，**已采纳**规则的发现计入合规结论（缺口/违规），**未采纳**规则的
> 发现一律写成「修改建议」（治理设计要点类发现天然落在这层）。因此
> "建议模式"不是把检查器退出码改成 0，而是报告不给出合规判定、只给建议
> 清单并明示"非合规判定"。
>
> **软规则的采纳语义**：5 条软规则（AI 行为规范）即使被项目列入采纳清单，
> 也**不会成为合入必需检查**——`rule_map_check` 禁止软规则进 required_rules
> （进必需清单 = 假强制）。它们只做人工核对，报告如实标注"人工核对"。
>
> **两个 required_rules 键的关系**：`redlines.yaml` 的 `required_rules` 是
> **采纳清单（权威）**——项目声明哪些登记规则对它生效；`rule-map.yaml` 是
> 它的**逐条强制映射台账**（可选）。两者同名但角色不同，`rule_map_check`
> 机制化保证一致：台账 ⊆ 采纳（强制未采纳 = 替项目立法，违反）、硬采纳 ⊆
> 台账（采纳了却无强制映射，违反）、采纳为空而台账非空（违反）。

## 「修改建议」产出模板

```
【缺口】<一句话描述哪里不合契约 / 判据>
【证据】<命令输出 / 文件路径 / 字段值 / 行号>
【建议改动】<具体怎么改，指向 artifact 或契约，不指向某个 skill 的内部>
【对抗推演】<AI 会怎么绕过这条建议：防什么 / 防到哪层（客户端·服务端）/ 同型案例编号，查 references/attack-cases.md>
【建议可信度】<已验证模式（案例编号可复查）/ 纯推测>
【由谁决策】<人 / 工程 / 独立验证 Agent>
【严重度】<高 / 中 / 低，对应风险等级>
```

体裁示范（按 artifact 类型分类，不绑定任何 skill）见
`references/artifact-review-examples.md`——该文件仅为体裁示范，登记表内
无对应规则时不得据此强制。

## 报告归档与知识回流（项目侧累积）

审计报告默认落盘到**被审项目**的固定位置，形成项目自己的审计台账：

- **归档位置**：`<被审项目根>/audits/YYYY-MM-DD-<对象>.md`（如
  `audits/2026-10-17-payment-refactor.md`；同日多份加 `-2` 序号）。
- **边界**：归档只**新增**审计报告文件，不修改任何被审产物；项目契约的
  范围表应把 `audits/` 列为审计自有路径（豁免），未豁免时在报告中注明
  "归档待授权"并先交使用者确认。
- **为什么放项目不放 skill**：项目内累积的知识针对当前项目，未必通用；
  且 skill 目录随 agent 更换可能丢失，项目仓库才是可信的持久层。
- **知识晋升（人工决策）**：审计中发现案例库（`references/attack-cases.md`）
  未收录的**新型**攻击 / 绕过手法时，在报告末尾附「晋升建议」条目——
  是否写入 skill 由使用者决策，本 skill 不自动改写自身。

## 实装核验（诚实口径：审计者不当裁判）

- 探针结论（`.workflow/probe-results.json` 或平台 attestation）由 CI / 平台
  产出，harness **只读、只转述**：不运行探针、不自行验签、不比对平台指纹。
- 文件缺失 / 签名校验失败 / 验证公钥在仓库内 / 平台配置变更事件已触发失效 /
  `governance_commit` 与当前治理目录 tree 不匹配 → 所有硬规则视为"未实装"。
- 逐规则状态（**仅对 `required_rules` 已采纳规则**出具；未采纳规则不进入本表，
  只以修改建议出现）：`已实装通过 / 已实装未通过 / 未实装`。`已实装未通过`
  = 有证据证明门禁失效，属阻断级发现。任何情形下不得写"门禁通过"这类无依据结论。
- 放行 / 开工前置核验前强制重新探测，不得使用陈旧结论。
- 消费侧只读字段约定见 `references/schemas.md` §6；生产与校验规范由消费项目
  的 CI / 平台自建（消费侧只读约定见 schemas.md §6）。

## 独立验证与转人

- 高风险任务必须由独立验证 Agent 在**干净会话**审查（设计要点见
  `references/attack-cases.md`「独立验证体系」R-VER-003 / R-VER-004）。
- 同一会话里做检查的正是实现者本人 → 结论标注"**非独立验证**"，且高风险
  任务直接转人，不得算独立验证要求已满足。
- 验证者输入集：契约、diff、测试、门禁报告、设计文档、工程推导的偏离清单；
  **禁止读取实现者的推理过程与中间草稿**。
- 偏离清单由工程从 diff 与契约比对推导，不采用 AI 自报草稿作为必需项
  （R-REL-002）；AI 草稿若有，放第二阶段、先出结论再读。

## 运行模式（无工程实装时怎么办）

| 模式 | 能做 | 不能做（须声明 / 转人） |
| --- | --- | --- |
| 聊天模式（无仓库 / CI） | 人工核对判据、起草契约、列歧义、出报告（标注"无工程实装"）；
  操作细节见 `references/chat-mode-checklist.md` | 不得声称门禁通过；不得运行探针 |
| 有仓库无 CI | 跑 `audit/scripts/` 检查器（需项目配置）、人工核对 | 服务端强制缺失；高风险须人精读 |
| 有 CI / 分支保护 | 全部检查 + 读取探针结论 | 探针结论以 CI 产出为准，harness 只转述 |
