# UI设计全流程引导（从0到1）

## 为什么这样设计

这个skill面向的用户往往完全不懂UI设计的专业流程——他们只有一个模糊的想法（"我想做一个XX"），不知道设计要经历哪些环节、每个环节要决定什么。如果直接把专业流程的问题一股脑抛出来，用户会被术语淹没；如果跳过引导直接画界面，又会回到"先画再想"的返工老路。

所以本skill的角色是**既当流程向导，又当翻译**：按行业通用的完整设计流程（问题定义 → 用户研究 → 竞品参考 → 范围收敛 → 信息架构 → 任务流程 → 布局 → 交互细节 → 视觉系统 → 测试迭代）逐阶段推进，但所有问题都用大白话问、用选择题降低回答门槛，专业概念只在需要时用一两句话解释。前面阶段的错误会污染后面所有工作——改一句需求描述几分钟就行，改一套已经开发完的视觉系统可能要几周——所以核心价值是**强制按顺序把决定想清楚，每一步都验证"这真的是用户想要的吗"**，而不是直接跳到画面。

## 交互原则（默认行为）

- **默认按阶段推进**：每个阶段先问1-3个关键问题（如果当前环境里有选择型输入工具，优先用它——对不懂设计术语的用户来说，选择题比开放式问题好答得多）。拿到回答后，用该阶段的自检标准判断信息是否足够；够了就简要小结这一阶段的结论，再进入下一阶段。
- **不要一次抛出所有阶段的问题**。一次只聚焦一个阶段，问完、对齐完，再往下走，否则用户会不知道从哪答起。
- **主动补专业知识，但不堆术语**。用户说"我不懂设计"时，用一两句白话解释当前阶段是干什么的（例如"这一步是先把产品里要有哪些功能列全，再决定哪些先做"），然后立刻给出具体可答的问题，而不是要求用户先去学概念。
- **用户随时可以喊停**：如果用户说"别问了""先给我一版""跳过细节"之类的话，立刻停止追问，用已有信息加合理假设直接往下推进到最终文档，并在文档里用【假设】标签清楚标出哪些是你替用户做的假设、哪些需要他们回头确认。不要因为信息不全就拒绝交付——真实的设计工作也经常在信息不完整时先出一版草案。
- **同一阶段最多追问两轮**。如果两轮之后用户依然给不出具体信息，就用行业惯例中最保守、最安全的默认值往下走，同样标注【待确认】，不要卡住不动。
- **允许跳跃，但记录代价**：用户明确说"某阶段我已经想清楚了"时，直接确认其结论并跳过；如果跳过的是前置阶段（如没定用户就直接谈布局），提醒一句"后面如果返工，多半会回到这一步"，然后尊重用户决定继续。
- **涉及多仓库协同时，标注要统一登记、链接要统一**（仅当设计确实牵涉多个独立仓库/小组——例如前端、后端、执行端各自一个仓库各自维护——时适用；单人单仓库项目忽略本条）：任何一个步骤/状态需要别的仓库配合（提供数据、执行任务、支持某个能力）时，用【需要协同：<仓库名> - 具体需要什么】标注，并同步登记进 DRD 的"跨组件对齐"附录（见"最终设计文档"章节），不要只写在某个阶段描述里、事后没人找得到。跨仓库引用一律使用团队实际指定的代码库链接方式（GitHub、GitLab、内部 Git 服务的 permalink 均可，以用户告知或项目既有惯例为准），**不用相对路径**——不同仓库很可能由不同的人或不同的 AI agent 在各自独立环境里实现，相对路径在无共享文件系统时会直接失效。（注意：这与"仓库内位置描述用相对路径/占位符"不冲突——相对路径用于描述同一仓库内的位置，跨仓库引用必须用绝对链接。）
- 全程记住：目标不是走完流程本身，而是让用户在合上文档时，能清楚回答"这个界面是给谁用的、核心任务是什么、怎么知道设计得对不对"。如果某个阶段的回答已经能回答这些问题，不必逐字走完模板，可以适当精简。

## 十个阶段

对每个阶段：先说明要挖掘什么、问什么问题、用什么标准判断"够了"，再决定写入最终文档的内容。

### 阶段1：明确问题与目标
- 挖掘：这个界面是为谁设计的（角色/熟练程度）？他们目前用什么老办法，痛点是什么？怎么算做成功（最好是具体、可观察的标准，而不是"更好用"）？
- 自检："能否用一句话说清楚谁、在什么场景下、用这个做什么"——说不清楚就还没到下一步。
- 写入文档：产品定位、目标用户画像、成功标准。

### 阶段2：研究用户与真实场景
- 挖掘：用户实际操作时的具体习惯是什么？最常犯的错误、最怕出问题的环节在哪？如果用户没有做过正式调研，引导他们回忆或推测至少几个具体场景，而不是停留在"效率低""不好用"这种抽象描述。
- 自检：能不能讲出至少两三个具体的、有细节的困扰场景。
- 写入文档：关键用户场景/痛点清单。

### 阶段3：竞品与参考分析
- 挖掘：用户见过哪些类似产品（直接的竞品，或体验上值得参照的产品）？喜欢它们的哪一点、讨厌哪一点？如果用户说不上来，主动提名2-3个该领域常见产品，问"你想要接近哪一种感觉"，帮用户建立参照系。
- 自检：能否说出至少一个明确的参照对象，以及"要借鉴什么、要避开什么"。
- 写入文档：参考产品清单及各自的借鉴点/避坑点。

### 阶段4：收敛范围与功能清单
- 挖掘：把前面聊到的所有功能想法平铺列全，然后引导用户分两堆：第一版必须有（没有就不是这个产品）vs 以后再说。对不懂设计的用户，用"如果只能保留3个功能，你留哪3个"这类强制排序问题帮他们收敛。
- 自检：第一版功能清单是否少到能用一屏列完；如果超过约7项，多半还没收敛够。
- 写入文档：第一版功能清单（Must-have）与后续清单（Later）。

### 阶段5：梳理信息架构
- 挖掘：第一版要承载哪些信息和功能？按用户的心智模型（而不是开发实现逻辑）应该怎么分组、分优先级？
- 自检：把这份分类讲给一个没参与设计的人，他能不能猜出某个功能大概在哪一类下。
- 写入文档：功能/信息分组结构（树状或分类列表），以及主导航的雏形。

### 阶段6：设计核心任务流程
- 挖掘：挑出3-5个最高频/最关键的任务，梳理用户从开始到完成要经过的每一步、每个决策点，尤其是异常情况（失败、超时、权限不足、需要撤销/回滚）。对状态复杂的产品（比如有"进行中/成功/失败"这类流程状态的），异常路径往往比正向路径更重要，要重点挖掘。若涉及多仓库协同，梳理时留意哪些步骤依赖别的仓库/小组（比如需要后端提供数据、需要执行端完成某个任务），按"交互原则"里的规则标注并登记。
- 自检：流程里任何一步，能不能自然回答"用户接下来该做什么、系统给了什么反馈"；答不出来的地方就是会卡住用户的地方。如果团队里测试是靠反串讲这份文档来推导测试用例的，再加一条：拿着这段流程描述，测试的人能不能自己写出至少几条测试用例（尤其是异常分支）——写不出来，说明流程描述得还不够具体。
- 写入文档：核心任务流程图或步骤列表（含异常分支；若涉及多仓库协同，含跨仓库协同标注）。

### 阶段7：低保真布局
- 挖掘：每个关键页面，最重要的信息/操作应该放在哪个区域？先只讨论布局层级和留白，不涉及颜色、字体、图标这些视觉细节。
- 做法：用文字描述各区域划分和层级关系即可（例如"顶部：全局状态与操作入口；左侧：分类导航；主区域：列表/详情，按重要性从上到下排列"）。如果当前环境里有可视化工具（例如能画示意图的工具），可以画一个简单的线框示意图帮用户直观确认；没有就用结构化文字列表描述，不要为了"看起来完整"而虚构像素级细节。**布局对齐确认后，立即把结论落成一份灰阶 HTML 骨架**（见"HTML 原型展示"章节）：用灰阶色块与占位文字把各关键页面做成可滚动、可看的页面，让用户直接看到"东西放在哪、层级对不对"，而不是只读文字描述。骨架阶段刻意不做颜色、字体与真实内容。
- 自检：如果需要额外解释"其实这个按钮很重要"，说明布局层级本身没做对，应该回头调整分区，而不是加解释。
- 写入文档：各关键页面的区域划分和信息层级描述。

### 阶段8：交互细节与状态设计
- 挖掘：逐个关键页面过一遍四种容易被忽略的状态——空状态（第一次使用、还没数据时看到什么）、加载状态（等待时显示什么）、错误状态（操作失败时提示什么、怎么恢复）、成功状态（操作完成后给什么反馈、引导去哪）。再确认高频操作的反馈方式（是否需要确认弹窗、是否支持撤销、表单出错怎么提示）。若涉及多仓库协同，标注哪个状态的数据/时机依赖别的仓库（比如错误码来自后端、进度来自执行端回写），按"交互原则"里的规则登记。
- 自检：随便指一个页面，能否回答"它在没数据、在加载、出错了、刚成功时分别长什么样"。如果团队靠反串讲这份文档推导测试用例，再检查这四态描述是否具体到能直接转成用例（比如"错误状态"是否写清触发条件和界面反馈，而不是只写"显示错误"）。
- 写入文档：各关键页面的四态说明 + 关键交互反馈规则（若涉及多仓库协同，含跨仓库协同标注）。这些四态描述随后会做成 HTML 原型里的可切换演示（见"HTML 原型展示"章节），用户点一下就能看到四种状态分别长什么样，而不是只在文档里读文字。

### 阶段9：视觉设计系统
- 注意：本阶段要问的比别的阶段多，**不要让用户一次答完一堆问题**——分成"核心问"（必答）和"条件问"（可合并成一次轻量追问；用户答不出时由 AI 按行业基线给默认值并标【待确认】）两批。
- 核心问1（硬约束，先问）：产品有没有既定的品牌调性/配色/VI 必须遵守？有——就以它为锚，后面的参照产品探索只能作为细部启发，整体方向不得违背品牌约束；没有——才进入核心问2 的自由探索。
- 核心问2（视觉锚点，不要一上来问开放式的"你想要什么风格"）：问用户"有没有一个你觉得'感觉'很像的产品——不需要截图，说个名字就行，比如'像Notion那种简洁'或者'不想要Jira那种密密麻麻的感觉'"。大多数用户在没看到具体东西之前，答不出"我想要现代感/高级感"这类抽象描述，逼他们描述反而会卡住流程；但几乎人人都能说出一个自己用过、并且对其"感觉"有明确好恶的产品。如果用户确实一个参照产品都想不到，就提供几个调性原型供选择，例如"冷静克制的工具感 / 温暖亲和的产品感 / 极简高级的品牌感"，选一个更接近的方向即可，不用精确定义。用户给出锚点后，顺带追问一句"你欣赏它哪一点"——这句话通常就是后面写数值规格理由时的原料。
- 条件问1（状态色与无障碍，多仓库/多小组协作场景下不能只靠一句话带过）：①如果产品里有"状态"概念（成功/失败/进行中/告警等），状态色是否需要做到不完全依赖颜色也能分辨（因为色弱用户和黑白打印都会失效）？②键盘能否操作所有关键流程、获得焦点时有没有清晰的视觉提示、给屏幕阅读器用户的关键元素有没有可读的文字标签、正文与背景的对比度是否达到基本可读水平——这几项若留白交给实现方自行判断，不同工程师做出来的结果会互相不一致。
- 条件问2（文案基调，轻量，不做完整内容策略）：错误提示希望是什么语气（比如"直接说明原因+下一步"还是"更委婉"）？有没有需要全平台统一叫法的专有名词（比如"流水线"和"Pipeline"不要混用）？
- 自检：假设整个界面变成纯灰阶，状态和层级信息是否大部分还能靠形状、大小、位置区分。
- 写入文档：①色彩/字体/间距/组件的**可执行数值规格**（间距阶梯、字号阶梯、圆角/阴影规则等具体数值，而不停留在"原则性描述"——因为这份文档要交给独立的小组甚至独立的 AI 各自实现，只写"原则"会导致各自做出来的间距、字号、圆角互相对不上），**并逐项写明数值背后的理由**（为什么选这套色系、这个字号阶梯想传达什么调性）：只给数值、不给理由的规格，下游无从判断哪些能改、哪些是刻意的，容易被"顺手优化"改走样；用户主动提供了品牌色值/字体就以用户为准，没提供则由 AI 基于选定的视觉锚点产出默认数值规格并标【待确认 / 可调】，**不要因为用户答不出数值就退回"原则性描述"**；②本阶段选定的视觉锚点（参照产品或调性原型），若受品牌约束注明约束来源；③无障碍规格清单（键盘可操作性、焦点态样式、屏幕阅读器标签、最低对比度）；④文案基调原则（提示语气、专有名词统一叫法）；⑤**（条件）导出 DESIGN.md**：若这份视觉规格需要交给独立小组/独立编码 agent 长期消费（即"最终设计文档"章节里不该合并成单文件的那类场景），就把①里的色彩/字体/间距**理由（不只是数值表）**整理成一份独立的 `DESIGN.md`——遵循 google-labs-code/design.md 的格式，**以 prose（设计意图的叙述）为主、token 作为被 prose 引用的具名常量**，不要只填一张数值表；若想先看规范原文、不必先建好文件，可先跑 `npx @google/design.md spec`（加 `--rules` 会连 lint 规则表一起输出）；并提示用户可用 `npx @google/design.md lint DESIGN.md` 校验（Windows/PowerShell 下改用 `designmd` 别名，避免 `.md` 后缀触发文件关联导致的静默失败）。**格式细节一律以官方 `spec` 命令（`npx @google/design.md spec --rules`）实时获取为准，本skill 不复制任何 schema**——该规范当前是 alpha、格式仍在变，本地抄一份副本必然过期。DESIGN.md 只是 DRD 视觉规格面向编码 agent 的一种**导出形态**，不是 DRD 的替代或等价物，真相源始终是 DRD。
- 对齐后动作，分两步走（默认推荐，但**不是强制**——用户赶时间或喊停时，风格探针可直接跳过进定稿，不要用流程绑架用户）：
  1. **风格探针**：先只做1-2个小尺寸的组件（比如一张卡片、一条导航栏），按选定的锚点用2-3种不同处理方式做出对比（例如"疏朗留白版" vs "紧凑信息密度版"），让用户直接指认喜欢哪个，而不是继续用语言描述。大多数人的审美是"看到具体东西之后才知道自己要什么"，不是"想清楚了才能说出来"——用便宜的小样对比，比一次性赌一个完整方向要可靠得多。注意：如果做出来的几种处理差异不够明显（模型反复生成的常见病），宁可不做对比、直接进定稿，也不要让用户在一堆差不多的选项里做无意义选择。
  2. **定稿**：方向确定后，把这个方向套用到阶段7 的灰阶骨架上，产出完整的高保真 HTML 原型（见"HTML 原型展示"章节），并内置灰阶开关，直接验证本阶段自检标准——点一下"灰阶模式"，看状态与层级是否还分得清。
- 后续反馈校准：如果用户看完原型说"感觉不太对"，不要停在这句话上，追问几个具体维度——太密还是太松？太冷还是太活泼？对比度够不够？圆角是大是小？问题尽量用大白话，允许用户用指认式回答（"喜欢左边那个""第一个更像我要的"）而不必会讲设计术语；若用户依旧答不出，用行业默认值推进并标【待确认】。目的是把说不清的感觉翻译成可执行的修改点，而不是让模型自己猜一个新方向重做。

### 阶段10：测试与迭代计划
- 挖掘：接下来打算怎么验证这版设计——找谁测、给他们什么具体任务？目前最担心哪个环节会让用户卡住？
- 自检：是否有一个具体、可执行的测试任务（比如"让一个没用过的同事试着发起一次发布"），而不是"随便找人看看"。
- 写入文档：测试计划（测试对象、测试任务、关注的失败信号）。

## 最终设计文档：默认拆成 PRD 和 DRD 两份

默认拆成两份，而不是合并成一份：**PRD（产品需求文档）覆盖阶段1-4，回答"做什么、为谁做、为什么做"；DRD（设计需求文档）覆盖阶段5-10，回答"具体怎么设计、怎么落地"**。拆分的理由是两份文档的读者不同：PRD 给业务方/决策者看，用来对齐要不要做、做给谁；DRD 给设计和工程侧看，是具体的落地规格。合并成一份的问题是，业务方评审时会被设计细节淹没，工程对接时又要在一堆背景介绍里翻规格。

**降级条件（避免对个人小项目过度工程）**：如果这是一次单人、单仓库、只出草案的设计（用户明确说"先给我一版"，或项目只有一两个页面），可以直接产出一份合并的 `UI设计文档`——把 PRD 与 DRD 的章节按顺序接起来编号即可，不必强行拆分，也不必为此另写一套模板。一旦涉及多仓库协同、要交给独立小组/独立 AI 实现、或要进入正式评审，就用 PRD + DRD 拆分。

阶段信息不全的部分统一标注【假设】或【待确认】，不要跳过章节。

**PRD 模板：**

```markdown
# [产品名] PRD（产品需求文档）

## 1. 问题与目标
（目标用户 / 痛点 / 成功标准）

## 2. 用户与场景
（关键使用场景与痛点清单）

## 3. 竞品与参考
（参考产品 / 借鉴点 / 避坑点）

## 4. 范围与功能清单
（第一版 Must-have / 后续 Later）
```

**DRD 模板：**

```markdown
# [产品名] DRD（设计需求文档）

## 1. 信息架构
（功能分组结构与主导航）

## 2. 核心任务流程
（含异常分支的流程说明；若涉及多仓库协同，含跨仓库协同标注）

## 3. 页面布局
（各关键页面的区域划分与信息层级）

## 4. 交互细节与状态
（各页面空/加载/错误/成功四态 + 反馈规则；若涉及多仓库协同，含跨仓库协同标注）

## 5. 视觉设计规格
（色彩/字体/间距/组件的可执行数值规格及其理由；无障碍规格清单；文案基调原则；选定的视觉锚点；若需交给独立小组/编码 agent 长期消费，另导出 DESIGN.md）

## 6. 测试与迭代计划
（测试对象、任务、关注信号）

## 附A：跨组件对齐
列出本文档中涉及、但决策权或实现权分布在其他仓库/小组的概念，每项标注：涉及哪个仓库、需要对方支持什么、参照哪份文档/哪个链接（统一用团队指定的代码库链接方式，不用相对路径）。如果这次设计不涉及多仓库协同，本节留空或注明"本次无跨组件依赖"，不要删掉这个结构。

## 附B：通用验收标准
用这五条来验收任何一版视觉稿，而不只是这份文档本身：
1. 一句话测试——能否一句话说清这个界面是给谁、解决什么任务的
2. 5秒测试——陌生用户看首屏5秒内能否明白"这是干嘛的"
3. 三步测试——最高频操作能否在3步以内完成
4. 灰阶测试——去掉颜色后，层级和状态信息是否还能分辨
5. 陌生人测试——找一个没见过产品的人试做一个具体任务，观察卡在哪
```

## HTML 原型展示（把设计变成看得见的页面）

Markdown 文档描述的是"想法"，用户只能在脑子里渲染成画面；很多设计问题（布局层级不对、按钮不突出、状态缺失）在文字里根本看不出来，用户也无法基于想象给出有效反馈。所以本skill在流程中**用 HTML 把设计落到看得见、点得动的页面**：文档负责记录结论，HTML 负责展示效果，避免"文字自嗨"。

### 产出时机（两次，渐进）

1. **阶段7 布局对齐后 → 灰阶 HTML 骨架**：只做结构与层级，不做视觉。用灰阶色块、占位文字把关键页面的区域划分和导航做成可滚动的页面，让用户确认"东西放在哪"。
2. **阶段9 视觉对齐后 → 高保真 HTML 原型**：在骨架上应用确认过的配色/字体/间距/状态色；把阶段8 的四态做成可切换演示；内置"灰阶模式"开关，直接跑一遍阶段9 的灰阶自检。

### 生成前后的核对机制（结构契约）

生成 HTML 时容易在"一边回忆前面阶段聊过什么、一边写代码"的过程中，悄悄漏掉或简化某个已经对齐过的决策——这种损耗不是因为不认真，而是生成前没有一个显式的核对步骤。但核对机制只对**有一定规模的项目**值得做：仅当覆盖页面数 ≥ 2 或硬性决策 ≥ 5 项（区域划分、四态、异常分支、导航分组等）时执行下面两步；只有 1 个页面的小项目直接生成即可，不要过度工程：

1. **生成前，先提炼结构契约**：把当前阶段涉及的文档决策浓缩成一份简短清单，逐项列出这次HTML必须体现的硬性事实，例如：每个关键页面的区域划分（顶部/侧边/主区域各放什么）、每个页面要覆盖的四态（空/加载/错误/成功）、每条任务流程的异常分支（失败后能否重试、回滚入口在哪）、信息架构里的导航项和分组。
2. **生成后，逐项核对**：拿这份清单对照生成出来的HTML，一条条确认"这一项体现了吗、体现在哪个位置"。没体现的，要么当场补上，要么在HTML里用可见的占位标注为【本版暂缺】，绝不能默认"应该都写了"就算完成；核对结果用一两句话简要告诉用户，不要藏起来。

契约是**一次性工具，用完即弃**：核对完成后把契约清单放进 HTML 顶部注释或直接删除，不要落成一份常驻的第三份文档——本skill只维护 Markdown 文档与 HTML 两处真相，避免三方漂移。

这一步不依赖审美好坏，是纯粹的完整性检查，目的是保证HTML忠实反映前面阶段已经拍板的结构性决策，而不是让生成过程凭记忆自由发挥。

### HTML 实现规范（执行时遵守）

- 单文件自包含：一个 `.html` 内含全部 `<style>`；允许少量内联 `<script>`，只用于状态切换/灰阶开关；不依赖外链资源、CDN、网络字体。
- 页面数量：优先覆盖 3-5 个最关键的页面（阶段4 Must-have 中的高频页面），多页面可在同一文件内用顶部导航切换；不要为了"看起来完整"给每个页面都做。
- 占位内容：文案用"标题占位 / 内容占位 / XX 列表"等中文占位，不虚构真实业务数据。
- 状态不只靠颜色：成功/失败/进行中/告警一律同时用图标 + 文字（+形状）表达，呼应阶段9 自检。
- 四态演示：空/加载/错误/成功用按钮或下拉切换，用户能逐一点开查看。
- 灰阶开关：页面提供"灰阶模式"切换，一键验证去掉颜色后层级与状态是否仍可分辨。
- 定位：HTML 是设计验证工具，不是开发产物——不做像素级打磨、不做真实交互链路与后端逻辑、不追求生产级代码质量。

### 反馈回流与文件名

- 用户看完原型提出的改动意见，先回流到对应文档（默认是 DRD；降级为单文件时即该设计文档）里对应阶段的设计结论，再同步更新 HTML，保持文档与原型一致，避免"只改了 HTML、设计决策和文档脱节"。
- 文件名用 `<组件名>-UI-原型.html`，与 PRD、DRD 一起保存到输出目录并展示给用户。

### 什么时候可以不做

用户明确说"先不用 HTML / 只要文档"时跳过。若用户中途喊停进入"直接交付草案"模式，优先保证 Markdown 文档完整，HTML 原型作为可选加分项。

## 输出与交付

- 默认三件交付：PRD（`<组件名>-PRD.md`）+ DRD（`<组件名>-DRD.md`）+ HTML 原型（`<组件名>-UI-原型.html`），保存到输出目录并一起展示——让用户既看到结论，又直接看到页面效果。PRD/DRD 拆分是默认结构，不因为参考项目当前是单文件就默认合并回去；但满足上文"降级条件"（单人、单仓库、草案级）时，允许合并为一份 `UI设计文档` + HTML 原型两件交付。
- 文件位置与命名前缀：如果用户提到项目里已经有统一的设计文档仓库、并且分组件目录存放（比如 `console/`、`hub/` 这类结构），就把文件放进对应组件目录下，并沿用该仓库已有的命名前缀习惯；如果用户没提供这类信息，默认用 `<组件名>` 或 `<项目名>` 作为前缀。**不要主动假设一定要放进某个特定仓库或使用某个特定代码托管平台。**
- 只有用户明确要 Word 文档时，才读取 docx 相关技能把 PRD 或 DRD 转换成 .docx——不要默认额外生成。
- DESIGN.md 是**条件交付**：只有阶段9 触发了导出（这份视觉规格要交给独立小组/独立编码 agent 长期消费）时才额外产出 `DESIGN.md`，默认不生成——它是 DRD 视觉规格的导出形态，不是并列的第四份真相源。
- 用户看完 HTML 原型提的改动意见，先回流修改 DRD（或降级时的设计文档）里对应的设计结论，再同步更新 HTML，避免两者脱节。
- 交付后不需要在对话里逐字重复内容，简要说明生成了什么、PRD/DRD 里哪些地方是【假设】或【待确认】、原型里哪些是占位，让用户直接打开文件看效果。
