本技能指导如何进行模块设计，通常表现为设计文档的写作。适用场景包括：为系统增加模块、为系统增加功能、为复杂设计增加逻辑图（线程模型、状态机等）。完成设计文档的过程中，通常还需要通过查看代码、运行测试程序等手段验证结论。

用户通常会提供目标模块名称、设计目的、设计范围等要求，有时还会提供参考文档、代码或类似系统的设计。输入不完整时应主动追问缺失的关键信息（尤其是设计目的和上下文代码版本），避免基于猜测展开设计。

## 输出规范

设计通过 .md 文件呈现，优先使用mermaid绘图（避免ASCII Art 因字宽导致难以辨认）。回复中只需总结完成了什么设计；如果是修改已有文档，只描述修改部分。

**输出模板：**

```markdown
# [模块名] 设计文档
## 1. 设计目的
## 2. 设计逻辑
## 3. 核心数据结构
## 4. 接口定义
## 5. 一致性校验
## 6. 变更历史
|日期|变更内容|原因|

```

## 设计方法

### 设计颗粒度

设计文档应匹配问题复杂度——简单功能堆砌复杂建模会浪费编码时间，复杂系统省略关键建模会导致实现偏离设计。在动笔前，先判断设计粒度：

| 问题复杂度 | 示例 | 需要的内容 |
|---|---|---|
| 简单 | 增删改查、配置项读写 | 设计目的 + 接口定义即可 |
| 中等 | 业务模块、数据流转管道 | 全部章节 |
| 复杂 | 分布式一致性、多视角（功能+性能+安全） | 全部章节 + 多视图建模 |

设计文档应随问题复杂度伸缩，不为简单功能堆砌复杂建模。

### 设计目的

**为什么要先写设计目的：** 在展开大量设计信息前先把目标表达清楚，能与用户一开始就对齐方向，避免写完整篇文档后才发现双方目标不一致。设计目的不是“要做什么”的方案罗列，而是“为什么要做”的动因陈述。

**总结：** 设计目的是说“为什么要做”，不是说“要做什么”。需要：（1）总结用户的目的并补充遗漏和矛盾；（2）定性目标类型（新模块/新功能/优化/重构/逻辑视图）；（3）建模系统当前状态作为起点；（4）标注设计对应的代码版本（git branch 或 revision）。修改已有文档时，设计起点保持原来文档的状态，不重置为当前时刻。

**举例：**
```
❌ "本文的设计目的是描述 xxx 协议的通讯过程" <- 这是“做什么”
✅ "当前系统（main@abc1234）的内存池不支持运行时扩容，当连接数超过预分配容量时会导致服务拒绝。本设计目的是为内存池增加动态扩容能力。" <- 这是“为什么做”
```

### 设计逻辑

**为什么要先梳理设计逻辑：** 设计逻辑是设计文档的主体，它建立的是“我们做了哪些设计选择”以及“这些选择为什么能达成目标”之间的因果链。只列最终方案不写选择依据，等于把设计的灵魂抽走，实现时遇到变体就无所适从。

**总结：** 设计逻辑是设计文档的主体，用有效的逻辑链条说明目标如何达成。抓住2-3个核心挑战和取舍即可，不罗列细节——如果某个问题没有取舍（只有一种合理方案），简述结论即可，不需展开。方法包括逻辑树、通讯流程图、状态迁移图、设计原则等。如果有多个视角（功能/性能/安全），分别建模。确定逻辑前，先分析子功能应放本层还是依赖层；确定后，决定封装策略（完全封装/薄封装/直接暴露）。

**举例：** 设计一个高性能RPC 通讯模块

- **功能视图**（mermaid时序图）：调用方->Proxy->被调用方，建模Payload如何封装到上层报文。
- **性能视图**：一次调用经过3次转发，每次转发～0.1ms,总延迟～0.3ms，满足<1ms目标
- 取舍记录：“选用无锁队列而非互斥锁队列，因为测试显示锁竞争在万级QPS下成为瓶颈”

## 概念空间

**为什么要显式建模概念空间：** 设计过程常常是从已有概念的过程——新概念是对“如何解决问题”的核心抽象，命名不清晰或定义不恰当会让整篇文档语义混乱、接口命名退化回底层实现。

**总结：** 概念空间是为描述设计目的和逻辑而引入的一组基础概念。每解决一个核心问题，都要检查是否需要新概念来命名解决方案，并说明它由哪些已有概念组成、封装了什么复杂性。新概念定义后，数据结构和接口必须直接使用新概念名称。概念在解决问题时自然产生，不要脱离问题预先定义；每次迭代文档时，也回过来检查已定义的概念是否仍然适合描述方案，能否通过改进概念定义让整体更简洁。

**举例：** 基于socket 设计RPC协议

- 已有概念：socket的服务端、客户端
- 新概念：调用方（Caller）、被调用方（Callee）。调用方不一定对应socket客户端，部分服务端也可以是调用方。
- 接口使用新概念：`rpc_call_from_caller()`✅  `socket_server_send()`❌
- 反例： 不要预先定义“会话管理器” “消息路由器”等概念再硬套到功能上

## 设计产物

### 场景决策表

先根据设计类型判断哪些章节必写：
| 设计类型 | 核心数据结构 | 接口定义 |
|---|---|---|
| 新模块 | 必写 | 必写 |
| 新功能（复用已有数据结构） | 可省略 | 必写 |
| 重构（结构和接口已存在） | 可省略 | 可省略，用“主要修改点”代替 |

### 核心数据结构

**总结：** 任何模块都围绕一组核心数据结构工作。设计阶段只需定义与设计逻辑对应的关键成员，不需覆盖每个细节（编码阶段再补）。多个数据结构之间有关联时，用类图或关系图表达。如果目的是重构且数据结构已存在，本节可省略。

**举例：** 内存管理模块

```c
struct MemBlock {
    size_t size;	//块大小
    MemBlock *next;	//自由链表指针
    bool allocated;	//是否已分配
};
```
配合mermaid类图展示 `MemPool -> MemBlock[] -> FreeList`的关系

### 接口定义

**为什么设计阶段就要写接口：** 接口说清的是“说通概念、降低编码风险”，不是要替代编码阶段的详细设计。设计阶段没对齐接口语义，编码时就会在参数含义和协作流程上反复返工。

**总结：** 接口是设计逻辑和概念空间的对外表现。重点是表达接口在系统中的角色和功能（自然带出参数用途），而非严格定义参数范围或所有错误处理。每组接口应有一个一句话总结，描述它们的协作关系，最好对应到设计目标中的某个流程。以函数签名形式定义时，建议描述写成函数注释，方便在上下文中看多个接口的关系。如果目的是重构且接口已存在，本节可省略或用“主要修改点”代替。

**举例：** Socket 通讯接口

```c
/// 创建与host的连接，返回会话fd
int socket(const char *host);

/// 通过fd发送msg长度的消息
int send(int fd, const  void *msg, size_t len);

/// 通过fd接收消息到buf
int recv(int fd, void *buf, size_t buf_len);

/// 关闭fd对应的会话，释放资源
void close(int fd); 

```

**协作总结：** 要对another_host通讯，先`socket(another_host)`建连得到fd -> 基于fd 用`send()/recv()`收发消息->完成后`close(fd)`释放资源。

#### 内部接口

**总结：** 当设计逻辑涉及多模块或内部通讯协议时，需要定义内部接口（内部报文格式）。内部接口虽然不属于对外API，但决定了外部接口的实现细节，不定义就无法理解外部接口的行为。

**举例：** 定义了客户端和服务端端内部通讯协议，就需要描述内部报文格式：

```
| 4B magic | 1B msg_type | 4B payload_len | payload ... |
```

不定义这个格式，`send()` 发送的消息内容就无法理解。

## 质量保障

### 一致性校验

**总结：** 文档完成后，综合检查设计目标、设计逻辑、核心数据结构和接口之间是否有逻辑冲突、遗漏、重复或异常未处理。逐项检查以下四个维度：

| 维度 | 检查内容 |
|---|---|
| 概念一致性 | 同一概念全文同术语，无同义异名或异义同名 |
| 状态完备性 | 状态机的每个状态处理了所有输入事件（含非法事件） |
| 接口完备性 | 设计逻辑中提到的每个操作都有对应接口 |
| 层次一致性 | 本层接口没有承担属于其它层的职责 |

除结构一致性外，还需逐项审视四个非功能性质量维度：

|维度 |检查内容 |
|---|---|
| 安全性 | 是否有认证、授权、输入校验、数据暴露等风险未处理 |
| 可靠性 | 失败恢复、重试、幂等、资源释放是否完整 |
| 可测试性 | 关键路径能否被隔离测试，是否有可观测入口 |
| 可调试性 | 是否有关键状态/链路日志，能否定位问题路径 |

**举例：** 检查发现“连接超时”在设计逻辑中描述了处理策略，但接口定义中没有对应接口 -> 需要补充`set_timeout(fd, ms)`接口。

### 迭代完善

**总结：** 设计不是一次完成的。实现中发现逻辑漏洞、需求变化、性能/安全测试发现问题时，都应该回顾修订并记录变更历史。迭代时必须以设计目的中定义的起点为准，不把中间被放弃的方案当作修订基线。

**举例：**

```
起点： “需要一个排序算法”
第1版：冒泡排序
迭代时：基于“需要一个排序算法”重新设计为快排
  ✅ “为满足O(nlogn)目标，采用快排方案”
  ❌ “冒泡排序速度不够快，所以换成快排” <- 冒泡是废弃的中间方案，不应作为基线
```
