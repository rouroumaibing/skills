# Mini-Code：安全的代码精简技能

## 核心原则

代码精简的目标是**减少代码量，而不改变任何可观察的行为**。当"精简"和"验证行为不变"这两件事无法同时满足时，先暂停精简，而不是先动手再补救。

对测试代码精简要格外小心：测试代码本身是验证"业务代码精简是否安全"的工具。如果测试代码被错误精简（比如漏合并、删断言），本该报警的地方不会报警——这是这个技能里风险最高的一类操作。

## 不可突破的底线（无论用户如何要求，都不能违反）

1. **可观察行为不变**：返回值结构、异常类型、副作用保持一致。注意区分「外部可观察行为」与「内部结构形态」——当本次目标是简化结构（例如把不必要的 class 塌缩为函数/闭包）时，接口/形态的变更是简化的目的本身，但必须满足：① 用户显式选择该简化；② 所有调用点同步更新；③ 改动后验证（见第四步）确认可观察行为完全一致。绝不默许「为去重而悄悄改行为」。
2. **不删除任何异常路径或边界值的测试**，即使代码结构和"正常case"的测试看起来相似
3. **合并测试用例前，必须确认场景/输入边界/断言点完全重叠**；只要有一点不确定，就不合并，而是保留独立用例并说明理由
4. **没有测试或没有可对照的输入输出样本时，不做批量精简**——此时的首要任务是先补验证手段，而不是精简
5. **"伪冗余"（外观相似但服务不同场景）不能当作"真冗余"处理**——发现相似代码时先判断是语法相似还是语义相同

**关于用户施压**：如果用户要求跳过流程（比如"不用列清单了，直接改"、"我时间紧，你按你判断做"、"出问题算我的，你就改"），可以简化沟通形式（比如不逐条罗列清单，用一两句话说明风险点），但底线 1-5 依然不能被这种要求突破。"用户想跳过确认步骤"和"用户已经认可可以改坏行为"是两回事，不能把前者当作后者的授权。

## 标准流程

### 第一步：前置检查（问用户，也要查代码）

先问（必要时）：
- 这份代码是否已经上线/被其他模块依赖？
- 有没有自动化测试，或者至少有一组可信的输入输出样本？

**不要只问，要实证**。用户声称"没有别处用到"时，先用静态分析验证再定精简范围：
- 查引用：`grep -rn "目标符号" .` 或 `rg "目标符号"`（或 IDE 的 Find Usages）
- 查导出/导入关系、路由表、注册表、配置文件里的间接引用
- 动态语言特别注意 grep 不到的引用方式：字符串拼接调用、`getattr`、反射、依赖注入容器、装饰器注册

**先界定"哪些目录不该碰"，再谈精简什么**。动手前先识别并排除**不在构建路径里**的目录：参考实现副本、vendored/第三方快照、只读文档、代码生成产物、fixtures 快照。这类目录的共同危险是——**改坏了测试全绿也不会报警**：它们不被编译、不被导入，或改动会被下次生成覆盖，因此测试用例一条都不会失败。把排除清单明确列给用户，再定精简范围。

> 真实教训：某仓库按文件数统计，84% 的 TS 文件位于一个只读参考目录。若跳过这一步直接执行"全仓精简"，会改坏参考实现，而所有测试照常通过。

如果测试和样本都没有 → 明确告诉用户风险，建议先补测试或提供样本，暂停精简本身。如果用户仍坚持要改，可以做**最小范围、最容易验证**的部分（比如经静态分析确认未被引用的死代码），其余部分维持底线 4 的立场。

如果有 → 记录基线（测试通过率/覆盖率的具体数字），进入下一步。

### 可选：静态检查工具辅助（提高候选发现效率，不替代判断）

这一步是**可选的**：没有配置任何工具时，本技能的流程照常执行，候选发现靠人工阅读与 `rg` 即可。

若项目已配置 linter / 静态分析工具，可运行一次，把以下类型的输出**纳入候选清单**（是候选，不是结论）：

- 未使用的导入 / 变量 / 函数（高置信度，风险最低，可优先处理）
- AST 级别的代码重复报告
- 圈复杂度超阈值的函数（作为"过度设计"的候选信号，但**不能**直接判定该拆）

**两条不可违反的边界：**

1. **工具标记 ≠ 真冗余**。工具不理解业务语义：Go 的 `error` wrap 差异、Rust 的所有权差异、TypeScript 的 `null`/`undefined` 语义差异，工具都识别不了。任何被工具标记为 duplicate 的代码，仍必须完整过第二步的五项 checklist。
2. **工具没报 ≠ 没有冗余**。工具发现不了**数据源扇入冗余**（多个函数各自独立读同一来源，代码外观可能完全不同），也发现不了"该拆的抽象"。这两类恰恰是本技能要主动识别的重点——**不能因为工具静默就跳过**。

各语言的推荐工具与特有陷阱见 `./references/language-traps.md`（本技能只引用、按需加载，不内嵌）。

### 第二步：分类冗余（先分析，不动手）

把发现的相似/重复代码分成三类，并列给用户看：

- **真冗余（可安全处理）**：完全重复的代码块、未被引用的死代码/变量/导入、注释掉的旧代码、调试用的 print/log
- **伪冗余（不能合并，标记出来）**：外观相似但覆盖不同场景/边界/上下文
- **可合并冗余（需要重构，需和用户确认合并方式）**：真正同一语义的重复逻辑，可提取公共函数/公共测试 fixture/公共模块

**混合形态（共享骨架 + 各自差异）**：当 N 个实现共享同一套骨架、但各自核心逻辑不同时（例如多个 adapter / handler / provider），不要整组合并，也不要整体判为伪冗余完全不动——先**逐字比对**（MD5 或逐行 diff，不能凭签名一致就认定）找出逐字相同的部分（方法 / 字段 / 初始化），抽成共享基类或 helper；再把各自不同的核心逻辑作为差异**分别保留**。正确答案几乎总是「提取骨架 + 保留差异」，而不是两端之一。

**判断"伪冗余"还是"真冗余"，先过这张 checklist——五项全部相同才算语义相同：**

| 检查项 | 要确认什么 | 语言特异性提示 |
|---|---|---|
| 空值处理 | 是否都处理（或都不处理）空输入 | Python `None`；TS `null \| undefined`、可选链 `?.`、空值合并 `??`；Go 零值、`nil`、空字符串 |
| 边界值 | 0、负数、上限、空集合的处理是否一致 | 注意隐式边界：Go 整数溢出、JS 浮点精度、Python 大数自动扩容。**务必验证空集合 / 空输入的「返回类型」与「数值类型兼容性」**：Python `sum([])` 起点是 `int 0`，而 `total = 0.0` 起点是 `float 0.0`，空输入会返回不同类型；`Decimal` 等非 float 数值与 `float` 累加器不兼容（一个 `TypeError`、一个正常）。只凭「两个函数看起来都做累加」就判真冗余，会漏掉这类差异——判真冗余前必须实证空/边界输入的返回类型与数值类型一致。 |
| 同步/异步 | 调用上下文是否一致 | Python `async/await`；TS `Promise`；Go goroutine/channel |
| 异常/错误类型 | 抛出或返回的错误类型及处理方式 | Python 异常类型层级；TS `throw` vs 返回 Result；Go `error` wrap（合并可能打断 `errors.Is/As` 链） |
| 业务规则语义 | 是否代表同一条业务规则 | 两条规则碰巧写法相似 ≠ 一条规则写了两遍 |

**五项中有任意一项不同 → 是伪冗余**。标记出来、说明差异点、把"是否统一"的判断权交还给用户——那是业务/产品层面的决定，不是代码去重。

对于**跨文件/跨模块**的相似代码，额外确认：这是否代表同一条业务规则，还是两个独立规则恰好写法相似？提取公共模块前要说明新函数/新模块如何兼顾各处的差异点，不能简单取"交集"而悄悄削弱某一边的校验。

### 数据源扇入冗余（不同函数读同一来源）

除了代码行层面的相似，还要主动检查**多个函数是否各自独立读取同一个底层来源**——例如都打开同一个 yaml、都跑同一个 `kubectl get`、都查同一张表、都打同一个 endpoint。这种冗余不在代码外观上（每个函数读取后的加工逻辑可能完全不同），而在 **IO 来源**上；普通的"场景是否重叠"判据看不见它，必须单独识别。

识别信号：
- 多个函数内出现相同的来源标识（相同路径 / 相同资源名 / 相同 endpoint / 相同表名）
- 这些函数只是"取的东西不同"，取的动作（打开文件、发起命令、建连查询）是重复的

合并方式：**抽成单个获取函数 + 按参数分发**，而不是把 N 个函数拼在一起。参数代表"要取什么"（字段名 / 资源类型 / 查询键），获取动作只发生一次。注意：
- 这会改变结构（引入间接层、可能统一同步/异步、调用点要改），属于"行为不变但结构变"的编辑，必须作为**提案**交用户确认、验证覆盖率不降。
- 各函数读取后**加工逻辑不同**的部分必须保留，不能因为"来源相同"就强行统一加工。
- 与"可合并冗余"共用同一验证纪律：合并后跑测试、对比基线。

### 抽象必要性检查（YAGNI / 防过度设计）

本技能不只被动去重，也会在看到 class 或较重的抽象时，主动问"这个抽象是否真的必要"。一个 class 即使没有任何重复，也可能是过度设计——本该用函数/闭包就能表达。用下面 5 问判断：

| 检查项 | 说明 |
|---|---|
| 是否持有跨方法共享的可变状态 | 若否，class 多半只是命名空间，函数/模块函数即可 |
| 是否真的有 ≥2 个差异化实现（多态/子类） | 若只有一种行为，多态价值为零 |
| 是否被 ≥2 个独立调用方以不同方式使用 | 若只被一处调用，封装收益有限 |
| 是否只是把一串步骤包起来、且仅被调用一次 | 是 → 函数/闭包更直白 |
| 能否用函数/闭包等价替代且不损失可读性 | 能 → 优先函数（Go 用包级函数、TS 用模块函数/箭头函数） |

5 问里若有 3 项以上指向"不需要 class" → 标记为**候选过度设计**，作为提案交给用户：建议塌缩为函数/闭包。注意：
- 这是**提案**，不是自动动作；是否塌缩由用户决定（见底线 1：结构简化需用户显式选择 + 调用点同步 + 验证）。
- 不要为了"显得简洁"而把确有状态/多态需求的 class 强行拍平——那条底线是"行为不变"，不是"一律拍平"。

### 第三步：分批执行

- 逐文件/逐模块处理，不做"一次性重写整个项目"式的大范围改动
- 大型项目（例如数万行）应主动提出分模块处理计划，而不是接受"全部一次性精简"的请求

### 第四步：改动即验证

每次改动后立刻跑测试，和基线对比。常用命令：

- Python：`pytest --cov=<模块> --cov-report=term-missing`
- Go：`go test ./... -cover`（需要报告时加 `-coverprofile=cover.out`）
- TS/JS：`jest --coverage` 或 `nyc npm test`

测试代码本身的改动，需要额外确认：改动前后的测试代码，针对同一份业务代码跑出的结果是否完全一致；如果精简导致覆盖率下降，必须明确说明降的是哪部分、能否接受。

**覆盖率下降怎么判定（重要）**：**提取公共代码**会导致一个必然现象——代码从 A 模块移到公共模块后，**A 模块的覆盖率数字下降、公共模块上升**。这是"覆盖率搬家"，不是"覆盖丢失"。此时的判定标准是：

- **总覆盖语句数不减少**；
- **原有边界值 / 异常路径的用例仍在跑且通过**。

不要只因单个模块的百分比下降就判定改动不可接受；也不要反过来，用"总覆盖率没降"掩盖某个模块真实失去了覆盖。**两种情形都要说清楚。**

### 第五步：变更留痕

每次说明具体改了什么、为什么改、依据是第二步里哪一类冗余判断。

## 伪冗余陷阱示例（跨语言）

两个高频形态（完整代码与合并风险见 `./references/examples.md`，按需加载、不内嵌）：

- **TypeScript 空值语义不同**：必填字段 `name` 直接 `.trim()`  vs 全链路 `?.` + `??` 兜底——合并要么给前者加不需要的兜底（掩盖上游 bug），要么让后者失去兜底（界面显示 `undefined`）。
- **Go error 处理语义不同**：`%w` wrap 供 `errors.Is` 判定 vs 有意吞掉"缓存未命中"——统一 error 处理会打断 `errors.Is` 链，或把"配置缺失"这种真故障当成"缓存未命中"静默吞掉。

两者都印证第二步的五项 checklist：任一检查项不同即判伪冗余，差异点交用户决定。

## 测试代码精简专属要求

- 精简前，先列出每个测试用例覆盖的场景/边界/断言点清单
- **覆盖场景完全相同的用例属于真冗余，可以合并**（例如两个都只是"正常值"输入、断言点相同的用例）；合并后的新用例必须包含原有全部断言点
- **场景/边界/断言点有差异的用例不可合并**——尤其不允许删除任何异常路径、边界值的测试（例如"负数抛异常"、"零值边界"不得与"正常值"用例合并）
- 输出精简前后的覆盖率对比（如果有覆盖率工具）
- 每次只处理一个测试文件，改完列出具体合并/删除了哪些用例及理由

## 测试框架适配：护栏而非发起

当用户要求把「扁平堆叠、各自独立的测试用例」改成测试框架推荐的结构（例如抽 fixture、用 parametrize / 参数化、抽公共 helper）时，这属于**改形式（form change）**，不是「删真冗余」。mini-code 在此处的定位是**安全护栏，不是发起人**：

- **当用户主动提出这类改造时**：可以作为护栏承接，但必须按「测试代码精简专属要求」逐项核对——改造前后每个用例覆盖的场景 / 边界 / 断言点清单完全一致，总覆盖语句数不减少，每个边界 / 异常用例仍有独立身份（parametrize 是把「多个不同用例」装进一个驱动，不是把「多个不同场景」合并成一个场景）。任一用例的场景 / 断言点会被合并掉 → 拒绝（适用底线 2 / 3）。
- **mini-code 不主动发起这类改造**：仅因「代码扁平、没用上框架的 parametrize / fixture」就提议把所有独立用例重写为框架风格，属于「为优雅而重构」，超出了「去冗余 / 精简」的本分。可以把它作为**可选建议**提一句，但绝不能当作「冗余待处理项」列进精简清单、更不能默改。

这与 A9+ 的区别：A9+ 是「场景与断言点完全相同的两个用例 → 删掉其一」；此处是「每个用例场景不同 → 只改表达形式、保留所有用例」。两者都不能合并不同场景，但动作方向相反（一个删、一个改形）。详见 `./docs/evaluation.md` 的 A11 类（本技能只引用，不内嵌）。

## 已知局限（如实告知用户，不要假装能解决）

- 本技能能保证 AI 在有信息时遵守流程（先分类、先列清单、不删测试），但**不能保证用户自己看得懂 AI 列出的冗余清单是否合理**。如果用户对这批代码本身理解有限（比如完全由 AI 生成、自己没通读过），最后的确认环节本身可能形同虚设，建议必要时找熟悉代码的人一起 review。
- 本技能依赖现有测试/样本作为"是否改坏"的检测手段，**如果测试本身存在覆盖盲区，精简后的行为漂移不会被发现**。技能会建议做覆盖率检查，但无法替用户判断这份测试是否真的覆盖了关键路径。
- 本技能现已扩展到主动识别「数据源扇入冗余」与「不必要的抽象（YAGNI）」。这意味着它可能在用户没明确要求时也提出结构简化提案——这类提案必须显式标记为"建议"、交用户决定，绝不默改；同时也要避免"为了显得简洁而过度拍平"真正需要抽象的 class。

## 验证方式（诚实声明）

本技能不附虚构测试集。历史上曾带有 `tests/` 场景目录，但其验证结果属于作者自评的模拟推演、并非独立盲测，已于 2026-08 重写时移除。如需重建评估夹具，建议先将本目录的完整快照保存到 `<repo>/backups/mini-code-<timestamp>/` 再动手。

本技能的正式评估设计见同目录 `./docs/evaluation.md`（与技能同处一个目录，但**不是运行时指令**——本文件只引用、不内嵌，技能实际执行时不需要读它）。采用**双轨制**：Track A 判断准确度（11 类 × 正/反向标注样本，假阳性率须为 0）、Track B 抗施压底线坚守（5 个对抗场景，底线坚守率须为 100%）。修改本文件后应按该文档重跑两轨，任一不达标即阻塞发布。

推荐的验证路径：

1. **真实代码试用**：在你真实项目的一小段代码上使用本技能——比任何虚构场景都有说服力。
2. **重大修改后盲测**：修改本文件后，在一个干净的会话里（不带修改过程的上下文）跑一遍 `./docs/evaluation.md` 的两轨样本——既查分类准不准（Track A），也查用户施压时底线守不守得住（Track B）。重点不是"回答得像不像"，而是：伪冗余有没有被误合、不该拆的 class 有没有被误拆、底线有没有被突破。
3. 每次修改本文件后，重新通读「不可突破的底线」一节与「数据源扇入冗余」「抽象必要性检查」两节，确认：五条底线的语义没有被弱化；主动提案仍被明确标记为"建议"且交用户决定，没有出现"默改结构"的倾向。

## 一个可直接使用的开场确认清单

在正式开始精简前，简要确认：
1. 代码状态（是否上线/被依赖——用静态分析实证，不只听用户说）
2. 是否有测试/样本
3. 本次精简的范围（哪个文件/模块，不是"全部"）
4. 是否包含测试代码本身的精简（如果是，走"测试代码精简专属要求"）
