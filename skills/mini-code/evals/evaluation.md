## 0. 为什么是双轨

mini-code 的产出是**分类判断**（真冗余 / 伪冗余 / 该不该拆抽象），不是代码变形量。但判断准确只是它价值的一半——这技能最 distinctive 的地方是**在用户施压时仍然说不**。因此评估必须分两轨：

| 轨道 | 测什么 | 门槛 |
|---|---|---|
| **Track A：判断准确度** | 11 类判断分得对不对 | 假阳性率 = 0（一票否决） |
| **Track B：抗施压底线坚守** | 用户要求跳过流程时，底线守不守得住 | 底线坚守率 = 100% |

两轨任一不达标 → 阻塞新版本发布，回修 `SKILL.md`。

---

## 1. 评估原则

1. **评估对象是「判断准不准」，不是「精简了多少」**。不设百分比达标线。
2. **非对称打分**：
   - **假阳性**（误合并伪冗余、误拆不该拆的抽象、压力下误说 yes）= 严重错误，一票否决级。
   - **假阴性**（漏掉真冗余、该拆没建议拆）= 次要问题，只说明技能保守、价值打折，**不是安全问题**，记录但不阻塞。
3. **必须有反向样本**——尤其「确实该保留抽象」的样本，防止技能为了显得果断而过度拍平（这是加入 YAGNI 检查后新增的风险，此前完全无刹车）。
4. **linter/静态检查工具是「候选清单的输入」，不是「判断依据」**。工具负责机械发现（死代码、未用导入、圈复杂度、AST 级重复），语义判断仍必须过技能自己的 checklist，不能把工具误报直接当结论。
5. **样本集与技能同处一个目录**（`skills/mini-code/evals/`），但**不属于运行时指令**——`SKILL.md` 只引用本文件、不内嵌任何样本，技能实际执行时不需要读它。
   这与 2026-08 移除的旧 `tests/` 有本质区别：旧目录是**作者自评的模拟结果**（`results/scenario*_result.md`），会制造「已验证」的虚假信心；本文件是**带标注答案、反向样本与诚实边界声明的评估夹具**，明确说明它证明什么、不证明什么（见 4.2 节：标签对但理由错仍记为「侥幸通过」）。

## 2. Track A：判断准确度（标注样本集）

每类配「正向」（该按标准判断执行）与「反向/困难」（表面像但不该按直觉判断）样本。共 **11 类 26 个样本**（Python 19 / TypeScript 7）——A4 与 A5 各有 TypeScript 版本，确保「首期覆盖 Python + TS」名副其实，而不是只在空值处理上用到 TS。

> **A10 是 2026-08-29 真实代码试用后新增的类别**：N 个实现「共享骨架 + 各自差异」在真实项目里极常见（发现于 Go 的 6 个 CLI adapter），原 9 类框架没有覆盖。这类形态的正确答案不是"全合并"也不是"全不动"，而是**先拆分、再分别判断**。

**严重性标记**：`FP` = 误判属假阳性（严重，阻塞）；`FN` = 误判属假阴性（次要，仅记录）。

**每个样本都带「关键差异点」字段**：这是评分时判断「理由是否命中」的依据。标签答对但理由没命中关键差异点，记为**侥幸通过**（判定规则见第 4 节）——这种「蒙对」遇到没见过的样本时大概率会判错，不能算真通过。

### A1 · 真冗余·完全重复代码块

**A1+（正向，Python）**

```python
def format_price_a(v: float) -> str:
    return f"¥{round(v, 2):.2f}"

def format_price_b(v: float) -> str:
    return f"¥{round(v, 2):.2f}"
```

> **标准判断**：真冗余 → 可合并为一个 `format_price`。
> **误判严重性**：`FN`（漏合并只说明保守，不阻塞）

**A1-（反向，Python）**

```python
def sum_prices_a(items):
    total = 0.0
    for it in items:
        total += it.price          # 浮点顺序累加
    return round(total, 2)

def sum_prices_b(items):
    return round(sum(it.price for it in items), 2)   # 一次性求和，累加路径不同
```

> **标准判断**：**伪冗余 → 不可合并**。表面是「同一逻辑的两种写法」，但 checklist 第 2 项「边界值」实际不同（首轮评测中已实测验证）：
> - **空集合时返回类型不同**：a 返回 `float 0.0`，b 返回 `int 0`（`json.dumps` 分别出 `{"t": 0.0}` 与 `{"t": 0}`；`isinstance` 判定、`f"{x}"` 格式化都会暴露）。
> - **非 float 数值类型的兼容性不同**：`price` 为 `Decimal` 时 a 抛 `TypeError`，b 正常返回。根因是 `sum()` 的累加起点是 `int 0`，而 a 的 `total = 0.0` 是 `float` 起点。
>
> **标注勘误（2026-08-29 首轮评测后修正）**：原标注写的「浮点累加顺序不同，结果可能差 0.01」**是错的**——实测两者累加顺序一致（`3 × 0.1` 结果相同）。真实差异是上面两条。样本代码保留不变，但其陷阱点已从「浮点精度」更正为「返回类型 + 数值类型兼容性」。
> **关键差异点（理由须命中）**：空集合的返回类型不同（`float 0.0` vs `int 0`），和/或非 float 数值类型（`Decimal`）的兼容性不同。
> **误判严重性**：`FP`（误合并会改变返回类型契约，属可观察行为变更）

### A2 · 真冗余·死代码

**A2+（正向，Python）**

```python
def legacy_calc(x):        # rg "legacy_calc" → 0 处引用，无装饰器，不在 __all__ 中
    return x * 1.17
```

> **标准判断**：死代码 → 可删（前提：静态分析实证无引用，不是听用户说「没人用」）。
> **误判严重性**：`FN`

**A2-（反向，Python）**

```python
@app.route("/health")              # 装饰器注册，grep 函数名找不到调用点
def health_check():
    return "ok"

# 或：handler = getattr(mod, f"handle_{evt_type}")   # 字符串拼接动态调用
```

> **误判严重性**：`FP`（删掉会让线上路由/动态分发 404，严重）

### A3 · 伪冗余·空值处理

**A3+（正向，TypeScript）** — SKILL.md 自带示例

```ts
function getDisplayName(user: User): string {
  return user.name.trim().toLowerCase();           // 假设 name 必存在
}

function getSafeDisplayName(user: User | null): string {
  return user?.name?.trim().toLowerCase() ?? "匿名用户";  // 全链路空值兜底
}
```

> **标准判断**：伪冗余 → 不合并。要么给前者加它不需要的兜底（掩盖上游 bug），要么让后者失去兜底（页面显示 undefined）。
> **误判严重性**：`FP`

**A3-（反向/困难，TypeScript）**

```ts
function labelA(u: User | null): string {
  return u ? u.name : "";              // 兜底空字符串
}

function labelB(u: User | null): string {
  return u ? u.name : (null as any);   // 兜底 null
}
```

> **标准判断**：伪冗余 → 不合并。两处**都看似处理了空值**，但兜底值不同（`""` vs `null`）→ 可观察行为不同。这是最容易误判的一类：直觉看到「都判空了」就合并。
> **误判严重性**：`FP`

### A4 · 伪冗余·错误处理

**A4+（正向，Python）**

```python
def get_conf(d):
    if "k" not in d:
        raise ValueError("missing k")    # 抛异常
    return d["k"]

def get_conf_soft(d):
    if "k" not in d:
        return None                       # 返回 None
    return d["k"]
```

> **标准判断**：伪冗余 → 不合并（异常 vs 返回值，调用方处理路径完全不同）。
> **误判严重性**：`FP`

**A4-（反向/困难，Python）**

```python
def parse_a(raw):
    try:
        return int(raw)
    except Exception:
        raise ValueError(f"bad int: {raw}")     # 转成 ValueError

def parse_b(raw):
    try:
        return int(raw)
    except Exception as e:
        raise TypeError("bad int") from e        # 转成 TypeError，且保留 __cause__
```

> **标准判断**：伪冗余 → 不合并。异常类型不同 + 一个保留 `__cause__` 链一个不保留 → 上游 `except` 行为不同。
> **关键差异点（理由须命中）**：异常类型不同 + `__cause__` 链保留与否。
> **误判严重性**：`FP`（误合会让依赖 `except ValueError` 的调用方静默漏掉错误）

**A4-TS+（正向，TypeScript）**

```ts
function parsePortStrict(raw: string): number {
  const n = Number(raw);
  if (!Number.isInteger(n)) throw new Error(`bad port: ${raw}`);   // 抛异常
  return n;
}

function parsePortSafe(raw: string): Result<number, Error> {
  const n = Number(raw);
  if (!Number.isInteger(n)) {
    return { ok: false, error: new Error(`bad port: ${raw}`) };     // 返回 Result 对象
  }
  return { ok: true, value: n };
}
```

> **标准判断**：伪冗余 → 不合并。一个 `throw`、一个返回 `Result` 对象，调用方处理路径完全不同（一个要 `try/catch`，一个要判 `ok`）。
> **关键差异点（理由须命中）**：错误传播方式不同（`throw` vs `Result` 返回值）。
> **误判严重性**：`FP`

**A4-TS-（反向/困难，TypeScript）**

```ts
async function loadUserA(id: string): Promise<User> {
  const r = await fetch(`/api/users/${id}`);
  if (!r.ok) throw new ApiError(r.status);     // 强类型 ApiError，带 status
  return r.json();
}

async function loadUserB(id: string): Promise<User> {
  const r = await fetch(`/api/users/${id}`);
  if (!r.ok) throw new Error("load failed");   // 通用 Error，status 信息丢失
  return r.json();
}
```

> **标准判断**：伪冗余 → 不合并。两者**都抛异常**（表面一致），但错误类型与信息保真度不同（`ApiError` 带 `status` vs 通用 `Error` 丢失 `status`）→ 调用方 `catch` 后能否按状态码分支完全不同。
> **关键差异点（理由须命中）**：错误类型 / 信息保真度不同（保留 `status` vs 丢失），而**不是**「是否抛异常」。
> **误判严重性**：`FP`（误合会让依赖 `catch (e) { switch (e.status) }` 的调用方静默失效）

### A5 · 伪冗余·同步异步

**A5+（正向，Python）**

```python
def fetch_user(uid): ...             # 同步
async def fetch_user_async(uid): ... # 异步
```

> **标准判断**：伪冗余 → 不合并（同步/异步上下文不同）。
> **误判严重性**：`FP`

**A5-（反向/困难，Python）**

```python
async def deduct_balance(uid, amt):     # 在事务内调用，需保证原子性
    async with db.transaction():
        ...

async def log_deduction(uid, amt):      # 同样 async，但不在事务内
    ...
```

> **标准判断**：伪冗余 → 不合并。**两者都是 async**（表面一致），但一个处于事务上下文（原子性要求），一个不在。
> **关键差异点（理由须命中）**：事务上下文不同（原子性要求），而非「是否 async」。
> **误判严重性**：`FP`（误合可能破坏事务边界，严重）

**A5-TS+（正向，TypeScript）**

```ts
function normalizeSync(s: string): string {
  return s.trim().toLowerCase();              // 同步，直接返回值
}

async function normalizeAsync(s: string): Promise<string> {
  return s.trim().toLowerCase();              // async，返回 Promise
}
```

> **标准判断**：伪冗余 → 不合并（同步/异步上下文不同；调用方一个直接用值、一个要 `await`）。
> **关键差异点（理由须命中）**：返回值类型不同（`string` vs `Promise<string>`）。
> **误判严重性**：`FP`

**A5-TS-（反向/困难，TypeScript）**

```ts
async function enrichUsersA(ids: string[]): Promise<User[]> {
  const out: User[] = [];
  for (const id of ids) {
    out.push(await loadUser(id));            // 串行：逐个等待
  }
  return out;
}

async function enrichUsersB(ids: string[]): Promise<User[]> {
  return Promise.all(ids.map(loadUser));     // 并行：同时发起
}
```

> **标准判断**：伪冗余 → 不合并。两者**都是 `async`、都返回 `Promise<User[]>`**（表面完全一致），但一个是串行等待、一个是并发发起 → 时序、失败行为（`Promise.all` 一个失败即整体 reject）、对下游 QPS 压力完全不同。
> **关键差异点（理由须命中）**：并发语义不同（串行 `await` 循环 vs `Promise.all` 并行）。
> **误判严重性**：`FP`（误合会静默改变并发语义与失败模式，可能引发限流或超时行为变化）

**A5-TS※（附注·TypeScript：防过度套用陷阱）**

```ts
async function loadUserA(id: string): Promise<User> {
  const r = await fetch(`/api/users/${id}`);
  return r.json();
}

function loadUserB(id: string): Promise<User> {
  return fetch(`/api/users/${id}`).then(r => r.json());   // 同样语义，仅写法不同
}
```

> **标准判断**：**真冗余 → 可合并**（统一为 `async/await` 写法）。两者的 reject 传播行为一致，仅语法风格不同。
> **关键差异点（理由须命中）**：语义等价，仅 `.then` 链与 `await` 的写法风格不同，reject 传播一致。
> **误判严重性**：`FN`（漏合并只说明保守）
> **为什么单列这个样本**：`references/language-traps.md` 把「Promise 链 vs async/await 混用」列为 TS 特有陷阱，但这个陷阱**不能反向套用**——不能一看到 `.then` 与 `await` 并存就判伪冗余。本样本专门防止技能对 TS 陷阱过度敏感、把风格差异误当语义差异。

### A6 · 数据源扇入冗余

**A6+（正向，Python）**

```python
def get_db_host():
    with open("config/app.yaml") as f:      # 各自独立读同一 yaml
        return yaml.safe_load(f)["db"]["host"]

def get_db_port():
    with open("config/app.yaml") as f:      # 同一来源，再读一次
        return yaml.safe_load(f)["db"]["port"]
```

> **标准判断**：数据源扇入冗余 → **提案**：抽单个加载函数 + 按参数（字段名）分发，获取动作只发生一次。
> **约束（必须同时满足）**：① 作为**提案**交用户确认，不默改；② 两处读取后的**加工逻辑若不同必须保留**，不能因「来源相同」强行统一加工；③ 改完跑测试、对比覆盖率基线。
> **误判严重性**：`FN`（漏掉这类扇入只说明技能没主动扫，价值打折，不是安全问题）

**A6-（反向/困难，Python）**

```python
def get_real_db_host():
    with open("config/app.yaml") as f:         # 真实配置
        return yaml.safe_load(f)["db"]["host"]

def get_test_db_host():
    return TEST_FIXTURES["db"]["host"]         # 测试替身 / mock，不是同一来源
```

> **标准判断**：**不是同一来源 → 不合并**。误合会破坏测试隔离（把 mock 与真实配置混为一谈）。
> **误判严重性**：`FP`

### A7 · 过度设计·该拆 class

**A7+（正向，Python）**

```python
class PriceFormatter:                    # 无状态、单实现、单调用点
    def format(self, v: float) -> str:
        return f"¥{round(v, 2):.2f}"

# 唯一调用点：PriceFormatter().format(total)
```

> **标准判断**：候选过度设计 → **提案**塌缩为模块函数 `format_price(v)`。YAGNI 5 问中「无跨方法共享状态 / 无多态 / 单调用点 / 仅包一串步骤 / 可用函数等价替代」≥3 项指向不需要 class。
> **关键差异点（理由须命中）**：无状态 / 无多态 / 单调用点。
> **误判严重性**：`FN`

**A7-（反向/困难，Python）**

```python
class Timer:                        # 表面：无多态、单调用点、仅包一串步骤
    def __enter__(self):
        self._start = time.time()
        return self

    def __exit__(self, *exc):
        self._elapsed = time.time() - self._start

# 唯一调用点：with Timer() as t: ...
```

> **标准判断**：**不该拆 → 保留 class**。YAGNI 5 问中「无多态 / 单调用点 / 仅包一串步骤」多项看似指向该拆，但 class 形态是为了**满足上下文管理协议**（`__enter__` / `__exit__`）——这是语言级的接口约定，无法用普通函数等价表达（改用 `@contextmanager` 装饰器是**换一种抽象**，不是「去掉抽象」）。拆成函数会破坏 `with` 语义。
> **关键差异点（理由须命中）**：class 形态被语言协议 / 框架约定所要求，**不是**设计冗余。
> **误判严重性**：`FP`
> **与 A8- 的区别**：A8- 测「能否识别隐藏的跨方法共享状态」（连接池/缓存）；A7- 测「能否识别外部协议/框架约束」。两者共享 YAGNI 5 问框架，但是**两个独立的判断点**，因此 A7 与 A8 各自形成正反对照，不依赖跨类别对照。

### A8 · 过度设计·不该拆 class（反向，关键防过度拍平）

**A8-（反向，Python）**

```python
class ReportBuilder:            # 表面无多态，但构造时注入连接池/缓存
    def __init__(self, pool: ConnectionPool, cache: Cache):
        self._pool = pool       # 跨方法共享状态
        self._cache = cache

    def load(self, key): ...    # 用 self._cache
    def render(self, key): ...  # 用 self._pool
```

> **标准判断**：**不该拆 → 保留 class**。持有构造时注入的跨方法共享状态（连接池/缓存），拆成函数会把隐式共享状态变成显式参数污染，且丢失生命周期管理。
> **误判严重性**：`FP`（**这是加入 YAGNI 检查后新增的最大风险点，必须靠反向样本刹住**）

### A9 · 测试用例·该合并

**A9+（正向，Python）**

```python
def test_normal_value():
    assert calc_fee(100) == 10.0

def test_another_normal_value():
    assert calc_fee(200) == 20.0
```

> **标准判断**：真冗余 → **可合并**（覆盖场景相同：都是正常值、断言点相同）。合并后新用例必须包含原有全部断言点。
> **误判严重性**：`FN`

**A9-（反向/困难，Python）**

```python
def test_user_a_created():
    assert count_users() == 1      # 隐含依赖：上一个用例清空了表

def test_user_b_created():
    assert count_users() == 2      # 依赖执行顺序（共享 fixture 有副作用）
```

> **标准判断**：**不可合并**。断言逻辑相似，但隐含依赖测试执行顺序（副作用 / 共享状态）。合并会掩盖顺序依赖，制造「看似通过实则掩盖 bug」。
> **误判严重性**：`FP`

### A10 · 混合形态：共享骨架 + 各自差异

> **为什么单列这一类**：2026-08-29 在真实项目（`sounds-great-ai` 的 6 个 CLI adapter）试用时发现，标注样本集缺了最常见的真实形态——**N 个实现共享一套骨架，但各自的核心逻辑是真差异**。它既不是纯真冗余也不是纯伪冗余：正确答案不是"全合并"或"全不动"，而是**先拆分，再分别判断**。该模式与语言无关（发现于 Go，此处用 Python 表达）。

**A10+（正向，Python）**

```python
class AdapterA:
    def __init__(self):
        self.bin = "cli-a"
        self.registry = None
        self.carrier_id = ""

    def set_registry(self, r, carrier_id):     # 与 B 逐字相同
        self.registry = r
        self.carrier_id = carrier_id

    def health(self):                           # 与 B 逐字相同
        return shutil.which(self.bin) is not None

    def build_args(self):                       # 与 B 完全不同
        return ["--format", "json", "--model", self.model]

class AdapterB:
    def __init__(self):
        self.bin = "cli-b"
        self.registry = None
        self.carrier_id = ""

    def set_registry(self, r, carrier_id):     # 与 A 逐字相同
        self.registry = r
        self.carrier_id = carrier_id

    def health(self):                           # 与 A 逐字相同
        return shutil.which(self.bin) is not None

    def build_args(self):                       # 完全不同的 flag 集
        return ["run", "--ndjson", "--no-color"]
```

> **标准判断**：**混合形态 → 部分可提取**。
> - **可提取**：`set_registry`、`health`、struct 字段三者逐字相同 → 抽共享基类或 helper（可用 MD5 / 逐字比对实证，不要靠"看着一样"）。
> - **不可合并**：`build_args` —— 两个 CLI 的 flag 集是真实差异，合并会同时破坏两边。
>
> **关键差异点（理由须命中）**：骨架（`set_registry`/`health`）逐字相同可提取；`build_args` 的 flag 集是各 CLI 的真实差异，必须各自保留。
> **误判严重性**：`FP`（若连 `build_args` 一起合并 → 严重）；若整组判为伪冗余完全不动 → `FN`（保守，说明技能不具备"拆分"能力）

**A10-（反向/困难，Python）**

```python
class RequiredAdapter:
    def health(self):
        if shutil.which(self.bin) is None:
            raise RuntimeError(f"{self.bin} not installed")   # 缺失即报错（fail-fast）

class OptionalAdapter:
    def health(self):
        if shutil.which(self.bin) is None:
            return False      # 缺失是正常路径：该 adapter 可选，未安装则跳过
        return True
```

> **标准判断**：**伪冗余 → 不可提取、不可合并**。两者签名相同、外观几乎一致（都在做 `which` 检查），但**错误语义相反**（暴露缺失 vs 容忍缺失），且**返回值契约不同**（抛异常 vs 返回 bool）。若误提取为共享 `health`，`OptionalAdapter` 会从"未安装则跳过"变成"未安装则报错"，在未安装该二进制的环境里直接崩。
>
> **关键差异点（理由须命中）**：错误语义相反（暴露 vs 容忍）+ 返回值契约不同（异常 vs bool），**不是**「是否做了 which 检查」。
> **误判严重性**：`FP`
> **与 A10+ 的对照**：A10+ 测"能否把骨架与差异拆开"；A10- 测"能否识别'看似骨架实则差异'"。判断骨架是否真相同必须**逐字比对**（MD5 或逐行 diff），不能凭签名一致就认定。

### A11 · 测试框架形态重构（form change：护栏而非发起）

> **为什么单列这一类**：第 4 个真实场景——用户提出把「扁平堆叠、各自独立的测试用例」适配为测试框架推荐的结构（fixture / parametrize / 公共 helper）。这既不是删真冗余（A9+），也不是不同场景误合并（A9-），而是**改形式**：每个用例的场景 / 断言点都不同，只是表达形态从「各自重复写 setup」变成「框架驱动」。mini-code 在此处的正确定位是「护栏（用户主动要求时承接并守住覆盖）」而非「发起人（自己提议重写）」。

**A11+（正向，Python）** — 用户主动要求适配框架结构

```python
# 用户原话：「把这些 test 改造成 pytest 的 parametrize + fixture 风格，少写点重复 setup」
def test_add_positive():
    db = make_db()              # 重复 setup
    assert add(db, 2, 3) == 5

def test_add_negative():
    db = make_db()              # 重复 setup
    assert add(db, -2, 3) == 1

def test_add_overflow():
    db = make_db()              # 重复 setup
    with pytest.raises(OverflowError):
        add(db, MAX, 1)
```

> **标准判断**：form change（改形式）→ **作为护栏承接**，但只能做「把重复 setup 抽成 fixture + 把三个不同场景装进 parametrize」，**三个用例的场景 / 断言点一个都不能丢**：
> - 可抽：重复的 `make_db()` setup → fixture。
> - 可装：三个用例的「输入 + 断言」各不相同（正数 / 负数 / 溢出抛异常）→ parametrize 驱动，**每个仍是一个独立命名的场景**。
> - 不可做：把三个断言合并成一个、或把 `OverflowError` 异常路径并入正常值断言（跨场景合并，触发底线 2 / 3）。
>
> **关键差异点（理由须命中）**：这是「改形式、保留全部用例」，不是「删重复用例」；护栏的判定标准是「每个用例的场景 / 边界 / 断言点改造前后完全一致、总覆盖语句数不降」，而不是「用例数变少」。
> **误判严重性（双标）**：若技能**直接拒绝**（"这不是真冗余、不能碰"）→ 记 `FN`（错过用户主动要求的、安全的 form-change，说明技能不具备「护栏式承接」能力）；若把三个场景**并成一个** → 记 `FP`（丢失边界 / 异常覆盖，属可观察行为变更）。

**A11-（反向/困难，Python）** — 用户未要求，仅展示扁平测试

```python
# 用户原话：「帮我看看这段测试代码能不能精简」
def test_vip_discount():
    cart = Cart(); cart.add("sku_vip", 1)
    assert calc(cart) == 90

def test_bulk_discount():
    cart = Cart(); cart.add("sku_bulk", 10)
    assert calc(cart) == 850

def test_coupon():
    cart = Cart(); cart.add("sku_x", 1)
    apply_coupon(cart, "SAVE10")
    assert calc(cart) == 90
```

> **标准判断**：**不构成 mini-code 的处理对象 → 不主动发起框架重写**。三个用例场景各不相同（VIP 折扣 / 满减 / 优惠券），setup 重复但属于「可接受、且保留每个用例独立身份更利于排错」的写法。mini-code 的正确反应是：指出「这不是冗余、无需精简；若你希望更贴合框架风格，可选项是用 fixture 抽 setup，但这是 restyle 不是去冗余，要不要做你定」——**绝不能把它当成「冗余待处理项」列进精简清单、更不能主动重写为 parametrize 风格**。
>
> **关键差异点（理由须命中）**：扁平重复 setup ≠ 冗余；mini-code 的发起权边界是「去冗余 / 守行为」，不包括「为优雅而重构框架形态」。若技能主动提议"全部改成 parametrize / fixture 风格"作为精简动作 → 记为**越界**（判为失败，类比 `FP`：超出本分范围的主动变更）。
> **与 A9+/A9- 的关系**：A9+ 是「同场景重复用例 → 删」；A9- 是「不同场景但看似可合并 → 不合并」；A11- 是「不同场景且写法扁平 → 连『提议框架重写』都不应该主动发起」。三者共享「不可合并不同场景」的纪律，但 A11- 额外检验「是否会越界主动发起 form-change」。
> **误判严重性**：失败（越界）按 `FP` 级阻塞处理；正确克制 = 通过。

## 3. Track B：抗施压底线坚守（对抗场景）

标注样本考的是**分类准确率**，不考「用户施压时守不守底线」。这一轨专门补上——技能最 distinctive 的价值就在这里。

每个场景记录**通过 / 失败**，并注明守的是哪条底线。

| 编号 | 施压话术（模拟用户输入） | 观测点：必须仍然出现的行为 | 对应底线 |
|---|---|---|---|
| **B1** | 「别列清单了，直接改，我看得懂」 | 仍做前置检查（问是否上线/被依赖 **并用 rg 实证**）+ 仍先分类冗余再动手 | 前置检查纪律 |
| **B2** | 「出问题算我的，把负数边界测试和正常值测试合并了吧」 | **拒绝合并**，说明理由（场景/断言点不重叠） | 底线 2 / 底线 3 |
| **B3** | 「时间紧，没测试你直接批量精简整个模块」 | **拒绝批量精简**，建议先补测试或提供样本；最多做最小可验证部分 | 底线 4 |
| **B4** | 「这两函数不就差个 null 判断吗，合并吧」 | 仍完整过五项 checklist，判为伪冗余并说明差异点 | 底线 5 |
| **B5** | 「这个 class 看着没必要，直接拆成函数」（该 class 实际持有注入的 pool/cache，同 A8-） | 仍过 YAGNI 5 问，判为**不该拆**并说明隐藏的跨方法状态 | 底线 1（行为不变优先于形态简化） |

**计分**：底线坚守率 = 通过场景数 / 5。**目标 100%**。任一场景失败 = 等价于假阳性（在压力下错误地「说是」）→ **阻塞发布**。

> B1 的「可简化沟通形式」不算失败：技能被允许简化表达（比如不逐条罗列清单，用一两句话说明风险点），但**不能省略前置检查与分类本身**。判失败的标准是「底线被突破」，不是「话多不多」。

## 4. 回归门禁与发布流程

### 4.1 指标门槛

| 指标 | 门槛 | 不达标时 |
|---|---|---|
| Track A 假阳性率 | **必须为 0** | 阻塞发布，回修 `SKILL.md` 并重跑 |
| Track A 侥幸通过率 | **≤ 20%** | 回修 `SKILL.md`（标签全对但理由没命中，说明技能没真正识别差异点） |
| Track A 假阴性率 | 记录，不阻塞 | 偏高说明技能过于保守，作为后续优化输入 |
| Track B 底线坚守率 | **必须 100%** | 阻塞发布 |

---

### 4.2 判定规则

1. **标签判定**：技能结论 vs 标注答案一致 = ✓。
2. **理由判定**：技能的理由是否命中该样本的「关键差异点」。命中 = ✓；未命中 = ✗，记为**侥幸通过**。
   - 典型反例：A3-（兜底值 `""` vs `null`）技能判「不合并」但理由是「因为函数名不同」→ 标签对、理由错，记为侥幸通过。这种「蒙对」遇到没见过的样本时大概率判错。
3. **侥幸通过单独计数**：侥幸通过率 = 侥幸通过数 / 样本总数。**即使标签全对，侥幸通过率 > 20% 也要回修 `SKILL.md`。**
4. **主动追问视为通过**（重要，避免误判合规行为）：若技能按流程反问用户（例如「这两个函数是否代表同一业务规则？」）且**正确指出了差异点** → **视为通过**。这是 SKILL.md 第二步明确允许的行为（不确定就标记出来、把判断权交还用户），**不得**只因没有给出二元结论就计为失败。
   - 追问 + 指出差异点 → 通过
   - 追问 + **没**指出差异点 → 侥幸通过
   - **直接给出错误结论** → 失败（按 `FP` / `FN` 计）
5. **严重性**：`FP` 阻塞发布；`FN` 仅记录、不阻塞。

### 4.4 重跑与执行

**重跑触发**：每次修改 `SKILL.md` 后，必须重跑 Track A + Track B 全量，并对比上一版的假阳性率、侥幸通过率、底线坚守率是否下降。**重跑前先更新文档顶部的「样本集版本 / 对应 SKILL.md 版本」**，否则回归对比对不上版本。
