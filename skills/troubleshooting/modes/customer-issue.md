# 场景③：客户问题（被动推理，禁止连接任何环境）

## 前提
通常只有客户给的报错文本和版本号。**不执行 connect.py、logs.py 等任何环境脚本。**

## 流程
1. 提取信息：组件名（可能是别名）、版本号（v0.0.1 / 0.0.1 均可）、报错原文、发生时间、操作步骤。
2. 缺组件名：根据报错里的类名、服务名、日志前缀推断候选组件，**说明依据并让用户确认**，不得直接替用户选。
3. 缺版本号：必须向用户索要，不得用最新版本代替。
4. 切换到对应版本：
   `scripts/resolve_version.py <组件> <版本>`
   成功输出包含 `path=...`（位于 `config.worktree.workdir` 下的只读 worktree）。后续读代码都在该 path 下。
   多个组件时逐个解析，结论中标明每条对应哪个组件的哪个 tag。
5. 在该 path 中按报错线索定位代码，还原调用路径，推导触发条件。
6. 需要对比相邻版本（如判断问题是否已修复）：再解析另一个版本，用 `git diff <tagA> <tagB> -- <文件>`。

## 结论输出格式
- **定位结果**：组件 / tag / 文件:行号
- **已证实**：代码中明确存在的逻辑、与报错文本吻合的位置
- **推测**：依赖客户环境或配置的部分，并说明还缺什么信息才能证实
- **建议向客户索取的信息**：具体到文件、命令或日志片段
- **是否已在后续版本修复**：有对比依据才写，否则写"未核实"

## 约束
- NOT_FOUND 时不得用 nearby 里的相近版本替换，带后缀的版本（-rc1、-hotfix）视为独立版本。
- 报错信息不足以定位时，明确说"无法定位"并列出需要的信息，不要编造看似合理的根因。
