# Project-to-Interview Experiences — 项目源码 → 面试备战手册

> **上一步**: 无（由用户请求触发）| **下一步**: 无（面试手册生成完成后通知）

## 价值门禁

这不是"读代码写文档"——是**主观防御型与表达转化型 Skill**，将代码库转化为**可口述、防砸盘、带量化数据**的面试备战讲稿。
与 OpenWiki（客观描述代码怎么写）不同，本 Skill 关注**"为什么这么做、面临什么挑战、你做了什么"**，终极目标是帮助求职者形成经得起深度追问的面试表达。

所有技术结论必须附带真实源码文件路径与行号（如 `src/cache/multilevel.go:42-85`），严禁凭空构想。量化收益无法从代码确认时，自动预留占位符 `[待补充: 量化数据]` 并提示用户补充。

## 核心视角对照

| 维度       | OpenWiki（架构分析）      | Project-to-Interview（本 Skill） |
| -------- | ------------------- | ----------------------------- |
| **核心视角** | 客观视角："代码怎么写的？逻辑在哪？" | 表达视角："为什么这么做？面临什么挑战？你做了什么？"   |
| **关注重点** | 模块依赖、调用链、静态架构图      | 选型对比、性能调优、踩坑排查、极限场景防守         |
| **终极目标** | 帮助开发者快速读懂代码库        | 帮助求职者形成可口述、防砸盘、带量化数据的面试讲稿     |

## Core Execution Protocol (Workflow)

按以下严格的阶段性流程递进分析，不得颠倒顺序：

### Phase 1: 项目侦察与技术栈识别 (Reconnaissance)

1. 扫描项目根目录，识别技术栈（语言、框架、中间件、数据库）。
2. 解析构建文件（pom.xml / package.json / go.mod / build.gradle / requirements.txt 等），提取依赖清单与版本。
3. 解析配置文件（application.yml / .env / docker-compose.yml / k8s manifests），提取真实生产参数（线程池、连接池、JVM、超时、重试等）。
4. 构建项目模块概览，确定核心业务模块与基础设施模块的边界。
5. 识别项目所处领域（电商/金融/日志/IM 等），为后续话术提供业务上下文。

### Phase 2: 亮点挖掘与 STAR 案例提炼 (Highlight Mining)

从源码与 Git 历史中逆向检索高含金量技术亮点，转化为 STAR 结构。

1. **源码模式扫描**：识别高阶设计模式与工程实践：
   - 分布式锁 / 分布式事务 / 幂等性保障
   - 线程池异步化 / 反应式编程 / 批处理优化
   - 多级缓存 / 读写分离 / 分库分表
   - 限流降级 / 熔断 / 灰度发布
   - 消息队列异步解耦 / 延迟任务 / 死信处理
2. **Git 历史逆向**：扫描 Commit 历史，提取：
   - `fix:` / `bugfix:` → 踩坑排查案例
   - `perf:` / `optimize:` → 性能调优案例
   - `refactor:` → 架构演进案例
   - `feat:` + 性能/并发相关 → 高含金量功能亮点
3. **STAR 转换**：将每个亮点强行转化为：
   - **Situation**：业务背景与痛点（从代码上下文与 Git 历史推断）
   - **Task**：目标与指标（从配置/注释/Commit 提取，缺失则占位）
   - **Action**：核心方案与关键代码（附文件路径与行号）
   - **Result**：量化收益（从代码可确认则提取，否则 `[待补充: 量化数据]`）

### Phase 3: 防守矩阵构建 (Trade-offs & Alternatives)

为每个核心技术选型生成"为什么选 A 而不用 B"的对比话术。

1. 自动识别项目中的关键技术选型（如：Kafka vs RabbitMQ、Redis vs Memcached、同步 vs 异步、单体 vs 微服务）。
2. 对每项选型生成防守表格：

| 选型项  | 候选方案                        | 选择理由             | 放弃原因          | 防守话术                               |
| ---- | --------------------------- | ---------------- | ------------- | ---------------------------------- |
| 消息队列 | Kafka / RabbitMQ / RocketMQ | 高吞吐 + 持久化 + 水平扩展 | RabbitMQ 吞吐不足 | "业务峰值 QPS 10w+，Kafka 顺序写磁盘+零拷贝..." |

1. 防守话术必须结合项目真实场景（从配置/代码提取 QPS、数据量、延迟要求），不可泛泛而谈。

### Phase 4: 真实性验证与底层原理图谱 (Authenticity & Fundamentals)

为防止"假项目/背八股"被问懵，构建两套防守体系。

1. **底层原理图谱**：将项目用到的核心组件向上/向下映射到底层原理：

```
Kafka → 零拷贝 sendfile + 顺序写磁盘 + 页缓存
Redis → epoll 多路复用 + 单线程Reactor + 跳表
MySQL → B+tree 索引 + MVCC + redo/undo log
线程池 → 核心线程数公式 N_cpu × (1 + W/C) + 阻塞队列策略
```

2. **标准术语定义**：为项目中涉及的核心概念提供"一句话专业标准定义 + 项目上下文结合"：
   - 幂等性：`f(f(x)) = f(x)`——同一操作执行多次结果一致。本项目在订单创建接口通过 `Redis SETNX + DB 唯一索引` 双重保障幂等。
   - CAP 理论：分布式系统只能同时满足 C/A/P 中两个。本项目选择 CP（Zookeeper 注册服务），牺牲可用性换一致性。
2. **架构演进脉络**：推演项目从 V1.0 到当前版本的演进过程：
   - V1.0 单体架构 → V2.0 引入缓存/读写分离 → V3.0 异步化/微服务化
   - 每次演进标注：驱动因素（什么痛点）+ 技术方案 + 量化收益
3. **真实生产参数推演**：对线程池、连接池、JVM 等参数，执行 3 层抓取与推演：

```
[Tier 1: 配置文件解析 (YAML / Properties / Docker / K8s)]
                    │
                    ▼ (若存在占位符/未配置)
[Tier 2: 源码 AST 扫描 (对象构造与 Bean 实例化)]
                    │
                    ▼ (若使用默认值)
[Tier 3: 框架默认值兜底与面试合理性推演]
```

抓取到参数后生成**反向翻译话术**，例如 `corePoolSize = 16`：

- "核心线程数 16：基于 8 核 CPU 节点与 IO 密集型业务公式 `N_cpu` × (1 + W/C) 推演设定"
- "队列长度 200：基于接口 50ms 延迟与目标 QPS 推算，兼顾 GC 停顿与内存占用"

### Phase 5: 深度追问模拟 (Deep-Dive Simulator)

针对每个核心技术点，扮演严格面试官预演 3-5 个深度追问。

1. 对 Phase 2 提炼的每个亮点，生成追问链：
   - **L1 基础追问**：原理是什么？怎么用的？
   - **L2 边界追问**：极端场景怎么办？并发冲突如何处理？
   - **L3 深挖追问**：底层怎么实现的？有什么坑？
   - **L4 延伸追问**：如果要扩展/替换/优化，你怎么做？
   - **L5 质疑追问**：为什么不用 X 方案？你这个方案的缺点是什么？
2. 每个追问附标准应答卡片（含代码关联位置）：

```markdown
**追问**：缓存击穿怎么处理的？
**应答**：使用 Redis 互斥锁 + 逻辑过期双重方案。
- 互斥锁：`src/cache/lock.go:23` — SETNX 加锁，过期时间 3s
- 逻辑过期：`src/cache/logic_expire.go:45` — 异步刷新，不阻塞读
- 兜底：DB 查询限流 `src/db/ratelimit.go:12`
```

### Phase 6: 电梯演讲生成 (Elevator Pitch)

提供不同时长的口语表达文本，适配不同面试场景。

1. **30 秒简历摘要**：一句话概括项目价值与技术亮点（适合简历 bullet point）。
2. **2 分钟技术主干汇报**：项目背景 + 核心架构 + 个人贡献 + 量化成果（适合面试开场自我介绍）。
3. **架构大图口述逻辑**：用口语化语言描述架构图，让面试官"听懂一张图"（适合白板画图时口述）。

## Output Location

生成的面试手册存放到**项目根目录**下，路径规则：

```
<项目根>/docs/interview/<YYYYMMDD-interview>/
```

- **目录名格式**：`<YYYYMMDD-interview>`，如 `docs/interview/20260730-interview/`
- **多次生成**：同一天多次分析覆盖同一目录；不同日期生成各自独立目录。
- **目录结构**：

```
docs/interview/20260730-interview/
├── interview-handbook.md      # 面试备战手册（完整 6 模块）
├── star-cases.md              # STAR 案例集（独立速查）
├── deep-dive-qa.md            # 深度追问应答卡片集
└── elevator-pitch.md          # 电梯演讲文本（30s / 2min / 架构口述）
```

> 若项目根目录下 `docs/interview/` 不存在，自动创建。

## STAR 案例文档 Schema

每个 STAR 案例遵循以下结构：

```markdown
### STAR 案例：[亮点名称]

> **技术标签**：`分布式锁` `高并发` `Redis`
> **核心代码**：`src/lock/distributed.go:23-65`
> **Git 来源**：commit `a1b2c3d` — "feat: add distributed lock for inventory deduction"

#### Situation（背景与痛点）
- 业务场景：高并发秒杀场景，库存超卖风险
- 痛点：DB 行锁性能瓶颈，QPS 上不去

#### Task（目标与指标）
- 目标：库存扣减零超卖
- 指标：支撑 QPS 5000+，响应 < 50ms

#### Action（核心方案与关键代码）
1. Redis 分布式锁（SETNX + 过期时间）：`src/lock/redis.go:23`
2. 锁续期守护协程：`src/lock/renewal.go:45`
3. DB 唯一索引兜底：`src/inventory/deduct.go:67`

#### Result（量化收益）
- 超卖率：0（上线后零超卖）
- QPS：从 800 提升至 6000
- [待补充: 上线后故障率对比]
```

## Execution Constraints & Safeguards

| 约束                          | 说明                                                             |
| --------------------------- | -------------------------------------------------------------- |
| **Strict Source Grounding** | 所有技术结论必须附带真实文件路径与行号（如 `src/cache/multilevel.go:42-85`），严禁凭空构想。 |
| **Quantitative Honesty**    | 量化收益能从代码/配置确认则提取，无法确认时用 `[待补充: 量化数据]` 占位并提示用户补充，绝不编造数据。        |
| **Defensive Stance**        | 每个技术选型必须生成"为什么选 A 不选 B"的防守话术，每个亮点必须预演深度追问，确保面试时不被问懵。           |
| **Oral Expression**         | 所有内容必须转化为**口语化、可口述**的表达，而非书面技术文档。避免"如图所示"等无法口述的表述。             |
| **Parameter Authenticity**  | 线程池/连接池/JVM 等参数必须经 3 层抓取（配置文件 → 源码 AST → 框架默认值），并附推演依据。        |
| **Token Efficiency**        | 优先基于符号表和依赖关系进行全局分析；仅在撰写特定亮点细节时读取该文件完整源码。                       |
| **Noise Reduction**         | 忽略纯 UI 样式文件、自动生成代码、测试用例，将 Token 资源集中于核心业务逻辑与高阶设计模式。            |

## Common Mistakes

| 错误               | 后果                 | 修复                                                              |
| ---------------- | ------------------ | --------------------------------------------------------------- |
| 跳过 Phase 1 直接读源码 | 缺乏技术栈全局视角，选型防守话术空洞 | 先完成项目侦察，建立技术栈全景                                                 |
| 量化收益编造数据         | 面试被追问数据来源时穿帮       | 无法确认时用 `[待补充]` 占位，提示用户补充                                        |
| STAR 缺少代码行号      | 无法溯源验证，面试官质疑真实性    | 每个 Action 必须附 `文件路径:行号范围`                                       |
| 防守矩阵只写选了什么不写为什么  | 面试官追问"为什么不用 X"时哑火  | 每项选型必须写明放弃原因 + 防守话术                                             |
| 深度追问只预演 1-2 个    | 面试官第 3 个追问就问懵      | 每个亮点至少预演 3-5 个深度追问（L1-L5）                                       |
| 底层原理泛泛而谈         | 被问"底层怎么实现的"露馅      | 映射到具体 OS/网络/DB 机制（如 sendfile/epoll/B+tree）                         |
| 参数不附推演依据         | "为什么线程数设 16"答不上    | 3 层抓取 + 反向翻译话术（公式 + 业务推算）                                       |
| 电梯演讲写成书面语        | 面试口述时像在念稿          | 转化为口语化表达，可自然说出的句子                                               |
| 术语定义脱离项目上下文      | "幂等性"背完不知道项目里怎么用的  | 一句话标准定义 + 项目中具体落地方式                                             |
| 架构演进只写结果不写驱动因素   | "为什么要从单体拆微服务"答不上   | 每次演进标注驱动痛点 + 技术方案 + 收益                                          |
| 文档输出到任意位置        | 文档散落难找             | 严格按 Output Location 规则写入 `docs/interview/<YYYYMMDD-interview>/` |
| 一次性读取所有文件源码      | Token 溢出           | 符号表优先，按需读取细节                                                    |
