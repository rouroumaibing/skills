# How Code Chain Work — 功能链路精确梳理协议

> **上一步**: 无（由用户请求或任务本身触发）| **下一步**: 无（计划性修改：报告经确认后进入修改；诊断模式：结论经确认后进入修复）

## 这个技能解决什么问题

大代码库里，模型天然倾向于"看到相关代码就直接改"或"看起来像原因就直接给结论"，导致五类失败：

1. **漏掉间接受影响的调用点**（改动 gap）——改了 A，B 处炸了却不知道 B 也依赖 A。
2. **对反射 / 依赖注入 / 事件总线等间接调用瞎猜**，给出"看似确定、实则无依据"的结论。
3. **只验证「语法对不对、能不能跑」，不验证「语义对不对、副作用变没变」**。
4. **排查问题时，给出「听起来合理」但没有实际复现或证据支撑的根因**（诊断场景特有，见文末「诊断模式」）。
5. **漏掉非调用依赖**——只顺着调用图追，却没意识到某处还依赖「这个符号从哪个模块导入」「这个资源路径相对源文件 / 工作目录」「这个对象字段的写入点与读取点是否一致」，结果改了符号来源、移动了文件、或在重构中改动了字段读写逻辑后，运行期找不到符号 / 文件、或字段被「只读不写」（有读取却无写入）而静默出错（迁移 / 重构高发）。

本技能把"改代码"拆成"先梳理、后动手"两段，把"排查问题"拆成"先复现/取证、后下结论"两段，强制在动手/下结论前把**调用关系 + 不确定点 + 证据**显式写出来。它不假设你有静态分析工具——最低要求只是"读文件 + 文本搜索"，任何 agent 环境都能保证这两件事。环境里若有更强工具（见附录 D），用以降低"未验证"比例，但**不能因为工具不够就降低标注标准去凑一个看起来完整的假象**。

## 四条铁律（不可跳过）

1. **先梳理，后动手**：任何跨函数 / 跨文件的修改，必须先走完 Phase 1 产出调用链报告，未经确认不得进入 Phase 3。
2. **剪枝必须留痕，且覆盖必须完整**：本层的每一个直接子调用，都必须归入「展开 / 剪枝（含理由）/ 标注未验证（含理由）」三者之一，不允许既不展开、也不写理由地悄悄消失。
3. **不确定就说不确定**：遇到无法用静态读代码确认的调用关系**或非调用依赖**（命中附录 A「气味清单」，含符号导入来源、资源位置 / 路径绑定、对象字段读写数据流），必须显式标注为「未验证-动态」并给出验证建议，**禁止用推测冒充确认结论，更禁止把"未确认来源的符号 / 路径 / 字段读写"直接标成「确认」**。
4. **诊断类任务，结论必须有证据**：排查"为什么会出问题"时，能复现就必须复现后再下结论；不能复现，必须显式声明"基于静态分析推断，未经运行验证"，不能把推断包装成确定的根因。

> 违反第 3 / 4 条比"漏查一个调用点"更危险——前者是诚实的信息缺口，后者是伪装成完整结论的信息缺口，会误导后续所有决策。

## 启用判定（比例原则）

不是所有任务都值得走完整协议。按下表决定启用哪一套：

| 场景                                           | 启用方式                        |
| -------------------------------------------- | --------------------------- |
| 跨文件 / 跨模块修改                                  | **完整协议（Phase 0-4）**         |
| 被多处调用的函数（尤其公共 util、interface 方法）             | **完整协议**                    |
| 重构、重命名导出符号、改返回值类型、移动文件 / 改目录结构                | **完整协议**                    |
| **删除导出符号 / 公共方法 / 被其他处引用的函数**                | **完整协议**（删除是最高危场景：漏一个引用即运行期崩溃，须走删除专用核对） |
| **改动对象字段的写入 / 读取逻辑、字段重命名、移除 / 改动字段写入点**     | **完整协议**（字段数据流是调用图覆盖不到的依赖边；重构中「只读不写」是高频漏改源，须走 1.6c 字段数据流对账） |
| 追查一个功能入口到底影响哪些地方                             | **完整协议**                    |
| 排查「改了 A 却在 B 出问题」/ 报错定位 / bug 复现 / 为什么会出这个问题 | **诊断模式**（见文末，不套用 Phase 0-4） |
| 单函数内、唯一调用方、纯局部变量重命名                          | 可轻量跳过                       |
| 确认无副作用的 1–2 行改动                              | 可轻量跳过                       |

**不确定该不该用 → 用。** 误用本技能的成本 << 漏用本技能的成本。

## 工作流程（计划性修改场景）

### Phase 0：定义任务边界（约 30 秒，不能省）

开始搜索前，先用一句话写清：

- **本次任务关心的行为是什么**（例：「确认修改 `calcDiscount()` 的返回值类型不会破坏调用方逻辑」；若为删除，写明「删除 `oldMethod()`，确认所有引用点已合理改写」；若改字段，写明「改动 `Order.total` 的写入逻辑，确认所有读取方已同步」）。
- **范围边界**：只看本仓库 / 本服务，还是要跨服务？第三方库源码要不要展开？**涉及移动文件 / 改目录时，必须显式把"资源路径耦合"列入关心范围；涉及改字段读写逻辑时，必须显式把"字段数据流"列入关心范围。**
- **正确性要求等级**：核心支付 / 权限类逻辑 → 要求「未验证」点数量趋近于 0；边缘功能 → 可接受合理浅层梳理。

这一步输出仅一两行，但决定后面"该展开到多深"的判断基准，不能靠临场感觉。

### Phase 1：梳理（只产出报告，不改代码）

**1.1 定位入口**  
用 Grep / Glob / LSP 定位目标函数、路由、事件处理器的**定义位置**（不是调用位置）。确认是唯一定义还是存在同名重载 / 多态实现，若有多个候选，全部记录。

**位置引用精度**：不同符号必须各自标注独立的定义行号，禁止把多个符号合并引用同一个行号。若某个结论落在符号内部的特定逻辑点（而非整个符号），用「符号定义起始行 + 段内说明」标注，例如 `file:1006 (_run_replace_pty 内，第 3 个分支)`；不强求把每一行代码都拆成单独引用。

**1.2 正向追踪（入口内部调用了什么）**  
分两步走，不要把"找齐"和"判断"混在一起：

- **第一步：机械枚举**。先用 grep / AST / LSP 把当前函数体内的**全部直接子调用**列出来，得到一个数量确定的清单（N 个）。这一步不做相关性判断，只做穷举，目的是防止"没读到"这种最隐蔽的遗漏。
- **第二步：逐一分类**。对枚举出的每一个子调用，归入以下三类之一，**总数必须等于第一步的 N，缺一不可**：
  - **展开**：判断为影响 Phase 0 关心的行为 → 展开看该函数定义，递归本步骤。
  - **剪枝**：判断为无关（日志、埋点、纯格式化等）→ 记入剪枝日志，写明理由，不展开。
  - **标注未验证**：命中附录 A 任一「气味」，无法静态判断真实路径 → 转入 1.4 处理。

不强制严格按"层"顺序广度优先展开——按相关性优先递归即可，但**每一层内部的直接子调用覆盖必须完整**（铁律 2）。

**1.3 反向追踪（谁在调用这个入口 / 这个函数）**  
搜索函数名 / 方法名在全仓库的所有引用点，至少覆盖以下变体，避免漏报：完整名 + 常见变体（驼峰 / 下划线互转、类名+方法名组合、可能的别名 import）。优先用 **LSP 的 find references**（符号级，优于字符串 grep）；无 LSP 时退回 grep 并显式声明"已用 grep，可能存在漏报"。

对每个调用点，确认传参方式、是否依赖返回值的具体类型 / 结构、是否依赖副作用，并判断是否受本次修改影响。

> **聚合入口场景**：当反向追踪发现是 N 个并行用例共享同一个编排方法（典型如表驱动测试、插件注册表）时，不必逐条重复记录，改用一句备注起头：「以下 N 条共享 XX 编排方法，仅列差异」，随后表格聚焦「调用方用例 / 传参差异 / 受影响范围 / 置信度」即可。这只是记录格式的轻量调整，不是独立的新模板。

> **删除场景专用要求**：当本次任务是**删除**某个方法 / 函数 / 符号时，1.3 反向追踪必须升级为**删除核对**——对每一个将被删除的符号名，做**全库精确匹配检索**（非子串匹配，避免 `parse` 误伤 `parseJSON` 这类无关符号），输出**完整的命中清单**（含 `file:行号`、命中上下文摘要），并显式提示「以下命中点需逐一核对：是否已合理改写、是否仍保持原语意」。禁止只找到主调用方就认为"已查全"；命名变体（驼峰 / 下划线互转、别名 import、类名+方法名组合）必须覆盖。该清单是 Phase 2 人工关卡与 Phase 4 机械核对的输入。

**1.4 间接调用处理（命中气味清单时）**  
不要猜。列出**全部候选实现 / 处理器**；若候选数 > 1 且无法从代码本身收敛到唯一执行路径，标记为「未验证-动态」，写清需要运行时验证还是需要人工确认业务分支。**绝不写「应该是走 XX 这个实现」这种无证据支撑的确定性表述。**

**1.5 梳理中发现的既有问题（若有）**  
梳理过程中，若在**本次追踪链路内**发现与本次任务或相邻正确性相关的既有问题（不是顺手做的代码质量审计，无关的代码洁癖不记录），单独记一笔：问题描述 / 证据位置 / 影响面 / 建议处理时机。**梳理阶段发现问题不代表可以顺手修——是否处理、何时处理，留给 Phase 2 由人工决定**，这样能保证"报告先于改动可 diff"。

**1.6 非调用依赖扫描（命中即进附录 A 气味清单）**  
调用图只覆盖"函数调函数"，但真实改动还会牵动**非调用依赖**——这正是 import 来源、资源路径、对象字段数据流三类遗漏的高发区。对当前追踪到的每个符号、每个资源访问、每个被改动读写逻辑的字段，逐一确认：

- **符号导入来源**：函数体内引用的、非本文件定义 / 非局部 / 非标准库的符号，是否能在代码中定位到唯一的 import / 模块来源？无法定位（命中附录 A「符号来源 / 导入绑定」气味）→ 标「未验证-动态」，写清需要 LSP 解析还是人工确认。
- **资源位置耦合**：是否基于「源文件所在位置 / 模块目录」或「当前工作目录（CWD）」来构造文件路径？这类对"移动文件 / 改 CWD / 打包"敏感，静态无法确定运行期实际路径 → 标「未验证-动态」，建议目标环境运行或补测试验证。
- **字段数据流（对象字段的写 / 读对账）**：本次修改**触及的核心对象、或被改动其读写逻辑的字段**，其效果经共享可变状态传播，不在调用栈里。须对每一个这样的字段，**全库精确搜索该字段名**（LSP find references 或精确匹配 grep，非子串），列出所有**写入点**与**消费点（读取点）**，并对账两个失败模式：
  - **只读不写（无写入点消费）**：存在读取点却找不到对应的写入点（如重构删掉了写入方、或字段本应由某处赋值却被遗漏）→ 标「未验证-动态」，写清需确认该字段是否仍有合法写入来源（常量初值 / 反序列化填充 / 框架注入 / ORM 托管等也算合法写入，须显式确认，不得默认"无写入即 bug"）。
  - **先读后写**：存在读取点早于任何写入点的执行路径，可能读到默认值 / None → 标「未验证-动态」，建议运行时验证或补测试。
  - 若命中附录 A「字段共享可变状态」气味（别名 / 继承覆盖 / 跨实例共享），无法确认读写点指向同一对象实例 → 标「未验证-动态」。

> 这一步与 1.2 的"直接子调用"是**不同维度**：1.2 管调用边，1.6 管来源边、位置边、字段数据流边。三者都禁止静默消失；即便 1.2 已判定某调用"确认"，其符号来源 / 路径 / 字段读写若未确认，仍不得整体标「确认」。

**1.7 产出调用链报告**  
用附录 B 模板整理成结构化报告，作为独立产物先给出，**不直接改代码**。报告末尾必须附上机械完整性核对（见附录 B 结尾）；若 1.6 扫描出非调用依赖，须单独成节列出；若为删除任务，须包含 1.3 删除核对产出的命中清单；若涉及字段改动，须包含 1.6c 字段数据流对账表。

### Phase 2：人工确认关卡

以下任一情况，必须暂停、展示报告、等待确认，不能自行决定继续：

- 报告里存在「未验证-动态」标记，且该路径处于 Phase 0 核心关心范围内。
- 实际需要修改的范围明显超出用户最初描述。
- 剪枝日志里有"自己也不太确定是否真的无关"的条目。
- 1.5 记录了既有问题，需要人工决定是否 / 何时处理。
- **1.6 扫描出 import 来源 / 资源路径类未验证项，且本次任务涉及移动文件 / 改目录 / 改符号来源**。
- **1.6c 扫描出字段数据流未验证项（如「只读不写」「先读后写」），且本次任务涉及改动字段读写逻辑 / 字段重命名 / 移除字段写入点**。
- **删除任务：1.3 删除核对的命中清单中存在尚未确认如何改写的引用点**。

若报告全部为「确认」级别、范围与预期一致、无 1.5 记录，可直接说明并进入 Phase 3，不必每次硬性等待。

### Phase 3：修改

按报告确认的范围修改代码。**删除场景下，对每个被删符号的每一个引用点，必须合理改写为仍能保持原语意的形式，再移除定义本身；字段改动场景下，对字段的每一个读取方都必须同步更新以承接新的写入语义，不得只改写入方而遗留「只读不写」的读取方。** 修改中若发现报告有遗漏，回到 Phase 1 补充梳理并更新报告，不要边改边发现边悄悄处理而不记录。

### Phase 4：回归验证（必须，非可选）

1. 对本次修改涉及的所有函数，重新执行一次 1.3 反向追踪，对比修改前后调用点清单是否一致——新出现或消失的调用点必须能解释原因。
2. **删除场景的机械核对（若有符号被删除，必须做）**：删除完成后，对每一个被删除的符号名，在全仓库做**精确符号名匹配**检索（用精确匹配而非子串，避免 `parse` 误伤 `parseJSON` 这类无关符号），输出命中清单。除以下三类**已声明豁免**的场景外，不得存在悬空引用；每一处命中必须逐条说明为何归入豁免、或清理掉：
   - **专门断言该符号已删除的测试**（如断言调用它应抛异常 / 断言其不在对象属性清单中）；
   - **变更日志 / 迁移说明 / 弃用记录**等文档性内容；
   - **对外契约字符串**（如报错信息、序列化字段名等需保留旧名以维持外部语义的场合）。
   任何无法归入上述三类、且非本次已合理改写的命中，均视为漏改，必须回到 Phase 3 处理。
3. **若有移动文件 / 改目录 / 改符号来源，必须实际运行或在目标环境验证资源路径与 import 是否仍解析正确**（静态梳理无法替代这一步）。
4. 若相关代码有测试覆盖，运行测试；无测试的核心路径，说明这一点并**建议补测试**，而不是默认"跑起来就行"。
5. 最终回复中明确区分：哪些调用点是「确认无影响」，哪些是「未验证，建议人工 / 运行时二次确认」——不要用一句笼统的"已完成修改，未发现问题"掩盖真实不确定性。
6. **字段数据流机械核对（若本次涉及改动字段读写逻辑 / 字段重命名 / 移除写入点，必须做）**：对比修改前后「字段写点 / 读点清单」是否一致——新出现或消失的写点 / 读点必须能解释原因；重点核对是否引入了「只读不写」（有读点却无写点）或「先读后写」路径，若存在须回到 Phase 3 处理，或显式标「未验证-动态」并给出运行时验证建议。

## 诊断模式（排查问题 / 复现 bug 场景，不套用 Phase 0-4）

计划性修改的失败模式是"漏改"，诊断类任务的失败模式是"给了一个听起来合理但没验证过的根因"。这是两类不同的任务形状——诊断往往没有清晰的"入口点"，硬套 Phase 结构会别扭，因此单独成一套流程：

1. **复现优先**：按原代码实际逻辑，尝试在真实 / 可控环境中复现问题（跑代码、写最小复现用例、查日志 / 报错栈），而不是仅凭读代码猜测根因。对「移动文件 / 改 CWD 后相对路径解析失效」「改字段写入逻辑后读取方『只读不写』」这类，必须在**目标目录结构 / 工作目录 / 实际运行**下验证才能坐实，纯读代码无法确认。
2. **能复现 → 基于复现证据解析根因**：报告中必须引用具体的复现证据（报错信息、日志片段、实际输出 vs 预期输出），并说明证据如何指向该根因。
3. **不能复现（无环境 / 无权限 / 无法触发）→ 显式声明**：必须写明"以下结论基于静态代码分析推断，未经运行验证"，并将结论整体标注为「推测」或「未验证-动态」，不能省略这句声明去追求结论看起来更确定。
4. 若诊断过程中需要沿调用链定位问题实际发生的位置，可复用 Phase 1 的 1.1–1.4、1.6 方法，但产出物是"诊断报告"（结论 + 证据 + 置信度），不是"调用链报告"，两者不混用同一模板。

---

## 置信度标注规则（贯穿全报告 / 诊断报告）

| 标注         | 含义                 | 何时使用                                     |
| ---------- | ------------------ | ---------------------------------------- |
| **确认**     | 静态读代码即可确定，或已通过复现验证 | 直接调用、类型明确、未命中任何气味、LSP 能唯一解析；非调用依赖（import 来源 / 资源路径 / 字段读写）已确认绑定；诊断场景下指已用证据坐实 |
| **推测**     | 有较强依据但非 100%       | 间接调用但有强约束能收敛到少数候选；诊断场景下指基于静态分析、逻辑自洽但未复现  |
| **未验证-动态** | 无法静态确定真实执行路径       | 命中附录 A 任一气味（含非调用依赖的 import 来源 / 资源路径 / 字段读写）且无法从代码收敛到唯一路径 |

> 标注必须写进报告每一行相关结论，不能只在末尾汇总；正向表、反向表、非调用依赖表、字段数据流表都需有独立的置信度列并逐行填写。

## 附录 A：动态分发「气味清单」(code smell)（命中即停止推测）

遇到以下模式，静态读代码无法确定真实执行路径，必须走 1.4 并标注「未验证-动态」：

| 模式           | 常见语言 / 框架特征                                                 | 识别线索                               | 通用特别提示                                                                             |
| ------------ | ----------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------- |
| 接口 / 多态      | Java/TS/Go interface、Python ABC                             | 调用的是接口类型变量的方法，需找出所有实现类             | 用 LSP find implementations 或 grep 实现声明列出所有 receiver 实现；图 / 工作流框架的节点常以 interface 注入 |
| 依赖注入         | Spring `@Autowired`、NestJS `@Injectable`、.NET DI 容器         | 构造 / 属性上的注入标注，实际实现由容器配置决定          | 查找 provider / 注册表（如 `wire`、`fx`、`graph.Node` 注册）                                   |
| 事件总线 / 发布订阅  | `emit`/`on`、EventEmitter、Kafka/RabbitMQ                     | 发布方与订阅方代码无直接引用，需全局搜事件名字符串          | 图 / 工作流框架：节点间数据流与 callback 触发类似事件总线，订阅点不在调用栈里，需按节点名 / callback key 全局搜             |
| 反射           | `getattr`/`setattr`(Py)、`Class.forName`(Java)、`reflect`(Go) | 方法 / 类名是运行时字符串拼接或变量，grep 搜不到静态引用   | 反射在部分语言更常见，但凡出现动态方法 / 字段调用必标未验证                                                    |
| 配置驱动分支       | feature flag、策略模式、`handlers = {"typeA": fnA}`               | 走哪个分支由配置 / 环境变量 / 数据库值决定，代码看不出运行时值 | 搜 map / registry 的 key，列出全部 handler 候选                                             |
| 装饰器 / AOP 切面 | Python 装饰器、Java 注解处理器、中间件链                                  | 真实执行顺序 / 是否执行由装饰器逻辑决定，易漏包裹层        | 中间件 / interceptor 链需逐个展开                                                           |
| ORM 懒加载 / 回调 | Django signals、SQLAlchemy events、Hibernate 回调               | DB 操作可能触发未在当前调用链显式出现的副作用           | —                                                                                  |
| 字符串拼接动态调用    | 动态 import、`eval`、模板方法名拼接                                    | 目标函数名非字面量，grep 会直接漏                | 列出可能的目标名模式，标未验证                                                                    |
| 符号来源 / 导入绑定  | 重导出 / 通配 import / 构建工具 re-export、动态 import                  | 函数体引用了非本文件、非局部、非标准库的符号，却无法静态确认它从哪个 import 解析 | 用 LSP go-to-definition 解析符号来源；grep 搜不到静态引用必标未验证；绝不直接假设符号是"局部定义"                       |
| 资源位置 / 路径耦合  | 基于「源文件所在位置 / 模块目录」解析的路径、基于「当前工作目录（CWD）」解析的路径       | 以源文件目录 / 模块目录 / CWD 为基准拼接文件路径（而非以调用点或绝对配置为基准）；相对路径的基准随文件落点或启动目录变化 | 对"移动文件 / 改 CWD / 打包"敏感，静态无法确定运行期路径，必须标未验证并建议在目标环境运行或写测试验证                        |
| 字段共享可变状态    | class/struct 字段、跨方法读写的实例变量                                 | 同一字段被多处写入 / 读取，且存在别名 / 继承覆盖 / 跨实例共享 | 用 LSP find references 列出字段全部读写点；重构改动写入方时，须逐一核对读取方是否已同步；「只读不写」「先读后写」必须显式标注           |

对每条命中项，报告必须写明：候选范围（哪几个实现 / 哪几个订阅者 / 哪几个可能来源 / 哪几个读写点）+ 无法收敛的原因 + 建议验证方式（运行时打日志 / 写单测触发 / 在目标环境运行 / 问业务方）。

若该气味在你的代码库 / 框架中有特定表现形式（如自研框架的 callback 机制、图引擎的节点注册），建议在具体项目中追加一行针对性识别线索，而不是每次都从头猜。

## 附录 D：工具能力分级（通用）

本协议最低要求只是"读文件 + 文本搜索"，任何分析环境都能执行。以下按**能力类别**列出可选增强手段（不绑定任何具体工具 / 产品），工具越强，报告里「未验证」的比例应越低；工具受限时，报告必须诚实反映这一点。

- **文本搜索能力（grep / ripgrep 类）**：1.3 反向追踪与删除核对的基础，支持正则与命名变体搜索；删除核对与字段数据流核对均须用**精确符号名匹配**而非子串，避免误伤无关符号。
- **路径匹配 / 文件发现能力（glob 类）**：定位定义文件、按模式发现候选实现。
- **文件读取能力**：读函数体理解控制流与副作用。
- **语言服务器 / 符号解析能力（LSP 类：go-to-definition / find references / hover）**：替代纯 grep，提供**编译器级符号解析**；既对 **interface 派发**关键——能直接列出某方法的所有实现，也对**符号 import 来源解析**关键——能直接跳到符号的定义 / 导入处，并对**字段读写点枚举**关键——能列出某字段的全部写入 / 读取位置，显著降低「未验证-动态」比例。
- **子代理 / 并行搜索能力（Explore / Agent 类）**：大规模、跨目录、需多轮试探的穷举式搜索（单条 grep 做不到）。
- **运行测试 / 构建 / 复现环境的能力**：验证附录 A 中「未验证-动态」的真实分支（含 import 来源、资源路径、字段读写），以及诊断模式下的根因复现（含「移动文件 / 改 CWD 后路径解析失效」「改字段写入逻辑后读取方只读不写」这类必须实际运行才能坐实的问题）；删除场景的悬空残留、字段数据流的读写对账也应在目标环境运行测试确认。

若代码库中存在某类特有的结构化记录需求（例如某种测试 fixture 的专属追踪格式），建议仿照附录 B 反向表的格式自行扩展一张专属表，不必强行塞进通用模板——保持核心模板通用、专属扩展放在项目自己的附录里。
