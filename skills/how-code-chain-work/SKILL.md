# How Code Chain Work — 功能链路精确梳理协议

> **上一步**: 无（由用户请求或任务本身触发）| **下一步**: 无（报告经确认后进入修改）

## 这个技能解决什么问题

大代码库里，模型天然倾向于"看到相关代码就直接改"，跳过系统性调用链梳理，导致三类失败：

1. **漏掉间接受影响的调用点**（改动 gap）——改了 A，B 处炸了却不知道 B 也依赖 A。
2. **对反射 / 依赖注入 / 事件总线等间接调用瞎猜**，给出"看似确定、实则无依据"的结论。
3. **只验证「语法对不对、能不能跑」，不验证「语义对不对、副作用变没变」**。

本技能把"改代码"拆成"先梳理、后动手"两段，强制在动手前把**调用关系 + 不确定点**显式写出来。它不假设你有静态分析工具——最低要求只是"读文件 + 文本搜索"，因为任何 agent 环境都能保证这两件事。环境里若有更强工具（见附录 D），用以降低"未验证"比例，但**不能因为工具不够就降低标注标准去凑一个看起来完整的假象**。

## 三条铁律（不可跳过）

1. **先梳理，后动手**：任何跨函数 / 跨文件的修改，必须先走完 Phase 1 产出调用链报告，未经确认不得进入 Phase 3。
2. **剪枝必须留痕**：凡是"判断为无关、不展开"的调用，必须写明理由；理由说不清楚 = 不能剪枝，必须展开看一眼。
3. **不确定就说不确定**：遇到无法用静态读代码确认的调用关系（命中附录 A「气味清单」），必须显式标注为「未验证-动态」并给出验证建议，**禁止用推测冒充确认结论**。

> 违反第 3 条比"漏查一个调用点"更危险——前者是诚实的信息缺口，后者是伪装成完整结论的信息缺口，会误导后续所有决策。

## 启用判定（比例原则）

不是所有改动都值得走完整协议。按下表决定是否启用：

| 场景 | 是否启用完整协议 |
|---|---|
| 跨文件 / 跨模块修改 | **必须** |
| 被多处调用的函数（尤其是公共 util、interface 方法） | **必须** |
| 重构、重命名导出符号、改返回值类型 | **必须** |
| 追查一个功能入口到底影响哪些地方 | **必须** |
| 排查「改了 A 却在 B 出问题」 | **必须** |
| 单函数内、唯一调用方、纯局部变量重命名 | 可轻量跳过 |
| 确认无副作用的 1–2 行改动 | 可轻量跳过 |

**不确定该不该用 → 用。** 误用本技能的成本 << 漏用本技能的成本。

## 工作流程

### Phase 0：定义任务边界（约 30 秒，不能省）

开始搜索前，先用一句话写清：

- **本次任务关心的行为是什么**（例：「确认修改 `calcDiscount()` 的返回值类型不会破坏调用方逻辑」）。
- **范围边界**：只看本仓库 / 本服务，还是要跨服务？第三方库源码要不要展开？
- **正确性要求等级**：核心支付 / 权限类逻辑 → 要求「未验证」点数量趋近于 0；边缘功能 → 可接受合理浅层梳理。

这一步输出仅一两行，但决定后面"该展开到多深"的判断基准，不能靠临场感觉。

### Phase 1：梳理（只产出报告，不改代码）

**1.1 定位入口**
用 Grep / Glob / LSP 定位目标函数、路由、事件处理器的**定义位置**（不是调用位置）。确认这是唯一定义，还是存在同名重载 / 多态实现——若有多个候选，全部记录，不假设只有一个。

**1.2 正向追踪（入口内部调用了什么）**
从入口函数逐层往下看它调用的函数：
- 判断该调用是否影响 Phase 0 定义的关心行为。
  - 是 → 展开看该函数定义，递归本步骤。
  - 否（如日志、埋点、纯格式化、与本次变更行为无关的分支）→ **记入剪枝日志**，写明"为什么判断无关"，不展开。
- 命中附录 A 任一「气味」→ 停止推测，转入 1.4。

**1.3 反向追踪（谁在调用这个入口 / 这个函数）**
搜索函数名 / 方法名在全仓库的所有引用点。注意至少覆盖以下变体，避免漏报：
- 完整名 + 常见变体（驼峰 / 下划线互转、类名 + 方法名组合、可能的别名 import）。
- 优先用 **LSP 的 find references**（符号级，优于字符串 grep）；无 LSP 时退回 grep 并显式声明"已用 grep，可能存在漏报"。

对每个调用点，确认：传参方式、是否依赖返回值的具体类型 / 结构、是否依赖副作用，并判断该调用点是否会被本次修改影响。

**1.4 间接调用处理（命中气味清单时）**
不要猜。执行以下任一动作：
- 列出**全部候选实现 / 处理器**，而不是挑一个。
- 若候选数 > 1 且无法从代码本身收敛到唯一执行路径 → 标记为「未验证-动态」，写清"需要运行时验证"或"需要人工确认业务上实际走哪个分支"。
- **绝不写「应该是走 XX 这个实现」这种无证据支撑的确定性表述。**

**1.5 产出调用链报告**
用附录 B 模板，把以上结果整理成结构化报告，作为独立产物先给出，**不直接改代码**。

### Phase 2：人工确认关卡

以下任一情况，必须暂停、展示报告、等待确认，不能自行决定继续：

- 报告里存在「未验证-动态」标记，且该路径处于 Phase 0 定义的核心关心范围内。
- 实际需要修改的范围明显超出用户最初描述（如发现还牵涉另一个服务）。
- 剪枝日志里有"自己也不太确定是否真的无关"的条目。

若报告全部为「确认」级别且范围与预期一致，可直接说明并进入 Phase 3，不必每次硬性等待。

### Phase 3：修改

按报告确认的范围修改代码。修改中若发现报告有遗漏（又牵出新的调用点），**回到 Phase 1 补充梳理并更新报告**，不要边改边发现、边悄悄处理而不记录。

### Phase 4：回归验证（必须，非可选）

修改完成后：

1. 对本次修改涉及的所有函数，**重新执行一次 1.3 反向追踪**，对比修改前后调用点清单是否一致——新出现或消失的调用点必须能解释原因。
2. 若相关代码有测试覆盖，运行测试；无测试的核心路径，说明这一点并**建议补测试**，而不是默认"跑起来就行"。
3. 在最终回复里明确区分：**哪些调用点是「确认无影响」，哪些是「未验证，建议人工 / 运行时二次确认」**——不要用一句笼统的"已完成修改，未发现问题"掩盖真实不确定性。

## 置信度标注规则（贯穿全报告）

| 标注 | 含义 | 何时使用 |
|---|---|---|
| **确认** | 静态读代码即可确定调用关系 | 直接调用、类型明确、未命中任何气味、LSP 能唯一解析 |
| **推测** | 有较强依据但非 100% | 间接调用但有强约束能收敛到少数候选（如 package-private、同文件内） |
| **未验证-动态** | 无法静态确定真实执行路径 | 命中附录 A 任一气味且无法从代码收敛到唯一路径 |

> 标注必须写进报告每一行相关结论，不能只在末尾汇总。

## 附录 A：动态分发「气味清单」(code smell)（命中即停止推测）

遇到以下模式，静态读代码无法确定真实执行路径，必须走 1.4 并标注「未验证-动态」：

| 模式 | 常见语言 / 框架特征 | 识别线索 | SG / Go / Eino 特别提示 |
|---|---|---|---|
| 接口 / 多态 | Java/TS/Go interface、Python ABC | 调用的是接口类型变量的方法，需找出所有实现类 | **Go**：用 LSP find implementations 或 grep `func (.*) MethodName` 列出所有 receiver 实现；Eino 的 `Callback` / `Graph` 节点常以 interface 注入 |
| 依赖注入 | Spring `@Autowired`、NestJS `@Injectable`、.NET DI 容器 | 构造 / 属性上的注入标注，实际实现由容器配置决定 | 查找 provider / 注册表（如 `wire`、`fx`、`graph.Node` 注册） |
| 事件总线 / 发布订阅 | `emit`/`on`、EventEmitter、Kafka/RabbitMQ | 发布方与订阅方代码无直接引用，需全局搜事件名字符串 | **Eino**：graph 节点间的数据流与 callback 触发类似事件总线，订阅点不在调用栈里，需按节点名 / callback key 全局搜 |
| 反射 | `getattr`/`setattr`(Py)、`Class.forName`(Java)、`reflect`(Go) | 方法 / 类名是运行时字符串拼接或变量，grep 搜不到静态引用 | Go 里少用，但若出现 `reflect.Value.MethodByName` 必标未验证 |
| 配置驱动分支 | feature flag、策略模式、`handlers = {"typeA": fnA}` | 走哪个分支由配置 / 环境变量 / 数据库值决定，代码看不出运行时值 | 搜 map / registry 的 key，列出全部 handler 候选 |
| 装饰器 / AOP 切面 | Python 装饰器、Java 注解处理器、中间件链 | 真实执行顺序 / 是否执行由装饰器逻辑决定，易漏包裹层 | 中间件 / interceptor 链需逐个展开 |
| ORM 懒加载 / 回调 | Django signals、SQLAlchemy events、Hibernate 回调 | DB 操作可能触发未在当前调用链显式出现的副作用 | — |
| 字符串拼接动态调用 | 动态 import、`eval`、模板方法名拼接 | 目标函数名非字面量，grep 会直接漏 | 列出可能的目标名模式，标未验证 |

对每条命中项，报告必须写明：候选范围（哪几个实现 / 哪几个订阅者）+ 无法收敛的原因 + 建议验证方式（运行时打日志 / 写单测触发 / 问业务方）。

## 附录 D：工具升级路径（WorkBuddy 环境）

本协议最低要求只是"读文件 + 文本搜索"，任何 agent 环境都能执行。本环境若具备以下工具，优先使用以提高准确率（非必需）：

- **Grep（ripgrep）**：1.3 反向追踪的基础，支持正则与变体搜索。
- **Glob**：定位定义文件、按模式发现候选实现。
- **Read**：读函数体理解控制流与副作用。
- **LSP（go-to-definition / find references / hover）**：替代 1.3 的 grep，提供**编译器级符号解析**；对 **Go interface 派发**尤其关键——能直接列出某方法的所有实现，显著降低「未验证-动态」比例。
- **Explore / Agent 子代理**：大规模、跨目录、需多轮试探的穷举式搜索（单条 grep 做不到）。
- **运行测试 / 构建的能力**：验证附录 A 中「未验证-动态」的真实分支。

**原则**：工具越强，报告里「未验证」的比例应越低；工具受限时，报告必须诚实反映这一点。
