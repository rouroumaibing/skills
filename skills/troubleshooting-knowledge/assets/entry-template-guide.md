# 条目模板使用指南（assets/entry-template.md）

本文件是 `entry-template.md` 的写作说明与落盘自检清单，**不是知识条目**，不会被
`scripts/validate.py` 扫描，也不会被消费方读取。

模板已做到**零注释**——既没有 `<!-- … -->`，也没有 frontmatter 里的 YAML `#` 注释。
原因是消费方会整篇读入条目，注释内容模型照样能看到，因此注释是绕过密钥/注入扫描的
隐蔽通道；validate 对两种注释都判 error。字段的取值与填写说明全部写在本文件里，
不随条目复制进去。你复制模板后**只需替换全部 `{{填写：…}}` 标记**，不需要删注释。

## 使用方式

1. 整份复制 `entry-template.md` 到 `knowledge/<oss|personal>/<domain>-<topic>.md`；
2. 替换全部 `{{填写：…}}` 标记（包括 mermaid 图里的 `{{填写：组件关系图}}` 等）；
   不适用的可选字段整行删除，别留空数组冒充已填——**但 `symptoms` / `error_codes` /
   `aliases` 与「异常归因速查」表是检索入口，必须写全、不能删**（见「检索入口必写全」）；
3. 不在条目里写任何注释（HTML 注释或 frontmatter 的 `#` 注释都不行）；
4. 跑 `python3 scripts/validate.py --file <草稿路径> --scope oss|personal` 先校验草稿
   （草稿不必先落盘）；确认无误后再复制到 knowledge/ 下，并跑全库复核；
5. 完成文末自检清单。

## frontmatter 字段填写

字段清单与完整定义以 **`references/schema.md`** 为唯一权威；下表只列模板里需要替换的取值。

| 字段 | 怎么填 |
|---|---|
| `schema` | 固定 `1`，别改 |
| `domain` | 组件或系统域，如 `k8s-service` / `coredns` / `envoy-gateway` |
| `scope` | `oss`（开源通用，可分发）/ `personal`（个人项目，不出库）；**必须与所在目录一致**，validate 机械校验 |
| `status` | 只能 `active` / `deprecated` / `disputed` |
| `confidence` | `verified`（运行时取证直接观测）/ `observed-once`（单次观察）/ `doc-sourced`（上游文档语义，oss 常用） |
| `evidence` | **必填非空数组**，每项含 `run` + `what`；`run` 写依据来源（上游文档名+版本+章节，或运行时观测方式/证据位），**不写具体日期、「哪次排查」、访问日期**；`covers` 标注本条证据覆盖的正文位置（如 `资源匹配关系 R1`）。每条 R# 都应有 covers 出处，否则 validate 告警 |
| `versions` | `doc-sourced` 条目必须带版本信息（本字段非空或 `evidence.run` 写明文档版本） |
| `updated` | **不写这个字段**：条目不体现任何日期；写了 validate 判 error（见「不写具体时间」） |
| `source` | 依据来源（哪份上游文档及章节 / 哪类观测事实），**不写具体日期或「哪次排查」** |
| `envs` / `related` | 适用环境；关联条目相对路径。没有就删除本行 |
| `symptoms` / `error_codes` / `aliases` | **检索入口，起草必写全**：见下「检索入口必写全」，不留空数组、不删行 |
| `error_codes` / `versions` | 数字型必须加引号（`"503"`），否则 YAML 解析成 int 被拒 |
| `superseded_by` | 模板里没有这行；仅 `status: deprecated` 时手动加，指向替代条目相对路径；**oss 条目禁止指向 personal/** |

未达 `doc-sourced` 的推测不进库（推测由河道按证据分级标注）。
**frontmatter 不写 `type` / `updated` 字段**：写了会被 validate 判 error（见「条目形态」「不写具体时间」）。

## YAML 书写坑（实测踩中）

- 值里含「冒号+空格」（如 `Last State: Terminated`）会破坏 YAML 映射 → 整句加引号；
- **值里含 `#` 要整句加引号**：YAML 只把「位于行首、或前面有空白」的 `#` 当注释。
  `source: k8s issue #1234` 会被吞成 `k8s issue`，validate 判 error；写成
  `source: "k8s issue #1234"` 才保得住原值。
  文档章节锚点 `source: https://…/spec/#gateway` 的 `#` 前是 `/`、**不是空白**，
  本来就是合法值——这类 URL 不必刻意改，validate 也不会误报。
- **块标量（`|` / `>`）里的 `#` 是普通字符，不是注释**：`run: |` 后缩进的内容
  （如日志特征行 `access log 出现 #hash`）validate 会整块跳过，不判注释；块外的
  行首/行尾真注释仍拦。块内容照样受全文密钥与注入扫描，别拿它藏东西；
- 数字型错误码/版本在数组里必须加引号（`"503"`），否则解析成 int 被拒。

## 阅读 / 写作顺序

阅读顺序 = 排查者的思考顺序：它是什么 → 由什么组成 → 正常时怎么走 → 逐环对照 → 按现象归因。
写作顺序必须一致：**先写正常，最后才罗列异常**——不要一上来就罗列症状。

## 锚点约定

- `R#` = 资源匹配关系 / `L#` = 请求或生命周期环节 / `P#` = 控制面下发环节。
- 「资源匹配关系」表首列是 R#；「流量走向 / 控制面下发」表首列是 L#/P#。
- 「逐环节排查」必须覆盖全部 L# 与 P#（控制面下发的 P# 也要写 `- **P1 …` 块）；
  「异常归因速查」每行写环节并回指 R#。锚点引用完整性由 validate 做 warn 级机械校验：
  L/P 已定义未覆盖、引用未定义 R#、速查环节列引用未定义编号都会告警。

## 条目形态（只有一种）

所有条目都是链路/系统型通用排查参考（如 envoy-gateway、k8s 网络），按模板全量结构写全，
不为单个错误码或行为建缩节条目。具体某报错（503、
CrashLoopBackOff 等）**不单独建条目**——错误码属于哪条链路/系统由消费方模型按语义自行
判断（这类归类 AI 可直接识别），不需要在知识库里维护「错误码 → 条目」映射表；报错线索
写进对应条目的 `error_codes` / `symptoms` 与「异常归因速查」表即可。
没有请求链路概念的对象，把「正常链路」写成「正常行为」，其余结构不变。

## 粒度：拆分看边界，不看体量

拆分依据是**链路或软件边界不同**（Ingress 与 GatewayAPI 是两条链路 → 分开写、用 `related`
串联），**不是体量**：同一个主题内容再多也写全、不拆。软上限数值以
**`scripts/validate.py` 的 `SIZE_LIMITS` 常量**为准（说明见 `references/schema.md`「粒度」），
超限只是 **warn**，提醒复核「是不是混进了两个主题」；确认同一链路/软件边界就直接写全，
别为压长度切条目。

写全不拖累读取：消费方按字节预算取水，`scripts/read_entry.py --sections <节名>` 按节、
`--hop L#` 按环节号切片，只读命中部分。别在文档里另抄一份数字——常量改了文档就会漂移。

## 检索入口必写全

所有条目都是链路型通用排查参考，具体报错由消费方按错误码自行归类、不单独建条目，
条目的 frontmatter 是关键词检索的主入口
（`scripts/search.py`：frontmatter 权重 3、正文权重 1；中文整词未命中才走 2-gram）。
用户口头说法没写进条目就命不中，所以起草时四项**硬性写全**：

- `symptoms`：用户会说的现象，**口语和术语都写**（`Pod 一直 Pending`、`5xx 陡增`）；
- `error_codes`：错误码 / 状态码 / 事件 reason / 响应标志，保留原始写法；
- `aliases`：缩写、中英文叫法、旧名（配合无命中时 `search.py` 的 `hint=` 换别名重试）；
- 正文「异常归因速查」表：现象 → 环节号（`L#`/`P#`），命中条目后靠它定位环节，再用
  `scripts/read_entry.py --hop L#` 切片取证。

validate 对 `symptoms` / `aliases` 为空发 **warn**；别用 `[]` 冒充已填。

## 不写具体时间

条目是**长期可复用的链路/系统参考**，不对应「某一次排查」。整个条目
——正文、`frontmatter`（含 `evidence.run` / `source`）、表格、图示——**不出现任何具体时间**：
某年某月某日、访问日期、排查 run 的日期/ID、日志时间戳、「截至某日」等都不要写。
理由：具体时间会把通用事实绑成一次性个案记录，读起来像某次故障纪要，也会随时间失效；
来源定位用**可复现的标识**（上游文档名 + 版本 + 章节、运行时观测方式/证据位），不靠日期指认。

frontmatter 不含 `updated` 字段，写了会被 validate 判 error（与 `type` 字段同规）；validate
不做过期复核。复核条目是否有新证据，靠 diff 与 `evidence` 追加体现，不靠日期。
`assets/conflict-report-template.md` 里要求运行时证据写「什么时间」是**冲突报告的定位信息**
（哪个 pod、哪行日志），不是知识条目，不在此限。

## 事实 / 流程边界

- 链路顺序是系统客观事实，可以按序写（请求物理上就按此顺序流动），不算排查流程；
- 不写「你先跑哪条命令」的执行序列（判定法与细则见 references/schema.md；执行序列归排查框架/河道）。

## 脱敏占位符

- 正文里代替真实敏感值用 `<INTERNAL_HOST>` 这种尖括号形态——与 `{{填写：…}}` 不同，
  前者是条目的最终内容，后者是未填完的标记（validate 会拒绝残留 `{{` 的条目）。
- 密钥/token/口令、PII、内部主机名/IP/租户 ID 一律替换；validate 全文（含代码围栏）扫描兜底，
  具体模式见 `references/schema.md`「脱敏硬规则」与 `scripts/validate.py` 的常量表。
- 自动扫描只挡**无意写入**：正则挡不住有意构造的变体。真正的防线是落盘前的 diff 确认
  ——把结构化 diff 给用户看，一条错误事实的代价远大于一次错误回答。

## 落盘前自检清单

- [ ] 查重：已用 `scripts/search.py` 确认无同主题条目（或走更新/合并）
- [ ] 顺序：是什么 → 组件与架构 → 正常链路 → 逐环节 → 异常归因，异常没有混进前面
- [ ] 零注释：条目里没有 `<!--`，frontmatter 里没有 YAML `#` 注释
- [ ] 无 `updated` 字段：frontmatter 不写日期元信息（写了会 error）
- [ ] 无具体时间：正文与 `evidence.run` / `source` 未写日期、访问日期、排查时间戳、「截至某日」
- [ ] 无 `type` 字段：条目形态只有一种，frontmatter 不写 type（写了会 error）
- [ ] 锚点：每个环节引用了 R#；逐环节覆盖全部 L#/P#；速查每行有环节
- [ ] 证据覆盖：每个 R# 都在 `evidence[].covers` 有出处
- [ ] 字段名精确：真实字段名，复数/单数、层级路径已对照上游 API 或文档
- [ ] 状态归属：状态条件写在它真正出现的资源上
- [ ] 推论已标注：非文档明确陈述的内容已标〔推论〕（verified 条目不允许）
- [ ] scope：oss（无任何内部信息）/ personal（确认不含可分发内容）
- [ ] 脱敏：无密钥 / token / PII / 内部主机名 / IP / 租户 ID（用 `<占位符>` 替代）
- [ ] 防注入：无照抄的祈使句；日志只摘特征行（扫描非安全边界，靠 diff 兜底）
- [ ] 无排查命令串：只写「哪一环出什么问题、证据在哪」
- [ ] 粒度：按链路/软件边界判断是否该拆（同一主题写全不拆）；收到体量 warn 只复核主题是否单一，未因「太长」而切条目
- [ ] 检索入口：`symptoms`（口语+术语）/ `error_codes`（错误码、reason、响应标志）/ `aliases`（缩写、中英文叫法）/「异常归因速查」表（现象→环节号）四项写全、无空数组
- [ ] 所有 `{{填写：…}}` 已替换，不适用的可选字段已删除
- [ ] 已跑 `python3 scripts/validate.py --file <草稿> --scope <oss|personal>`
- [ ] diff 已按结构化摘要给用户确认（新增/改了哪些 R#/L#、confidence、〔推论〕数、证据来源），确认后再落盘
