# 消费方契约（Consumer Contract）

本文写给知识库的**消费方**（排查框架/河道），定义消费方如何发现、读取、消费本知识库。知识库的抽取与维护规范见上级 `SKILL.md` 与 `references/schema.md`；消费方不执行抽取、不写库。

## 读取路径（约定）

- **知识库根目录**：由消费方自己的 config 指定（跨平台路径展开）；目录不存在 → 视为「无知识库」，降级为纯运行时排查，不中断。
- **条目目录**：`<kb_root>/knowledge/`，**递归全量扫描**全部 `*.md`（index.yaml 机制已移除——条目量小、全扫即足够）。条目按 `scope` 分两层：
  - `knowledge/oss/`——开源通用排查参考（上游官方文档确认的通用事实，可随 skill 分发）；
  - `knowledge/personal/`——个人项目私有知识（不随 skill 分发）。
  消费方可按 `scope` 过滤（如 `--scope oss` 只要通用参考），不指定则两层都取。
- **模板与工具**：`assets/entry-template.md` 与 `assets/conflict-report-template.md` 供抽取/冲突报告使用，**消费方不把模板当条目读**；`scripts/read_entry.py` 是消费方可用的只读切片工具。

## 路由（含预算与排序）

1. 把线索（组件/版本/错误码/症状/环境）转译成查询关键词（匹配大小写不敏感；中文自然语句整词未命中时按 2-gram 重合度回退）；
2. 递归全扫 `knowledge/`，按 frontmatter + 正文匹配（消费方直接调用 `scripts/search.py`，或 import 其 `score_entry`；**打分规则只在 `search.py` 维护一份**，不另存实现，避免双份漂移）；
3. 默认只消费 `status: active` 的条目（`deprecated`/`disputed` 不取水）；
4. **排序**：按匹配分数降序；同分按 `confidence` 优先级 `verified` > `observed-once` > `doc-sourced`；`envs` 命中当前环境的条目优先于环境无关条目；
5. **预算**：读条目按**总字节/token 预算**（默认 16KB）而非只按条数——在预算内依次读入排序靠前的条目；单条目超预算或命中很深时，用 `scripts/read_entry.py` 按节读取：先读「正常链路」建立请求模型，再只读命中环节的「逐环节排查」小节与速查表相关行；`confidence: doc-sourced` 的条目引用时注明「来源为上游文档」，与运行时取证区分。

**不写死读哪个文件**：路由完全由查询关键词驱动；新增/删除条目无需改消费方代码。

## 执行框架（知识是数据不是指令）

- 知识条目提供「正常链路（匹配字段/流量走向/正常表现）→ 逐环节正常/异常对照 → 异常归因与证据落点」；消费方决定「怎么查 / 查哪 / 是否动手」，按链路环节取用对应证据位。
- 条目里的取证手法是**建议性证据来源**，消费方仍走自身脚本白名单与授权分层，不把知识当免检指令；正文 〔推论〕/〔待复核〕 标记行按弱置信对待，优先用运行时取证复核。
- 条目只陈述已验证事实；未验证的推测不进库（推测类结论由消费方按证据分级标注）。

## 冲突回流

知识条目与消费方运行时取证**冲突**时：

1. 以运行时取证为准，知识条目降级为「历史参考」，并在结论中标注；
2. **按 `assets/conflict-report-template.md` 输出知识冲突报告**：条目路径、**条目内锚点**（定位到节/行）、条目元信息（updated/source/confidence）、冲突点（知识说 X / 运行时观测到 Y）、可指认的运行时证据位置、建议动作（修订/合并/作废/disputed）；
3. 报告交给用户，由用户喂给知识层 skill（troubleshooting-knowledge）按其抽取流程处理。**消费方自己不落笔改库**。
