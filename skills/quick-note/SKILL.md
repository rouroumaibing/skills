# quick-note（顺手记）

## 这个 skill 解决什么问题

写代码时做的选择——选了哪种实现方式、对模糊需求补了什么假设、用了什么 workaround——通常不会被记下来。等结构需要修正、需要返工的时候，没人（包括 AI 自己）记得当初为什么这么写，只能靠猜或重新分析一遍。

本 skill 要求做两件事，覆盖两种不同重量级的记录：

1. **breadcrumbs（顺手记）**：写实现代码的**同时**顺手留一笔，几乎零成本，不打断"用户定方向、细节交给 AI"这种工作方式。
2. **正式 ADR**：当用户（或 AI 自己经过分析后）**明确做出/推翻一个决策**的时刻，生成一份规范的决策记录。

两者都是纯 Markdown，存在代码仓库里，不依赖任何专有工具或格式，任何人、任何 AI agent 都能直接读懂。

## 使用前提与边界（写文件之前的硬约束）

记录动作会产生文件系统副作用，但**不需要为它单独征求一次许可**——触发条件本身就是"决策已经发生"，落盘只是把既成事实写下来，不是额外发起一次决策。落盘前只确认两件事：

1. **能力门**：当前 session 确实有文件写入能力（有可用的写入工具，能真正创建/追加文件）。
2. **项目根门**：当前工作目录是一个**有归属的项目根**，满足其一即可：
   - 它本身是 git 仓库；
   - 它是多仓并列的工作区根——**直接子目录**里有 ≥1 个 git 仓库；
   - 它含项目标记文件（`go.mod` / `package.json` / `pyproject.toml` / `Cargo.toml` / `Makefile` / `CLAUDE.md` / `AGENTS.md` 等），且标记文件就摆在这一层、不在更深的地方。

这道门只确认一件事：**写下去的东西有归属、有人会看到**。它不负责保证落点一定在版本控制内——那是下面「范围门」单独管的事。把两件事塞进同一道门，代价是"四仓并列的工作区根"被一并挡在门外，而那恰恰是跨仓决策唯一自然的归属地（同时也别把"纯文档目录"当成降级理由——文档仓本身就是个 git 仓）。

两条同时满足 → 直接落盘。只有下面两种**硬情况**才降级为"只在回复里提一句这条值得记"，不创建任何文件：

- 没有可用的文件写入工具（只读 session）；
- 当前目录**不是**有归属的项目根（`/tmp`、scratch 目录、纯对话）。

在此之上，还有三条不能越的边界：

- **范围门**：默认只写**记录根**（定义见「存放位置」）内的记录文件，不动 `.git`。唯一的例外是使用者显式指定的目录（情形③）——那时写到哪儿就是哪儿。两种情形下，只要落点**不在版本控制内**（仓库外，或者记录根本身不在仓里），都要先在回复里说明落点。目的很清楚：仓库外的写入可以有，但不能静默发生。
- **不越界**：不改 `CLAUDE.md` / `AGENTS.md` / 根 `README.md` / commit message 模板 / CI 配置等其它约定文件。本 skill 只管决策记录，不顺手替用户改别的规范。
- **只追加**：breadcrumbs 只允许**追加**，不得重写既有条目；ADR 与索引允许多行修改，但必须遵守下方「写入顺序与幂等」。

落盘后在回复里用一句话说明（见文末「回复里怎么说」）——那是"不静默"，不是"要许可"。

## 存放位置

**先判顺序，命中即停：使用者显式指定（③）→ 记录根下已有 `docs/`（①）→ 复用记录根下别的 ADR 目录（②-复用）→ 都没有才新建（②-新建）。**

显式意图**优先于**任何启发式探测——顺序倒了就会出这种事：你说了"记录到 `hub/`"，它仍先去 `docs/` 找，没找到，于是当场新建一个 `docs/architecture-decision-record/`。用推测覆盖明确指令，是这个 skill 最不该犯的错。

两个锚点先定义清楚，下面全部按这个口径：

- **记录根**：本次会话的项目锚点，**不是裸的 cwd**。
  - 当前目录在某个 git 仓内 → 取该仓的根（`git rev-parse --show-toplevel`）；
  - 否则（多仓并列的工作区根等）→ 取当前目录。

  为什么要强调"不是裸 cwd"：会话从仓库子目录启动是常态（比如 `repo/internal/domains/auth`），拿 cwd 当根会让 ① 去找 `auth/docs/`、② 在 `auth/` 下建 `auth/docs/architecture-decision-record/`——就地生成一棵没人想要的目录树。
- **现场**：本次写入的目标目录。情形③ 下就是使用者指定的那个目录，其余情形下就是记录根下的记录目录。全文说"跟现场""与现场一致"，都是这个意思。

### 什么算「已有 ADR 目录」（① 与 ② 共用，只在这里定义一次）

一个目录算「已有 ADR 目录」，当它满足任一：

- 里面有 `NNNN-*.md` 形态的文件，且首行为 ADR 标题；或
- 里面有文件名含 `ADR` / `adr` 的文件，且首行为 ADR 标题——`ADR-dispatch-durable-queue.md`（首行 `# ADR-002:`）这类命名是真实存在的，**只认"文件名带数字前缀"会把这一整类漏掉**，而漏掉的直接后果是撞号；或
- 它本身就是 `adr/` / `.adr/` / `decisions/` / `architecture-decision-record/` 这类约定俗成的目录名。

### ③ 使用者显式指定了目录

写到该目录，**不再做任何探测**。

- 目录不存在 → 递归创建；落点越出记录根（写到别的仓、别的路径）时**先说明落点再写**。
- **会话内持久**：指定一次之后，本次 session 后续记录沿用同一目录，不要每写一条重新问一遍。
- 这一情形下"现场"指的是**那个指定目录**里的既有文件，不是记录根的现场。
- **别让索引撞上约定文件**：若指定目录恰好就是仓库根，索引不能落在根 `README.md`（那是「不越界」明令禁止改的文件）——改写到该目录下的 `docs/` 或一个专用索引文件，并在回复里说明挪到哪儿了。

### ① 记录根下已存在 `docs/`

`docs/` 存在**不等于**里面没有 ADR 约定——先在 `docs/` **内部**找，命中就复用，不要另起第二套：

1. 按顺序探测：`docs/adr/` → `docs/decisions/` → `docs/architecture-decision-record/` → `docs/` 下任何满足上面「已有 ADR 目录」判定的目录。
2. 命中则**复用**该目录，并把 breadcrumbs 放在同一目录下（保持两层记录同处一地，便于互链）。
3. `docs/` 下没有 → 才在其下创建默认结构。

### ② `docs/` 不存在 → 先看别处，都没有再新建

**记录根下可能已经有 ADR 目录，只是不在 `docs/` 下**（顶层 `adr/`、`.adr/`、`decisions/`，或任何满足上面判定的目录）。有就**复用它们**——不要因为"不在 `docs/` 下"就视而不见，那会造出本节开篇要防的"第二套记录"。

确实一个都没有，才新建。按记录根是否在版本控制内分两支：

- **②a 记录根是 git 仓库** → 直接在其下建默认结构，无额外条件。
- **②b 记录根不是 git 仓库**（例如多个仓并列、自己不是仓的工作区根）→ 下面两条**都**满足才建，否则降级为"只在回复里提一句"：
  1. 它下面**不存在**名字含 `docs` / `documentation` 的目录或仓库。已经有一个文档仓/文档目录摆在那儿，再新造一个 `docs/` 等于制造第二个真源——这种情况提示使用者改用情形③ 显式指定落点，而不是替他们决定。
  2. 落点不在版本控制内 → 按「范围门」先在回复里说明落点。

默认结构是 `<记录根>/docs/architecture-decision-record/`：

```
<记录根>/docs/architecture-decision-record/
├── README.md               # 索引，列出所有正式 ADR（首次使用时创建）
├── breadcrumbs.md          # 轻量留痕的流水记录（首次使用时创建）
├── 0001-<短标题>.md        # 正式 ADR，按序号递增
├── 0002-<短标题>.md
└── ...
```

### 复用既有目录时：先认约定，再续写

现场已经有约定时，**本 skill 的模板让位**。落笔前先扫一眼既有文件，把下面几项认下来，然后照着它们续写（照的是现场，不是这份 SKILL.md）：

| 要认的项 | 看什么 |
|---|---|
| 编号位数 | 现场是 `1`、`01`、`001` 还是 `0001`？ |
| 文件名形态 | 有没有 `ADR-` / `adr-` 前缀？编号与标题之间用什么分隔？ |
| ADR 首行标题 | 既有文件第一行长什么样（`# ADR-0001: xxx` / `# 0001 xxx` / `# xxx`）？ |
| 必填字段与字段名 | 用的是"状态/日期/决策者"还是 `Status` / `Date` / `Deciders`？有哪些必填项？ |
| 状态取值 | `Accepted` / `Approved` / `采纳` / `Proposed`？ |
| 索引位置与列格式 | README 表格？`index.md`？列顺序是什么？ |
| breadcrumbs 落点 | 既有目录里是否已有一个轻量记录文件？叫什么名字、什么格式？ |

**只有"全新创建这套目录、现场没有任何可参照的约定"时，才启用本 skill 自带的默认形态**（4 位编号、`0001-短标题.md`、`# ADR-0001: 标题`、README 索引表）。

下面所有示例（编号写法、文件名、模板字段、索引表格）都是**默认形态的示例**。现场有约定就跟现场——不要拿这份模板去覆盖团队原有习惯，那会让新旧记录形态不一致，比不记录更糟。

首次创建该目录时，顺带写一个简短的 `README.md`，说明这套两层记录的约定（见下方模板）。目的：换别的 AI 工具或新人接手时，光看仓库目录就能明白这是什么、该怎么续写，**不需要读这份 SKILL.md**。

## 第一层：breadcrumbs（何时触发、怎么写）

### 触发时机

在**用户给了大方向、AI 自己写实现细节**的过程中，出现下列情况就在写代码的同时顺手记一笔，不需要停下来问用户，也不需要在对话里逐条汇报。

**默认记**（成本低、返工代价高，见到就记）：

- 需求本身没说清楚的地方，自己补了一个默认行为/假设
- 用 workaround 绕开了某个限制、上游 bug 或边界情况，而不是根治
- 做了"先这样能跑、以后再优化"的取舍（性能 vs 简单、硬编码 vs 可配置…）
- 选了特定的错误处理策略（静默失败 / 抛异常 / 返回默认值…）
- 故意没有按项目/团队常见的写法来写

**有条件记**（只有在影响面跨模块/跨文件时才记，单文件内部的不记）：

- 存在两种及以上差不多都能跑的实现方式，选了其中一种（数据结构、算法、库、并发模型…）
- 新建文件/模块时，目录结构、放在哪个位置是自己拿的主意，需求没规定

**不要记**：

- 纯粹的 bug 修复（修复方式没有可选分支）
- 命名/格式化/风格调整
- 只影响函数内部、且没有可选分支的实现细节
- 项目里本来就是标准做法的写法

⚠️ 注意一个反直觉的例外：**"为了绕开某个 bug 而做的兼容层/workaround"要记**，它不是普通 bug 修复——它是一条 A/B 选择（治标 vs 治本），后面的人最需要知道。

**同一决策只记一次**：对同一文件、同一处逻辑的后续普通编辑不再重复追加条目；只有当这次编辑**改变了**先前那条 breadcrumb 的选择时才新增一条，并在新条目里写 `取代：<旧条目的日期 + 文件路径>`。

### 格式

追加到 breadcrumbs 文件末尾。每条尽量在 3–4 行内说完，不要写成小作文：

```markdown
## 2026-09-19 14:32 — payment-service/retry.py
- **选择**：失败重试用指数退避，最多 3 次
- **原因**：避免下游服务故障时被重试请求进一步打垮
- **备选**：固定间隔重试（更简单，但故障时冲击更大）
- **状态**：active
```

字段说明：

- 标题行 `## <YYYY-MM-DD HH:MM> — <相对路径>` 是这条记录的**聚合锚点**，保持"时间 + 路径"的固定形状，方便日后按模块 grep。
- `备选` 字段**可选**。写不出真实备选时宁可删掉这一行，不要写"无"或"没有别的方案"凑格式。
- `状态` 只有四个取值：
  - `active`——还没被推翻
  - `superseded by ADR-000X`——已被正式决策取代
  - `superseded by breadcrumb @ <YYYY-MM-DD> — <路径>`——被后续某条 breadcrumb 直接推翻（不走 ADR 的场景）
  - `obsolete`——做法已废弃，但没有继任者

> 上面括号里的编号写法是默认形态；现场编号位数/前缀不同时（例如 `ADR-0001`），状态字段里的引用也跟着现场写。

## 第二层：正式 ADR（何时触发、怎么写）

### 总闸门：触发词命中 ≠ 触发

下面的信号表是**语言锚点**，不是关键词抓取。命中之后还要再满足至少一条，才生成 ADR：

- 存在两个以上可辨识的技术方案，且这次选择了其中一个；或
- 改变了此前的既定做法（含推翻一条 breadcrumb）。

只有触发词、没有方案分歧的日常表达（例如用户只是在否定一句文案）**不触发**。

### 触发信号

当对话里出现下面这类**纠正/拍板**语气的表达时触发（中英文皆可，这里列的是模式，不是穷举）：

| 类型 | 示例表达 |
|---|---|
| 否定+替换 | "这样不行，改成…" / "不要用A，换成B" / "don't use X, use Y instead" |
| 推翻此前方案 | "之前选的X有问题" / "改回…" / "revert to…之前的做法" |
| 明确拍板 | "我决定…" / "最终就用这个方案" / "I've decided…" / "let's go with…" |
| 否决 AI 的提案 | "不用这个方案，因为…"（哪怕 AI 给的方案能跑） |
| 结构/设计不满 | "结构不对，应该…" / "这样设计不好，应该…" |
| 重复出现的问题 | 同一类 bug/结构问题第二次出现，用户说"这次要根治" |
| 面向未来的规则 | "以后不要再…" / "以后统一用…" / "from now on always/never…" |
| 显式要求记录 | "记一下" / "这个要留档" |
| 架构边界调整 | "这个模块不该管…" / "这部分职责应该挪到…" |
| 合规/安全/性能倒逼 | 之前"能跑就行"的实现，因为硬约束被推翻重做 |

### AI 自主决策同样适用

当用户要求 AI 做双向钢人论证、方案对比分析，AI 自己分析完拍板选了某个方案并据此实施时，也要生成正式 ADR——不要因为"决策者是 AI 自己"就跳过记录，这类决策的推理过程往往只存在于当次对话里，一旦不记录，换个 session、换个工具，没人（包括 AI 自己）能找回当初为什么这么选。

两条额外约束：

- **状态默认 `Proposed`**，等用户确认后再改成 `Accepted`。AI 的自主决策不应自动获得与用户决策同等的权威性。
- **备选方案栏必须写出对方方案的最强理由**，禁止稻草人。把没被选中的方案写成明显更差的选项，等于伪造论证过程——这比不记录更有害。

### 编号逻辑

1. **先认现场的编号形态**（位数、前缀、分隔方式，见「复用既有目录时：先认约定，再续写」），照它续号；现场无约定时才启用默认的 4 位补零（`0001`、`0002`…）。
2. 只把**由上面「已有 ADR 目录」判定识别出来的 ADR 文件**、且符合现场编号形态的计入编号，取最大编号 +1。**编号可能只写在首行标题里、不在文件名里**（文件名 `ADR-dispatch-durable-queue.md`、首行 `# ADR-002:`）——这类照样计入，取标题里的最大编号 +1（→ `ADR-003`），并**沿用现场的命名形态**，不要顺手改成 `0003-xxx.md`。
3. 目录不存在或没有任何 ADR 时从起始号开始（默认 `0001`）。
4. 写入前检查目标文件名是否已存在；存在则再 +1，直到找到空位（防止多分支/多 agent 并发撞号）。
5. 编号是**约定式唯一**，没有中心注册表：多人分支合入时以先合入者为准，后合入者改号并同步修正所有指向它的链接。

### 模板

新建 `<序号>-<短标题-用连字符>.md`（序号形态跟随现场约定；全新创建时用 4 位补零）。

下面是**默认形态**的模板。**现场已有模板时，以现场模板的字段名与章节为准**，只借用下面的"背景 / 决策 / 备选 / 后果"这套信息骨架：

```markdown
# ADR-000X: <一句话标题>

- **状态**：Accepted | Proposed | Superseded by ADR-YYYY
- **日期**：2026-09-19
- **决策者**：用户 | AI（经双向钢人论证分析后自主决策）——仅当决策者是 AI 时才需要这行，用户决策可省略
- **取代**：Breadcrumb @ <文件路径>（<日期>）—— 如果这次决策推翻了某条 breadcrumb，填这里；否则删掉此行
- **被取代**：——（如果以后这条 ADR 又被新的 ADR 推翻，回来这里补上新 ADR 编号和链接）

## 背景
简述当时面临的问题/需求/约束是什么，为什么需要做这个决策。

## 决策
最终选择了什么方案，用一两段话说清楚，不要照抄代码 diff。

## 考虑过的备选方案

- 方案B：是什么，为什么没选

这个决策带来的好处和代价，包括明知道但接受的技术债或限制。
```

## 联动逻辑：两层记录连成演化链

生成正式 ADR 时，快速扫一遍 breadcrumbs，看这次决策涉及的文件/模块是否有对应的旧条目：

- 有 → 把那条 breadcrumb 的 `状态` 改成 `superseded by <这条 ADR 的编号>`，并在新 ADR 的"取代"字段里回链过去。
- 没有（全新决策，不是推翻隐性选择）→ "取代"这一行直接删掉，不要勉强找一个来关联。

同理，新 ADR 推翻旧 ADR 时，必须回改旧 ADR 的"被取代"字段。**这条最容易忘——把它当成写新 ADR 的必做步骤，而不是"以后记得"。**

### 写入顺序与幂等

一次决策涉及多处写入时，严格按这个顺序，任一步失败就停下并如实报告，不要继续往下写：

1. 先落盘 ADR 正文（新文件是唯一"无依赖"的写入）。
2. 再回改被取代的 breadcrumb / 旧 ADR 的状态字段（此时它引用的 ADR 已经存在，不会产生悬空链接）。
3. 最后更新索引 README。

回链**只允许指向已落盘存在的 ADR 编号**。如果第 2 步失败，第 3 步索引里那条 ADR 要标注为"待回链"，不能假装完整。

### 更新索引

每次新增 ADR 后，在记录目录的索引文件里加一行。默认是 `README.md` 表格：

```markdown
| 编号 | 标题 | 状态 | 日期 |
|---|---|---|---|
| [0001](0001-xxx.md) | 用指数退避做重试策略 | Accepted | 2026-09-19 |
```

现场用的是别的索引文件或别的列顺序 → **跟现场**，别为了套上面的格式而多建一张表。

首次创建 `README.md` 时，除了这个空表格，开头加几句话说明这套约定（两层记录是什么、breadcrumbs 文件是什么、**格式的权威定义在哪**），方便任何人类或 AI 工具打开这个目录就能看懂。

> 若发现该目录的 README 是由脚本/静态站点生成的（文件头有生成标记），不要手改：分别记录到生成源，并提示用户重新生成。

## 写完自检

落盘后花一次动作自查，避免留下悬空引用（这类机制一旦自相矛盾就再也没人信）：

1. **编号唯一**：目录内不存在两个相同编号的 ADR 文件。
2. **索引对齐**：每条新 ADR 在索引里有且只有一行，链接可达。
3. **回链闭合**：被取代的 breadcrumb/旧 ADR 的状态字段已改，且指向的编号真实存在。
4. **约定一致**：新增文件的编号形态、文件名、字段名与索引格式，与**现场**（定义见「存放位置」）的既有文件一致（全新创建时用本 skill 的默认形态）。
5. **无越界**：本次写入没有触碰 `CLAUDE.md` / `AGENTS.md` / 根 `README.md` 等约定文件。

任一条不通过，先修好再结束，并在回复里说明。

## 语言

breadcrumbs 和 ADR 的内容语言按以下优先级决定：

1. 项目既有记录/代码注释的语言（看记录目录或代码库现状）；
2. 当前对话使用的语言。

两者冲突时**以项目为准**（英文代码库 + 中文对话 → 记录写英文）。不要固定死用某一种语言。

## 一个重要的分寸

宁可少记，不要多记。第一层的目的是让"以后修正更便宜"，不是让用户逐条审查 AI 的每个实现细节——为了凑触发条件硬写，反而制造噪音，让这套机制变得没人看、没人信。

但"少记"不是一句态度，而是一条可操作的判据：

> **能否在 3 行内说清"选了 A 而不是 B，因为 C"？**
> 能 → 记。不能（要么没有 B、要么说不出 C）→ 不记。

用这条替代"拿不准就不记"，既挡住了噪音，也不会让 breadcrumbs 退化成几乎不写。

## 回复里怎么说

落盘不需要事先征求同意——触发条件就是"决策已经发生"，写下来只是把既成事实落盘。写完后用一句话提示即可（例如"已记录为 ADR-0003"、"已在 breadcrumbs 补了 retry 策略那条"），**不要逐条念给用户听**，也不要贴出模板全文。降级情况（无写入能力 / 不是有归属的项目根）则改为提示"这里值得记一条 breadcrumb/ADR"。
